# Dashboard

The Dashboard is the first section of the sidebar and the one a new main window opens on. It summarises the window's active project on one screen with widgets: what the project is, how many tickets it has in each status, its recent chats, what it has cost and, for a Go service, the pods where it runs and, when its graph is enabled, how its services call each other. A click on a row of the sidebar's Sub Projects category shows the Dashboard of that sub project in the same way, without switching the active project. Each project has its own list of widgets, stored in its project file, which the user changes in edit mode: adding and removing widgets, placing and sizing them on a grid, and setting what each one shows. Every value comes from the window's workspace, which the engine's events keep current, so the Dashboard changes live on This Mac and on remote devices. This document specifies the grid the widgets are placed on, the widgets and their settings, edit mode, where each value comes from and what a click on them does.

## Section

| Property    | Value                                                                                      |
| ----------- | ------------------------------------------------------------------------------------------ |
| Section     | `dashboard` ([ProjectSection](engine-api.md#projectsection))                               |
| Title       | `Dashboard`                                                                                |
| SF Symbol   | `square.grid.2x2`                                                                          |
| Shortcut    | ⌘1 ([Menus and keyboard shortcuts](ui.md#menus-and-keyboard-shortcuts))                    |
| Sidebar row | the first row ([Sidebar](ui.md#sidebar))                                                   |
| Default     | the section of a new main window (`WindowState.section`, [WindowState](ui.md#windowstate)) |

The symbol is a design-time choice. Default chosen at design time.

A click on a row of the sidebar's Sub Projects category shows the Dashboard of that loaded descendant of the active project in the centre column, without activating it ([Sidebar](ui.md#sidebar)): the window's active project, its breadcrumb, its sidebar and its inspector stay, the clicked row is selected and the window keeps its section (`WindowState.subProjectDashboardID`, [WindowState](ui.md#windowstate)). It is the sub project's own Dashboard: its widget list and their settings, its name, type, folder, ticket counts and cost, and its recent chats. In this document, the shown project is the project whose Dashboard the centre column shows: the active project, or that sub project.

- The active project's Dashboard has a title row: a pane header 36 points high that spans the centre column, with the title `Dashboard` in the headline font, above the bar with the `Edit` button ([Pane headers](ui.md#pane-headers)). It stays at the top while the widgets scroll.
- A sub project's Dashboard has, in place of the title row, a pane header 36 points high with the sub project's name in the headline font, above the bar with the `Edit` button.
- While the sub project is loading, or after its loading failed, the centre column shows the loading or failure state of [Empty states](ui.md#empty-states) in place of its Dashboard, as for a section of the active project.
- The window leaves it as [Sidebar](ui.md#sidebar) specifies: by anything that selects a section, by View ▸ Global Memories and View ▸ Internal Skills, by a switch of project or device, and when the sub project is removed, hidden or no longer loaded.

The title row ([R194](requirements.md#requirements)), the pane header of a sub project's Dashboard and the sub project's own Dashboard come from the user. The headline font of the sub project's name and the loading and failure states are design-time choices. Default chosen at design time.

## Layout

The centre column shows a bar with the `Edit` button at its top right, after the `Window` menu of the [graph widgets](#graph-widgets) while the Dashboard shows one, under the title row of the active project's Dashboard or the pane header of a sub project's Dashboard ([Section](#section)), and under it the widget area: the shown project's [widgets](#widgets), each at the place and with the size it has on the [grid](#grid). The widget area scrolls vertically when the widgets are higher than it. Each widget has its title in the headline font and a rounded background in the system's secondary fill colour. A project whose list has no widget shows only its title row or pane header and the bar with the `Edit` button. The bar is a design-time choice. Default chosen at design time.

### Grid

The widget area is an invisible grid of 24 columns of square cells, as in Grafana. The grid is never drawn, in or out of edit mode.

- **Cells.** The widget area is as wide as the centre column without a margin of 20 points on each side and, when macOS always shows scroll bars, without the width of the area's scroll bar, whether that bar shows or not. Neighbouring cells are 16 points apart, so a cell is (width of the area − 23 × 16 points) / 24 wide, and as high as it is wide.
- **Widgets.** A widget covers whole cells: a column, 0 to 23 from the left; a row, 0 or more from the top; a width in columns, 1 to 24, with column + width at most 24; and a height in rows, 1 or more. Its frame starts column × (cell + 16) points from the left of the area and row × (cell + 16) points from its top, and it is width × cell + (width − 1) × 16 points wide and height × cell + (height − 1) × 16 points high. Neighbouring widgets are therefore 16 points apart.
- **Scaling.** The cells scale with the width of the centre column, so every window and every device shows the same arrangement. They keep shrinking down to the centre column's minimum width of 540 points ([Main window layout](ui.md#main-window-layout)), where a cell is 5.5 points wide, or less by the room kept for the scroll bar; a widget whose content no longer fits then scrolls it ([Content](#content)).

The 24 columns of square cells, the gap of 16 points, which the widgets had before the grid, and the cells that scale with the width and keep shrinking come from the user. The margin of 20 points and the room kept for the scroll bar, without which a bar that showed would make the cells smaller, the widgets lower and itself useless, are design-time choices. Default chosen at design time.

### Placement

The place and the size of a widget are the keys `column`, `row`, `width` and `height` of its entry in the list ([Dashboard widget](data-model.md#dashboard-widget)): its stored position. The Dashboard places the widgets it shows as Grafana does, free and floating up, with the placement rule:

1. It takes the stored positions of the shown widgets in order of row, then of column; widgets with the same row and the same column come in list order.
2. Each widget, in that order, moves down below any widget placed before it that it overlaps, until it overlaps none, then rises as far as it can without overlapping a widget placed before it, up to row 0.

- No empty row stays above a widget, and stored positions that overlap, for example written by hand, are resolved: the widget that comes later in the order moves down.
- The rule changes what the Dashboard shows, never the project file: a widget keeps its stored position until a change made in [edit mode](#edit-mode) stores another one.
- Graph widgets hidden while the graph is not enabled ([Graph widgets](#graph-widgets)) take no place: the other widgets rise into their space. Every widget keeps its stored position, so when the graph is enabled again the graph widgets take their stored places and the widgets that had risen into them move down. A move, a resize, an addition or a removal made meanwhile stores the other widgets where they had risen ([Edit mode](#edit-mode)): the stored positions then overlap, and the rule resolves them as any others, so a graph widget that comes later in the order is the one that moves down.
- A project file edited by hand can hold a position outside the grid, since the engine checks it only when it writes it ([Write rules](data-model.md#write-rules)). The Dashboard then counts a width within 1 to 24, a column that keeps the widget inside the 24 columns, a row within 0 to 100000 and a height within 1 to 100000. A widget with only some of the four keys counts as a widget without position.

The free placement that floats up comes from the user. The order of widgets with the same row and column and the display of positions written by hand are design-time choices. Default chosen at design time.

### Lists without positions

A widget has no stored position while its entry has none of the four keys: every widget of the default list and of a list stored before the grid, and a widget whose keys were removed by hand. The Dashboard places the shown widgets without position in list order, two per row:

- The first of a pair is at column 0 and the second at column 12, each 12 columns wide and with as many rows as its content needs at the cell size of the window: the fewest rows that hold its title row, its content at that width and its padding.
- The first pair starts under every shown widget that has a stored position, at row 0 when there is none, and each pair starts under the previous one. The widgets then rise by the [placement rule](#placement), so the widget under a short one leaves no empty row above it.
- While they have no stored position, their rows follow their content and the cell size of the window. A Service graph widget counts a map 260 points high, and a Requests per minute widget a chart 120 points high, whatever they show.
- A project without a stored list therefore shows Project and Tickets side by side on the first row, and Recent Chats and Cost under them, each half the width of the Dashboard.

The first move, resize, addition or removal made in edit mode stores the positions and the sizes that the Dashboard shows, with that change ([Edit mode](#edit-mode)).

Two widgets per row, each half the width and as high as its content, come from the user. The 260 and 120 points, the heights the map and the chart had before the grid, are design-time choices. Default chosen at design time.

### Content

The title row stays at the top of the widget, and the content has the space under it. Content larger than that space scrolls inside the widget, in the direction where it does not fit:

- The content is laid out at the width of the widget: a text that does not fit is truncated or wrapped onto more lines, as before the grid. The content scrolls vertically when it is higher than the space under the title row.
- It scrolls horizontally when it cannot be as narrow as the widget: the counts of a Tickets widget, the total of a Cost widget, the numbers of calls of a Busiest calls widget, the status and the start time of a failed request and the number of a Requests per minute widget are never truncated or wrapped.
- The map of a Service graph widget and the chart of a Requests per minute widget fill the space, whatever its size ([Graph widgets](#graph-widgets)); such a widget scrolls only when what it shows with them, its number or a message, is larger than the space.
- Nothing is drawn outside a widget: one smaller than its title row and its padding, which only a narrow window or a hand edit gives, shows the part that fits.
- A scroll with the pointer over a widget scrolls the Dashboard when the content of that widget does not scroll in that direction.

The content that scrolls inside the widget, under the title row, comes from the user. What is truncated, wrapped or scrolled horizontally, the clipping and the scroll over a widget are design-time choices. Default chosen at design time.

## Widgets

A project without a stored list shows the default list: Project, Tickets, Recent Chats and Cost, in this order, each with the default values of its [settings](#settings) and without stored position ([Lists without positions](#lists-without-positions)); the Instances widget is not in it. A list can hold each kind any number of times, each widget with its own settings.

### Instances widget

An Instances widget lists the pods where a Go service runs: the pods of the deployment of the shown project's [current working environment](projects.md#current-working-environment), found with the deployment's [label selector](engine-api.md#label-selector) as [k8s_status](mcp.md#k8s_status) finds them, in kubectl's order. It follows the current working environment, which the user chooses next to the project identifier in the sidebar footer ([Sidebar](ui.md#sidebar)), and has no environment of its own. The engine of the main device reads the pods with [kubernetes.pods](engine-api.md#kubernetespods): kubectl runs on the main device, so the widget works in the windows of remote devices too.

It is a table with the column headers of `kubectl get pods -o wide`, in their order, one row per pod:

| Column     | Value                                                                                                                               |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `Name`     | The pod's `name`.                                                                                                                   |
| `Ready`    | `<ready containers>/<containers>`: its `readyContainers` and `containers`, for example `1/1`.                                       |
| `Status`   | A coloured dot, then kubectl's STATUS, the pod's `status` ([Pod STATUS](engine-api.md#pod-status)), for example `CrashLoopBackOff`. |
| `Restarts` | Its `restarts`.                                                                                                                     |
| `Age`      | Its `age`, in the format of [Pod age](engine-api.md#pod-age), for example `5m12s`.                                                  |
| `Node`     | Its `node`; empty while the pod is not scheduled.                                                                                   |

The dot's colour:

| Colour                  | When                                                                                                                                                                                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| green (`systemGreen`)   | The STATUS is `Running` and every container is ready (`readyContainers` equals `containers`).                                                                                                                                      |
| orange (`systemOrange`) | The pod starts or stops: `Pending`, `ContainerCreating`, `PodInitializing`, `Init:<n>/<m>`, `Terminating`, or `Running` with not every container ready.                                                                            |
| red (`systemRed`)       | The pod fails: `Failed`, `Error`, `CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull`, `CreateContainerConfigError`, `OOMKilled`, `Evicted`, and `Init:` followed by one of these reasons, for example `Init:CrashLoopBackOff`. |
| grey (`systemGray`)     | Any other STATUS, for example `Completed`, `Succeeded`, `NotReady` or `Unknown`.                                                                                                                                                   |

- A deployment without pods shows the headers alone. A click on a row does nothing.
- A small spinner shows in place of the table while the first read runs, and again when the current working environment changes, until the first read of the new one ends.
- A project without environment, which is always the case for a project whose type is not `goService`, shows `Add an environment in Project Settings.` with a `Project Settings…` button, which selects the window's Project Settings section ([Environments](projects.md#environments)). It calls no method.
- An environment without a deployment shows the message of `kubernetes.pods`, `Environment “<name>” has no deployment.`, `<name>` being the environment's name, without calling it.
- A failed read, kubectl's failures included, shows the engine's message in red in place of the table, until a later read succeeds.

The widget, its columns, its STATUS and the colours of its dot, the empty table, the click that does nothing, the spinner of the first read, the messages and the reads every 10 seconds come from the user. The spinner after a change of environment, the place of the spinner, the colour of the message of an environment without a deployment, the widget of a project of another type and the 10 seconds counted from the end of a read are design-time choices. Default chosen at design time.

### Graph widgets

The four kinds Service graph, Busiest calls, Failed requests and Requests per minute are the graph widgets: they show the [Graph](graph.md) of the shown project and its requests. They read the namespace and the Jaeger of the shown project's [current working environment](projects.md#current-working-environment), as the Instances widget reads its pods, with [graph.read](engine-api.md#graphread), whose engine runs on the main device, so they work in the windows of remote devices too.

- **Enabled graph.** While the shown project's graph is enabled (`graphEnabled` of its [ProjectDetail](engine-api.md#projectdetail), [Enabling](graph.md#enabling)), the Dashboard shows its graph widgets and the `Add Widget` menu offers them. While it is not, they are hidden, in and out of edit mode, and not offered, and the list keeps them: they show again when the graph is enabled again.
- **Window.** The time window of the graph widgets is the Dashboard's: the `Window` menu, in the bar of the `Edit` button, at its left, while the Dashboard shows a graph widget, in and out of edit mode. It lists `Last 5 minutes`, `Last hour`, `Last 24 hours` and `Last 7 days`, with a check mark before the window of the project, `Last hour` by default. Choosing one applies it at once with [projects.update](engine-api.md#projectsupdate) and `dashboardGraphWindow` ([Project file](data-model.md#project-file)), so every window and device shows it; every graph widget uses it. A failed call shows the engine's message in red under the bar, as a change of edit mode does.
- **Reads.** The Dashboard reads the graph once for all its graph widgets, with [graph.read](engine-api.md#graphread): when it shows a graph widget, then 5 seconds after the end of each read while it shows one, and at once when the window, the current working environment or one of its fields changes. The engine gives one read to the calls made for the same project, environment and window within 2 seconds, so that the Dashboards and Graph sections of several windows share them.
- A small spinner shows in place of the content while the first read runs, and again when the window or the current working environment changes.
- Without environment, a graph widget shows `Add an environment in Project Settings.` with a `Project Settings…` button, as the Instances widget does. A failed read shows the engine's message in red in place of the content, until a later read succeeds.
- Without Jaeger, or when Jaeger cannot be reached, Service graph shows its map with every arrow grey and, under it, `Jaeger cannot be reached: <reason>` ([Without Jaeger](graph.md#without-jaeger)); the three other widgets show that message in place of their content.
- **Service graph.** The whole graph, laid out as the Graph section lays it out ([Layout of the graph](graph.md#layout-of-the-graph)). The map fills the content area of the widget, above the Jaeger message when there is one, and the graph is fitted to it at 150% at most, the numbers of calls written on the arrows when the zoom is 50% or more and the names hidden below 30%. It cannot be zoomed or panned. A click on it, out of edit mode, opens the Graph section of the shown project, which a sub project's Dashboard activates ([Actions](#actions)).
- **Busiest calls.** The arrows that have at least one call in the window, the busiest first, arrows with the same number by their order in the graph; `No calls in the window.` when no arrow has one. The colour of each number is the colour of its arrow in the Graph section ([Colour of an arrow](graph.md#colour-of-an-arrow)).
- **Failed requests.** The requests of the window whose status is 400 or above, newest first; `No failed requests in the window.` when there is none. The start time is written `HH:mm:ss`. A click on a row, out of edit mode, opens the Graph section of the shown project with the view of that request ([Request view](graph.md#request-view)).
- **Requests per minute.** The window is cut into minutes from its end: the last point counts the requests that started in the last 60 seconds of the window, the one before it the 60 seconds before, and so on, the requests of the window being those of the [request list](graph.md#requests); the chart has one point per minute of the window, from its start at the left to its end at the right, its vertical axis starting at 0. The chart fills the content area left under the number and its caption. The large number is the last point's.

The four widgets, their contents, the Number setting, the Window menu with its windows, its default and its storage in the project file, the widgets hidden and kept while the graph is disabled, the click that opens the Graph and the click that opens a request come from the user. The map and the chart that fill their widget come from the user too. The arrows without call left out of Busiest calls, the order of equal counts, the empty texts, the caption, the minutes counted from the end of the window, the place of the menu, the shared reads and the messages are design-time choices. Default chosen at design time.

## Edit mode

The `Edit` button enters edit mode, in which the user changes the shown project's widget list, a sub project's own list on its Dashboard; the button then reads `Done`, which ends edit mode. In edit mode:

- Each widget shows a remove button at the start of its title row, the SF Symbol `minus.circle.fill` in red with the tooltip `Remove Widget`, which removes the widget at once, and a settings button at the end of its title row, the SF Symbol `slider.horizontal.3` with the tooltip `Widget Settings`, which opens a popover with the widget's [settings](#settings). Removing a widget lets the widgets under it rise.
- **Move.** A widget is dragged by any point other than its buttons and its resize handle. It follows the pointer, drawn above the other widgets, which it hides, and a placeholder, a rounded outline in the accent colour, shows the cells where it will land. The Dashboard takes the cells nearest to the widget's top-left corner, kept inside the 24 columns and at row 0 or below, and applies the [placement rule](#placement) to the arrangement it showed when the drag started, with the widget at these cells and placed before the other widgets that start on its row. The widget lands where the rule puts it, and the other widgets make room live. Releasing the widget applies the arrangement.
- **Resize.** Each widget shows a resize handle at its bottom-right corner, the SF Symbol `arrow.up.left.and.arrow.down.right`, with the tooltip `Resize Widget`; the pointer is the diagonal resize cursor over it and while resizing. The handle is drawn in the caption font and the secondary label colour, and a square of 18 points at the corner takes the drag. Dragging it changes the width and the height together: the widget's bottom-right corner follows the pointer, and the placeholder shows the size it will take, snapped to the whole cells nearest to that corner. The widget keeps its column, its width never goes past column 24, the other widgets make room live as for a move, and releasing the handle applies the arrangement.
- **Smallest size.** A widget cannot be made smaller than its title row: the columns needed by the title row at full width, with the remove button, the whole title, the settings button and the padding, at most 24, and the rows needed by its height with the padding, both at the cell size of the window. Column 24 comes first: a widget whose title row needs more columns than its column leaves up to column 24 takes those. A stored widget smaller than its title row, for example after the window narrowed, keeps its size until it is resized, and its title is truncated.
- **Scrolling.** While a widget is moved or resized with the pointer within 40 points of the top or the bottom edge of the visible area, or beyond that edge, the Dashboard scrolls that way: faster the nearer the pointer is to the edge, at 600 points per second at the edge and beyond. The widget stays under the pointer.
- The `Add Widget` menu, at the left of `Done`, lists `Project`, `Tickets`, `Recent Chats` and `Cost`, then `Instances` when the shown project's type is `goService`, then `Service graph`, `Busiest calls`, `Failed requests` and `Requests per minute` while its graph is enabled ([Graph widgets](#graph-widgets)). The chosen widget is appended to the end of the list with the default values of its settings and a new id, at column 0 under every widget the Dashboard shows, 12 columns wide and with as many rows as its content needs at the cell size of that window ([Lists without positions](#lists-without-positions)); then it rises by the placement rule. A widget whose content is still read when it is added, such as the pods of an Instances widget, is as high as what it shows then.
- The content of a widget takes no click and no scroll: the rows of Recent Chats widgets open no chat, and a scroll over a widget scrolls the Dashboard.

Every change applies at once, without Cancel: the Dashboard sends the whole new list of the shown project with [projects.update](engine-api.md#projectsupdate), and the first change of a project without a stored list stores the default list with that change. A move, a resize, an addition and a removal give each shown widget the position and the size that the Dashboard shows once the change is made, whether the widget had a stored position or not, and the hidden graph widgets keep theirs; a change of a widget's settings stores no position. A widget released where it was, or at the size it had, changes nothing. Changes made in quick succession are sent one after the other, each made from the stored list once the `project.updated` of the previous one has arrived, or after 2 seconds without it. Every window and device shows the new list when `project.updated` arrives ([Live updates](#live-updates)). When the call fails, the engine's message shows in red under the bar until the next change, whether the change was made in the bar, on a widget or in a settings popover, and the widgets keep showing the stored list. A change made just before the Dashboard goes away, such as a Title applied when showing another section closes its popover, is still sent.

Edit mode belongs to the window: it ends when the window shows another section, project or device, when it leaves a sub project's Dashboard or shows another one, when the connection to the window's remote device drops ([Reconnect view](ui.md#reconnect-view)), and when the window closes. Out of edit mode the widgets show no buttons and no handle, and cannot be moved or resized.

The move with its placeholder, the resize handle with its SF Symbol and its cursor, the smallest size, the scrolling during a drag and the place and the size of an added widget come from the user. The SF Symbols of the buttons, their colour, the place of the buttons and of the messages, the widget placed before the others of its row, the look of the handle and its square of 18 points, the 40 points and the speed of the scrolling, the height of a widget added while its content is read, the content that takes no scroll, the positions a change of settings does not store, the order of quick changes with its 2 seconds and the scope of edit mode are design-time choices. Default chosen at design time.

## Settings

The settings button of a widget opens a popover with the settings of its kind. Each change applies at once with `projects.update` on the shown project: a click on a checkbox or on the stepper, which changes the stored value, so that each of several quick clicks counts; the `Title` field on Return, when it loses the focus or when the popover closes, once the user has changed its text. A title changed in another window or on another device replaces the text of the field unless the user has changed it. The popover has no Cancel or Save button.

| Setting              | Widgets                        | Control                                                   | Default     | Effect                                                                                                                                                                                            |
| -------------------- | ------------------------------ | --------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Title                | every widget                   | text field with the title of the kind as placeholder      | empty       | The widget's title; empty means the title of its kind. One line of at most 100 characters after trimming: `Enter a title of at most 100 characters.` under the field, which then applies nothing. |
| Fields               | Project                        | checkboxes `Name`, `Identifier`, `Type` and `Folder`      | all checked | The fields the widget shows.                                                                                                                                                                      |

- The last checked box of a group (Fields, Statuses or Chat kinds) cannot be unchecked: it is disabled while it is the only checked box of its group.
- The settings, their labels, their values, their defaults and the rule of the last checked box come from the user; the stepper, the placeholder, the length limit of the title and its message are design-time choices. Default chosen at design time.

## Actions

Out of edit mode, a click on a Service graph widget opens the [Graph](graph.md) section of the shown project, and a click on a row of a Failed requests widget opens it with the view of that request ([Request view](graph.md#request-view)); on a sub project's Dashboard, the window activates the sub project and shows its Graph. A click on a row of a Recent Chats widget opens the chat where it is listed ([Navigation](ui.md#navigation), target `chat`): in the Chats tab of its ticket or bundle for a ticket, bundle or CI chat whose ticket or bundle exists, otherwise in the Chats section of its project ([Resolving a target](ui.md#resolving-a-target)); on a sub project's Dashboard, the window activates the sub project and selects the chat there. The other widgets have no action: a click on a row of an Instances or Busiest calls widget does nothing. In edit mode the actions are those of [Edit mode](#edit-mode).

## Live updates

The Dashboard reads only data that the workspace keeps: the summaries and the chat metadata of every project of the device, and the detail of the shown project: the active project's, which the window loads before it shows any section, or the sub project's, which the window loads with the active project's loaded descendants. The events update the Dashboard of a sub project as that of the active project, on This Mac and on remote devices. Apart from the pods of the Instances widgets and the graph of the graph widgets, it needs no loading of its own and no method or event of its own ([DeviceWorkspace](ui.md#deviceworkspace), [Event handling](ui.md#event-handling)):

| Value                                  | Changed by                                                                                                                                                                                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Widgets, their settings and positions  | `project.updated`, emitted when the project file is written or reloaded: a change made in edit mode in any window or on any device, or an edit by another program ([External changes](data-model.md#external-changes)).                                       |
| Name, type, folder, counts, cost       | `projects.changed`, emitted when a project's summary changes: a rename, a new type, a ticket created, deleted or moved to another status, a chat's cost ([Live updates](costs.md#live-updates)).                                                              |
| Recent chats                           | `chat.updated` and `chat.deleted`.                                                                                                                                                                                                                            |
| Pods of an Instances widget            | [kubernetes.pods](engine-api.md#kubernetespods): when the widget appears, 10 seconds after the end of each read while the Dashboard shows it, and at once when the current working environment or its fields change.                                          |
| Graph of the graph widgets             | [graph.read](engine-api.md#graphread), once for all of them: when the Dashboard shows a graph widget, 5 seconds after the end of each read while it shows one, and at once when the Dashboard's window, the current working environment or its fields change. |
| The Dashboard's window, `graphEnabled` | `project.updated`                                                                                                                                                                                                                                             |

## Requirements covered

- R106: A Dashboard section summarises the active project: its identity and type, ticket counts, recent chats and cost.
- R152: A project's Tickets section lists the tickets of its sub projects too.
- R163: When the active project has sub projects, the sidebar lists them all in a Sub Projects category, indented by depth, each with its icon in its color, and a click on one shows its Dashboard without switching the active project.
- R170: The user adds, removes, moves and configures the widgets of each project's Dashboard.
- R178: The Dashboard of a Go service can show an Instances widget listing the pods of the current working environment with their status.
- R193: The Dashboard of a Go service whose graph is enabled can show a service graph, the busiest calls, the failed requests and the requests per minute of a time window chosen on the Dashboard; a click on the graph or on a failed request opens the Graph section.
- R194: Every section of the main window shows a title, and so do the Global Memories and Internal Skills views: Dashboard, Tickets, Bundles, Chats, Web, Builds, Skills, Memories and API Explorer show their sidebar title in a title row above their left column.
- R200: The user places and sizes each widget of a project's Dashboard on an invisible grid of 24 columns of square cells, like Grafana.
