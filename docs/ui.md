# User interface

HephaestusV2's windows are clients of one device's engine. This document specifies the application shell: the windows and their lifecycle; the main window with its toolbar, the `Device ▸ Project ▸ Sub project` breadcrumb selector, the sidebar, the project chat inspector and the status bar; every menu item and keyboard shortcut, in one table; unsaved changes and quitting; the app-level empty states, including the reconnect view; the Settings window; and the UI state model (`AppModel`, one `DeviceWorkspace` per device connection, one `WindowState` per main window) with navigation through `NavigationTarget`. What each sidebar section shows is specified in that section's document; this document only places it.

## Principles

| Rule                | Behaviour                                                                                                                                                                                                                                                                                                                                                                                              | Origin                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| One API             | Views never read project files or data-directory files. | Live state          | One `DeviceWorkspace` per device holds that device's data, built from its snapshot and kept current by engine events, so changes made in another window, on another device, by Claude or on disk appear without a refresh.                                                                                                                                                                             | Brief §2.1                                          |
| Cache updates       | A workspace changes its data only from snapshots, seeding call results and events. A mutation result serves only the flow of the view that made the call, for example selecting the ticket it created ([Events and ordering](architecture.md#events-and-ordering), [Seeding calls and the replay rule](remote.md#seeding-calls-and-the-replay-rule)).                                                  | [Architecture](architecture.md#events-and-ordering) |

The scene ids, the window titles and subtitles, the window sizes and the restoration column are design-time values; the chat window's title follows the chat title (Brief §5.3). Default chosen at design time.

- Automatic window tabbing is disabled (`NSWindow.allowsAutomaticWindowTabbing = false`): windows never merge into native tabs, and View ▸ Show Tab Bar does not exist. Default chosen at design time.
- Closing the last window does not quit the app; the engine, its servers and Claude processes keep going. Default chosen at design time.
- At launch, macOS state restoration reopens the previous session's main windows, each with its persisted [WindowState](#windowstate), and its chat windows. When nothing is restored, one main window opens on This Mac with the default project of the [project selector](projects.md#project-selector); when, 1 second after the app has finished launching, no window is open and none was restored, the app opens that window itself and logs the warning `no window was open after launch; opening a main window` (component `ui`). The menu commands keep the `openWindow` action of the SwiftUI environment from launch on, so the app can open this window before any window exists. A process started with `HEPHAESTUS_DATA_DIR` or `HEPHAESTUS_WINDOW_SCREEN` restores no window and saves no window state ([Environment overrides](architecture.md#environment-overrides)). macOS restores them only when Close windows when quitting an application is off, or after Quit and Keep Windows (⌥⌘Q). A restart for an update keeps the windows in every case: before posting `app.quitting` with `restart` true, `AppModel` writes the persisted `WindowState` of every main window and the `ChatWindowValue` of every chat window, front to back, to the `UserDefaults` key `windowsAtRestart`; at the next launch, when that key exists, the app opens exactly those windows, deletes the key and disables macOS restoration for that launch (`restorationBehavior(.disabled)`). The key holds a JSON array, front to back, of `{"main": <the persisted WindowState as JSON text>}` and `{"chat": {deviceID, chatID}}` objects; a value that cannot be decoded is deleted and counts as absent. When the restart does not happen (the Updater does not answer `installing`), the app deletes the key, so the next launch restores as usual. A process started with `HEPHAESTUS_DATA_DIR` or `HEPHAESTUS_WINDOW_SCREEN` neither writes nor reads the key. Default chosen at design time.
- `HEPHAESTUS_WINDOW_SCREEN` places every window as [Window placement](architecture.md#window-placement) specifies.
- A chat window shows one chat of one device. Opening a chat that already has a window brings that window to front. A chat window closes when its chat is deleted, when its project is removed and when its device is removed from the paired devices. Default chosen at design time.
- Each main window has its own device, active project, section and panel visibility; several windows may show different devices at once.

The sizes are design-time values, except the 26-point status bar (Brief §9.1). Default chosen at design time.

At its minimum width of 190 points, the sidebar is wider than the toolbar's leading item, the Sidebar button, which ends inside its width, and it holds the Project Settings row on one line.

A main window opens with the sidebar at its default width and the inspector at `inspectorWidth` ([WindowState](#windowstate)), 380 in a new window. A pane shown again takes its width back: the inspector `inspectorWidth`, the sidebar its last width in this window, 200 at first. Only a divider dragged by the user changes these widths; the inspector's new width is then stored in `inspectorWidth`, while the sidebar's width is not persisted. Default chosen at design time.

A drag that collapses the sidebar ([Sidebar](#sidebar)) does not change its last width.

The sidebar, the centre column and the inspector are the three panes of one `NSSplitView` with plain panes (SwiftUI `HSplitView`, or an `NSSplitView` wrapped with `NSViewRepresentable`); ⌃⌘S, ⌥⌘0 and the widths of the table above act on these panes. `NavigationSplitView` and the `.inspector` modifier are not used: the in-process capture of [Screenshot capture](feedback.md#screenshot-capture) leaves a `NavigationSplitView` sidebar column transparent and draws the text of an `.inspector` column without its vibrancy, while `HSplitView` panes render as shown (checked on macOS 27.2). Default chosen at design time.

The sidebar pane and the inspector pane are frosted: each is drawn over an `NSVisualEffectView` with the material `.sidebar` and the blending mode `.behindWindow`, so the desktop and the windows behind the app show through them, blurred, as in the sidebars of Finder or Music. The material follows the light and dark appearance and the window's active state (`.followsWindowActiveState`), and macOS makes it opaque when Reduce Transparency is on. The text and controls of the panes are drawn over the material without vibrancy. The centre column, the toolbar and the status bar keep their opaque backgrounds. The capture of [Screenshot capture](feedback.md#screenshot-capture) cannot render what is behind the window, so it fills the frosted areas with an opaque colour close to the material. The state and the absence of vibrancy are Default chosen at design time.

The toolbar is one plain band across the whole window width, whatever the window shows under it: its background is the window background colour (`NSColor.windowBackgroundColor`), opaque, in light and dark appearance, and only the window's close, minimise and zoom buttons and the toolbar items are drawn on it. No pane background, header, scrolled content or divider of the columns shows in the band, neither between the columns nor inside the centre column: the sidebar, the centre column with its panes, the inspector and the dividers between them are seen from the toolbar's bottom edge down, in every section and at every width of the panes.

SwiftUI lays the split views and their panes out under the toolbar whatever padding or safe-area modifier their container gets (checked on macOS 27.2), so the band is the toolbar's own opaque background, which covers the part of the columns under the toolbar: `toolbarBackground(_:for:)` with that colour and `toolbarBackgroundVisibility(_:for:)` set to `visible`, both for the `windowToolbar` placement. No line separates the band from the columns, not even above the scroll views at the top of the sidebar, Dashboard, Costs and Project Settings: macOS draws no scroll edge line under an opaque toolbar background. Drawing the band as the toolbar's background over the columns, which stay laid out under the toolbar, is Default chosen at design time.

The welcome view and the reconnect view replace the sidebar, the content and the inspector ([Empty states](#empty-states)). Only the search panel ([Search panel](search.md#search-panel)) is drawn over the columns.

### Pane headers

Every header bar at the top of a pane of the centre column, and the inspector's header, is 36 points high, from the toolbar's bottom edge to its bottom separator, so that the separators of all the headers of a window lie on one horizontal line.

The sections Dashboard, Tickets, Bundles, Chats, Web, Builds, Skills, Memories and API Explorer show their title in a title row: a pane header that holds only the title, in the headline font, at its leading edge. The title is the section's sidebar title ([Sidebar](#sidebar)): `Dashboard`, `Tickets`, `Bundles`, `Chats`, `Web`, `Builds`, `Skills`, `Memories` or `API Explorer`. The Global Memories view and the Internal Skills view show `Global Memories` and `Internal Skills` the same way.

- The title row is the pane header of the left column only: it sits above the list's filter field or header bar, and above the contract list of the API Explorer, which follow under its separator. The right column, an editor, a detail or a chat view, keeps its own header, on the same line.
- Dashboard and Web have a single column: their title row spans it, above the Dashboard's bar with the `Edit` button and above the Web tab strip.
- An empty state or a notice that takes the place of the whole section shows no title row: `No Memories`, `No Global Memories`, `No chats yet`, `No Web Tabs`, `No Skills`, and the notices of the API Explorer (the spinner while the file is read, `The file could not be opened.` and `The contract could not be read.`). The lists of the Tickets and Bundles sections keep their header bar when they are empty, so they keep their title row.
- Docs, Costs, Code, Graph, Views, Project Settings, a sub project's Dashboard, the detail of a virtual machine and the setup view of an image keep their headers and have no title row. The Contract view of the Code section has none either: only the API Explorer section shows `API Explorer`.

## Breadcrumb selector

The principal toolbar item shows up to three segments separated by the symbol `chevron.right`, like Xcode's scheme and destination control. Each segment is a menu button with an icon and a name; clicking it opens its menu. Which project a window selects and how it reacts to changes is specified in [Project selector](projects.md#project-selector).

| Segment     | Icon             | Title                                                                                           | Menu items, in order                                                                                                                                                                                                                                                                                                                      | Shown                                                                    |
| ----------- | ---------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Device      | `laptopcomputer` | `This Mac`, or the remote device's name followed by the dot of its [device state](#status-bar)  | `This Mac`; a separator; the paired devices in the order of [Paired devices](remote.md#paired-devices), each with a dot, green when [online](remote.md#online-status) and grey otherwise; a separator; `Add Device…` ([Adding a device](remote.md#adding-a-device)); `Manage Devices…` (opens the Settings window on [Devices](#devices)) | always                                                                   |
| Project     | `folder`         | the name of the active project's top-level project; `No Project` when the device has no project | the device's top-level projects in `projects.list` order; a separator; `New Project…` ([Creating a project](projects.md#creating-a-project)); `Open Project…` ([Opening an existing project](projects.md#opening-an-existing-project))                                                                                                    | always                                                                   |
| Sub project | `folder`         | the title of the checked menu item                                                              | `<top-level project name> (root)`; every descendant of the top-level project in `projects.list` order, indented by depth (`NSMenuItem.indentationLevel` = depth, at most 15); a separator; `New Sub Project…` ([Sub projects](projects.md#sub-projects))                                                                                  | when the active project's top-level project has at least one sub project |

- The current device, top-level project and active project carry a checkmark in their menus.
- Choosing a device changes only this window: the window shows the reconnect view until the device's workspace is connected, then the device's default project ([Project selector](projects.md#project-selector)).
- A segment title longer than 240 points is truncated in the middle.
- The selector has 12 points of horizontal padding on each side, between the border of the toolbar item's pill and its first and last segments.
- The pill sits on the plain band of the toolbar ([Main window layout](#main-window-layout)): in every section, at every width of the panes and in light and dark appearance, only that band shows behind it, with no change of colour and no divider.
- While the window's device is not connected, the Project and Sub project segments are disabled and show their last titles dimmed.

The segment icons, the dot in the Device title, the 240-point truncation and the disabled state are design-time choices. Default chosen at design time.

## Inspector

The inspector is the project chat panel in the right column ([Where chats appear](chats.md#where-chats-appear)).

- A new main window shows it. The toolbar's Project Chat button and View ▸ Show Project Chat / Hide Project Chat (⌥⌘0) toggle it; its visibility persists per window, and so does the width the user sets by dragging its divider ([Main window layout](#main-window-layout)).
- Header, 36 points high, its separator on the line of the centre column's header separators ([Pane headers](#pane-headers)): a pop-up button listing the active project's chats of kind `project` and its Auto Setup chats, of kind `setup` ([Auto Setup](virtual-machines.md#auto-setup)), most recently updated first, each with its title and the state indicator of [Where chats appear](chats.md#where-chats-appear), where the SF Symbol `progress.indicator` stands for the spinner, which cannot animate in a menu; a `New Chat` button (`plus.bubble`); an `Open in New Window` button (`macwindow.badge.plus`), disabled while a draft is shown, that opens the selected chat in a [chat window](#windows).
- Body: the chat view of the selected chat ([Chat view](chats.md#chat-view)).
- Background: the frosted material of [Main window layout](#main-window-layout), behind the whole column: the header, the transcript, the pinned cards, the status line and the composer. The chat view draws no background of its own there and the transcript's web view is transparent ([Web view and bridge](chats.md#web-view-and-bridge)); the message bubbles, the cards and the composer's field keep their backgrounds.

When the selected chat is deleted, the next most recently updated one is selected. With no chat in the pop-up, the inspector shows a draft chat ([Draft chats](chats.md#draft-chats)).
- `Auto Setup` of Settings ▸ Virtual Machines shows the inspector of the window that shows the setup view, when it is hidden, and selects the new Auto Setup chat in it.
- New Chat (the inspector button, the toolbar button, File ▸ New Chat ⌥⌘N) shows the inspector when it is hidden, shows a new draft chat in it (`inspectorShowsDraft`) and puts the keyboard focus in its composer. The draft is stored as a chat only at its first Send ([Draft chats](chats.md#draft-chats)).
- Ticket, bundle, feedback and CI chats are not listed in the inspector: feedback chats appear in the Chats section, and ticket, bundle and CI chats on their ticket or bundle, or in the Chats section once that ticket or bundle is deleted ([Where chats appear](chats.md#where-chats-appear)).

### Weekly usage

The Weekly usage item, in main windows and chat windows, shows the plan usage of the window's workspace (`planUsage`, [DeviceWorkspace](#deviceworkspace)): the newest weekly usage of the Claude account known to the connected devices ([Plan usage](engine-api.md#plan-usage), [Plan usage sharing](remote.md#plan-usage-sharing)). The 5-hour window is not shown anywhere.

- The ring, 12 points wide, is filled clockwise from the top to `utilization`, at most full. It is green below 0.8, orange from 0.8, and red when the account is limited: `status` is `rejected` or `utilization` is 1 or more. Its unfilled part is drawn in the separator colour.
- The percentage is `utilization` × 100 rounded to the nearest integer and capped at 100, as the CLI's `/usage` writes it: 0.685 gives `69%`, 1.04 gives `100%`.
- The tooltip, which is also the item's accessibility label, is `Weekly usage: <percentage>% used`.
- The item disappears when `resetsAt` passes, without waiting for an event, and appears again when a newer value arrives. It is hidden while no value is known.

A click opens the weekly usage popover under the item, with these lines:

| Line       | Text                                                                                                                                                                                                                                                | Shown                           |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| Title      | `Weekly usage`, in bold                                                                                                                                                                                                                             | always                          |
| Percentage | `<percentage>% used`                                                                                                                                                                                                                                | always                          |
| Reset      | `resets <weekday> <time>`: the weekday of `resetsAt` abbreviated in English, `Mon` to `Sun`, and its time in the Mac's short time format, both in the Mac's time zone, for example `resets Sun 14:00`, or `resets Sun 2:00 PM` with a 12-hour clock | always                          |
| Overage    | `Overage: <overageStatus>`, followed by ` · <overageDisabledReason>` when present and by ` · in use` when `isUsingOverage` is true, the CLI values written with spaces in place of underscores, for example `Overage: rejected · out of credits`    | when `overageStatus` is present |

The popover follows the workspace's value while it is open and closes when the item disappears. The ring's size, its unfilled colour, the bold title and the popover's place are Default chosen at design time.

## Unsaved changes and quitting

An unsaved editor is a code editor tab, the Docs section's doc buffer or the editor of the Views section ([Editor](views.md#editor)) whose content differs from what was last loaded or saved, or a skill whose form or open extra file does; a skill counts as one unsaved editor, with its own prompt, even when both have changes ([Saving](skills.md#saving)). The memory form of the Memories section and its `MEMORY.md` editor are unsaved editors too ([Saving](memories.md#saving)), and so are those of the Global Memories view, and the skill of the Internal Skills view, which belong to no project: removing a project does not count them. Unsaved editors belong to their window, not to the engine.

- Quitting checks unsaved editors first, then running work. Cancel at either step cancels the quit. A restart for an update runs the same checks with its own running-work alert ([Restart rules](updater.md#restart-rules)).
- `AppModel` counts This Mac's chats from the local workspace, which holds the metadata of every chat ([DeviceWorkspace](#deviceworkspace)).
- When a save fails (for example on a conflict), the close, the removal or the quit is cancelled and the editor shows the failure.
- A chat in state `waitingAnswers` is not counted unless its Claude process has background work running: its questions are stored and can be answered after the next launch.
- Ticket description edits are saved when the window closes, and when the app quits or restarts: after the checks, the app calls `tickets.update` for each changed description editor and waits for the answers, at most 5 seconds; a failure cancels the quit and shows the error ([Ticket detail](tickets.md#ticket-detail)). Comment and composer drafts are discarded.
- After confirmation the app shuts down as [Shutdown](architecture.md#shutdown) specifies. Chats of remote devices are not affected: they run on their own device.

The texts, the check order and the counted states are design-time choices. Default chosen at design time.

## UI state model

The UI state lives in `@MainActor @Observable` objects of the HephaestusUI module; their place in the architecture is in [UI state architecture](architecture.md#ui-state-architecture). Views read them and call their methods; a view keeps only presentation state of its own (scroll position, hover, focus, the composer text of a draft chat).

```
AppModel                       one per app
├── DeviceWorkspace            one per open device connection (This Mac's is always open)
│   └── EngineConnection       LocalEngineConnection or RemoteEngineConnection
├── WindowState                one per main window, refers to a DeviceWorkspace by deviceID
└── ChatWindowValue            one per chat window, refers to a DeviceWorkspace by deviceID
```

### AppModel

| Property                | Type                        | Meaning                                                                                                                                                                                                  |
| ----------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `localDeviceID`         | `String`                    | This Mac's device id (`device.yml`).                                                                                                                                                                     |
| `localWorkspace`        | `DeviceWorkspace`           | The workspace of the in-process engine; created at launch, never closed.                                                                                                                                 |
| `workspaces`            | `[String: DeviceWorkspace]` | Open workspaces by device id, This Mac's included.                                                                                                                                                       |
| `devices`               | `[DeviceEntry]`             | This Mac first, then the paired devices in the order of [Paired devices](remote.md#paired-devices). `DeviceEntry {id, name, isLocal, online}`.                                                           |
| `windows`               | `[UUID: WindowState]`       | The state of every open main window, by window id.                                                                                                                                                       |
| `keyWindowOrder`        | `[UUID]`                    | Main window ids, most recently key first.                                                                                                                                                                |
| `chatWindows`           | `Set<ChatWindowValue>`      | The open chat windows.                                                                                                                                                                                   |
| `lastProjectIDByDevice` | `[String: String]`          | Last active project per device, persisted ([Persistence](#persistence)).                                                                                                                                 |
| `minimizedQuestionSets` | `[String: String]`          | Minimized pinned question, symbol, color, sound, shortcut, font and animation cards: chat id → id of the minimized set or request, persisted ([Persistence](#persistence), [Chats](chats.md#questions)). |
| `updaterStatus`         | `UpdaterStatus`             | The last status received from the Updater; `idle` without version, build or message before the first one ([Updater states](updater.md#updater-states)).                                                  |
| `imageSetups`           | `[UUID: VMSetupSession]`    | The setups whose virtual machine runs, by image id, from `Set Up…` until the virtual machine has stopped, whether a window shows them or not ([Setup view](virtual-machines.md#setup-view)).             |

Responsibilities:

1. At launch, create the local `Engine`, `localWorkspace` on a `LocalEngineConnection` and the local-only services, then start the Updater, in the order of [Startup](architecture.md#startup).
2. `workspace(for: deviceID)` returns the open workspace of a device, or opens one: a `RemoteEngineConnection` to the paired device ([One connection per device](remote.md#one-connection-per-device)) and a new `DeviceWorkspace`.
3. Close a remote workspace and its connection as soon as no main window and no chat window shows its device.
4. Keep `devices` current from the paired devices service and Bonjour discovery ([Online status](remote.md#online-status)).
5. Route `ui.open` events to a window ([Choosing the window](#choosing-the-window)).
6. Ask for the permission to post notifications at launch, post the chat notifications, replace and remove them, and handle their click ([Status bar](#status-bar)).
7. Share the newest plan usage between the open workspaces ([Plan usage sharing](remote.md#plan-usage-sharing)).
8. Run the [quit checks](#unsaved-changes-and-quitting), then the [shutdown](architecture.md#shutdown).
9. Show the detail of a virtual machine for `Show` of Settings ▸ Virtual Machines ([Choosing the window](#choosing-the-window)), and make every main window leave the detail of a virtual machine that left This Mac's list ([Detail](virtual-machines.md#detail)); show the setup view of an image for `Set Up…` of Settings ▸ Virtual Machines and for a click on its preview in the Virtual Machines popover, stop a setup virtual machine for `Stop` of the setup view and of the popover ([Stop](virtual-machines.md#stop)), and, once a setup has ended, make every main window that shows its setup view go back to its section, after the alert of a virtual machine that failed ([Setup view](virtual-machines.md#setup-view)).

Loading:

1. Device-level data (device, projects, skills, settings, Claude status, plan usage) comes from the snapshot: This Mac's workspace subscribes to the events, then calls `snapshot.get` under the [replay rule](remote.md#seeding-calls-and-the-replay-rule); a remote workspace takes the `welcome` snapshot ([Welcome snapshot](remote.md#welcome-snapshot)).
2. The workspace then runs the seeding calls `claude.models`, and `chats.list` followed by `chats.listAgents` for every project, so that the status bar and the quit check count the chats of every project. A project that appears later (`projects.changed`) gets its `chats.list` and `chats.listAgents` calls too. These calls have no failure state: a failed call leaves the data as the events make it.
3. When a main window or a chat window shows a project that is not loaded, the workspace runs the seeding calls `projects.get`, `tickets.list`, `bundles.list` and `webTabs.list` under the replay rule; the project counts as loaded when all four have succeeded; when one fails, the centre column shows the failure state of [Empty states](#empty-states) until Try Again succeeds. A main window that shows a project also has the workspace run these seeding calls for each loaded descendant of the project that is not loaded, at once and whenever a descendant is added or opened, so that the Tickets section lists the descendants' tickets ([Tickets section](tickets.md#tickets-section)). A descendant whose calls fail keeps its tickets out of the list; its own failure state shows when a window activates it or shows its Dashboard ([Section](dashboard.md#section)). Default chosen at design time.
4. Section views load their own data (doc lists, file trees, file contents, memory lists, transcripts with `chats.get`) through the workspace, as their documents specify, with the same rule: while a seeding call is in flight, the events that change its data are recorded; when the result arrives it replaces that data, then the recorded events are applied in arrival order ([Seeding calls and the replay rule](remote.md#seeding-calls-and-the-replay-rule)).
5. Loaded data stays until the project disappears or the workspace closes. Mutation results are never written into the workspace.
6. After a reconnection the workspace follows [After a reconnect](remote.md#after-a-reconnect): device-level data is replaced, every seeding call runs again and window state is kept.

Loading every project's chat metadata and keeping loaded data are design-time choices. Default chosen at design time.

While the setup view shows, `unlinkedItems` may hold the key `imageSetup:<image id>` of its linked item.
- The view state of a project stays in memory while its window is open, so returning to a project restores its selections and its unsaved editors.
- A chat window's state is its `ChatWindowValue {deviceID: String, chatID: String}` (`Codable`, `Hashable`): the window observes the workspace of `deviceID`, opening it when needed, and shows `chatID`; it never changes while the window is open. - `section` is `apiExplorer` only in a project whose sidebar shows the API Explorer row, or while the first read of its contract runs; otherwise the window selects `dashboard` ([Availability](openapi.md#availability)). It is `graph` only in a project whose graph is enabled, or while the project's detail is loading ([Enabling](graph.md#enabling)), and `views` only in a project whose type is `swiftApplication` ([Visibility](views.md#visibility)).
- `WindowSheet` has one case per sheet that a document attaches to a main window, with the values the sheet needs to open: `newProject`, `newProjectInFolder(path)`, `newSubProject(parentID)`, `openProjectFolder`, `newTicket(projectID)`, `ticketPicker(projectID, use)`, whose `use` is `newBundle`, `selection(ticketIDs)` for Create Bundle from Selection or `addTickets(bundleID)` ([Ticket picker sheet](tickets.md#ticket-picker-sheet)), `implementTicket(ticketID)`, `implementBundle(bundleID)`, `addLink(ticketID)`, `addDevice(deviceID?)`, `feedback(previewID)`, `newSkill(projectID)`, `newSkillFile(skillName)`, `newMemory(projectID?)`, without `projectID` for the global memories folder, `newDoc(projectID, folder)`, `renameDoc(projectID, path)`, `newFile(projectID, folder, isFolder)`, `renameFile(projectID, path)`, `newView(projectID, folder)`, the [New View sheet](views.md#new-view-sheet) with the folder it first holds, `webPageDialog(tabID)`, `newVM` and `addImage`, the New VM and Add Image sheets that the [Virtual Machines popover](virtual-machines.md#buttons) opens, and `editVM(vmID)`, the Edit VM sheet that `Edit…` of a Stopped row of the popover opens ([Virtual Machines](#virtual-machines)).
- `WindowState`, `ProjectViewState` and `ChatWindowValue` are `Codable`. They belong to their window: they are never sent to an engine and never synced. `debug_ui_state` encodes them as [WindowState](architecture.md#windowstate) specifies, without buffers: an editor tab encodes its path only, and `docBuffer`, `apiExplorerBuffer`, the skill form and the `memoryEditor` of `projectStates` and of `globalMemoryStates`, and the `skillEditor` of `internalSkillStates`, are left out. The feedback context is built from them ([Feedback context](feedback.md#feedback-context)).
- In JSON, `projectStates` is an array of `{deviceID, projectID, state}` objects sorted by device and project, since JSON object keys are strings; `globalMemoryStates` and `internalSkillStates` are objects whose keys are device ids.
- The persisted `projectStates` holds the active project's entry without buffers and, for every other project the window showed, an entry with only `hidesClosedChats`, so a relaunch restores the filter of the chat lists ([Where chats appear](chats.md#where-chats-appear)) for each of them. The persisted `globalMemoryStates` holds only the entry of the window's device, with its `selectedMemoryFile`, and the persisted `internalSkillStates` only the entry of the window's device, with its `selectedSkillName`.

## Navigation

A `NavigationTarget` ([NavigationTarget](engine-api.md#navigationtarget)) names something to show. Search results, links between docs and tickets, the status bar's chats popover, links and ids clicked in chat views and chat windows (ticket and bundle ids of transcripts and pinned cards included, [Chats](chats.md#links-images-and-files)), ticket and bundle ids clicked in ticket descriptions and comments ([Tickets](tickets.md#ticket-detail)), `ui.open` events (sent when Claude calls `open_in_app`, [open_in_app](mcp.md#open_in_app)), Send in the Feedback sheet ([Feedback sheet](feedback.md#feedback-sheet)), a click on a chat notification ([Status bar](#status-bar)), `Show` of Settings ▸ Virtual Machines ([Virtual Machines](#virtual-machines)), a click on a preview of the Virtual Machines popover ([Previews](virtual-machines.md#previews)) and the debug tool `debug_navigate` all call `WindowState.navigate(to:)` on a main window. It behaves the same on This Mac and on remote devices.

### Resolving a target

| Kind                              | Project                                                                                                                                       | Section   | Selection                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project{projectID}`              | `projectID`; the breadcrumb shows its top-level ancestor and, for a sub project, the project itself                                           | unchanged | none                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `ticket{ticketID}`                | the identifier part of the ticket id (`HEPH` for `HEPH-12`)                                                                                   | `tickets` | `selectedTicketIDs = [ticketID]`; the list filters that hide the ticket are cleared: a ticket whose status is off turns All on, a done ticket turns All and Show Done on, and a text filter it does not match is emptied; while the ticket is not known yet (its project loading), All and Show Done are turned on and the text filter is emptied ([Ticket list](tickets.md#ticket-list))                                                       |
| `bundle{bundleID}`                | the identifier part of the bundle id (`HEPH` for `HEPH-B2`)                                                                                   | `bundles` | `selectedBundleID`; a done bundle turns the list's done filter off (`bundleList.hidesDoneBundles = false`); while the bundle is not known yet (its project loading), the filter is turned off too ([Bundles section](tickets.md#bundles-section))                                                                                                                                                                                               |
| `chat{chatID}`                    | `projectID` of the chat's `ChatMeta`; the active project (else the device's default project) when the workspace has no metadata for the chat  | as listed | the chat, selected where it is listed: in the Chats tab of its ticket or bundle, or in the Chats section (`selectedChatIDs = [chatID]`), as the rules under the table say                                                                                                                                                                                                                                                                       |
| `doc{projectID, path, fragment?}` | `projectID`                                                                                                                                   | `docs`    | `selectedDocPath = path`, in the window's current doc mode; with a non-empty `fragment`, the preview scrolls to that heading anchor once the doc is rendered, also when the doc was already selected ([Opening a doc](documentation-viewer.md#opening-a-doc))                                                                                                                                                                                   |
| `file{projectID, path, line?}`    | `projectID`                                                                                                                                   | `code`    | opens the file in an editor tab or selects its open tab, with the folders above it expanded and the file selected in the file tree; the cursor goes to the start of `line`, which is scrolled to the vertical middle, or to the start of the file without `line`; a folder path is revealed (the folders above it expanded) and selected in the file tree, and the editor tabs stay as they are ([Opening files](code-editor.md#opening-files)) |
| `skill{name}`                     | the active project, unchanged; no project for an [internal skill](skills.md#internal-skills): the window shows it in its Internal Skills view | `skills`  | `selectedSkillName`; for an internal skill, `selectedSkillName` of the device's entry of `internalSkillStates`                                                                                                                                                                                                                                                                                                                                  |
| `webTab{projectID, tabID}`        | `projectID`                                                                                                                                   | `web`     | `selectedWebTabID`                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `section{projectID, section}`     | `projectID`                                                                                                                                   | `section` | none                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `virtualMachine{vmID}`            | none: the active project stays, and the target needs none                                                                                     | unchanged | `shownVirtualMachineID = vmID`: the centre column shows the virtual machine's detail ([Detail](virtual-machines.md#detail))                                                                                                                                                                                                                                                                                                                     |

1. When the window's device is not connected, the target is stored in `pendingTarget` and applied once the workspace is connected.
2. When the window shows a sheet, the target is stored in `pendingTarget` and applied when the sheet closes.
3. The project is resolved as in the table. When it is not a project of the window's device, the window shows the alert `Project <projectID> was not found on <device name>.` and nothing else changes. A `skill` target of a skill that is not internal, in a window without an active project, first activates the device's default project; when the device has no project, the target is ignored. A `skill` target of an internal skill resolves no project, and neither does a `virtualMachine` target.
4. The window activates the project, loading it when needed, and selects the section, which leaves the Global Memories view and the Internal Skills view; a `project` target, which keeps the section, keeps them too ([Global Memories view](memories.md#global-memories-view), [Internal Skills view](skills.md#internal-skills-view)). A `skill` target of an internal skill changes neither the project nor the section: the window shows the Internal Skills view of its device, also without an active project. A `virtualMachine` target changes neither of them either: the window shows the detail of the virtual machine, also without an active project, once the workspace has read the virtual machines with `vms.list` when it does not hold this one. It is ignored, and nothing changes, in a window that shows a remote device, and when the device has no virtual machine with this id. Every target leaves a sub project's Dashboard ([Sidebar](#sidebar)). A `section` target naming `apiExplorer` in a project where the API Explorer row is not shown ends on `dashboard` once the first read of the project's contract has ended ([Availability](openapi.md#availability)). A `builds` section gives way to `dashboard` when the project, once loaded, has no GitHub page ([Visibility](builds.md#visibility)).
5. When applying the selection would replace a doc buffer or a skill form with unsaved changes, that section's or the Internal Skills view's unsaved changes prompt is shown first; Cancel keeps the current selection, and the project and section changes of step 4 stay. The selection is applied. When the item does not exist once the project is loaded, the section's detail area shows `<Kind> <id> was not found.`, with `<Kind>` one of `Ticket`, `Bundle`, `Chat`, `Doc`, `File`, `Skill` or `Web tab` and `<id>` the target's id, path or name, until another item is selected; a missing web tab shows it until that tab appears too ([Selection](web-tabs.md#selection)).
6. A target always refers to the device whose workspace delivered it; navigation changes the window's device only for `debug_navigate`.

A `chat` target shows the chat where it is listed ([Where chats appear](chats.md#where-chats-appear)):

- A ticket chat, or a CI chat linked to a ticket (its `ticket`), while that ticket exists: the `tickets` section, the ticket selected as by a `ticket{ticketID}` target, its Chats tab (`ticketTab = chats`) and the chat selected in it (`chatsTabSelection[ticketID] = chatID`).
- A bundle chat, or a CI chat linked to a bundle (its `bundle`), while that bundle exists: the `bundles` section, the bundle selected as by a `bundle{bundleID}` target, its Chats tab (`bundleTab = chats`) and the chat selected in it (`chatsTabSelection[bundleID] = chatID`).
- Every other chat, a project chat, a feedback chat, a chat whose ticket or bundle no longer exists, or a chat whose metadata the workspace does not hold: the `chats` section, `selectedChatIDs = [chatID]`.
- The Chats tab then shows the chat's view, not a draft, a workflow or an agent ([Ticket chats and Implement](tickets.md#ticket-chats-and-implement)).
- Whether the ticket or the bundle exists is decided once the tickets and bundles of the chat's project are loaded: the navigation waits for them, at most 10 seconds, and a ticket or a bundle still not known then counts as existing, as in the Chats section's list. Default chosen at design time.

Keeping the section for `project` targets, `pendingTarget`, the not-found texts, turning the bundle list's done filter off for a bundle not known yet and ignoring a `virtualMachine` target that cannot be shown are design-time choices. Default chosen at design time.
