# User interface

HephaestusV2's windows are clients of one device's engine. This document specifies the application shell: the windows and their lifecycle; the main window with its toolbar, the `Device ▸ Project ▸ Sub project` breadcrumb selector, the sidebar, the project chat inspector, the console drawer and the status bar; every menu item and keyboard shortcut, in one table; unsaved changes and quitting; the app-level empty states, including the reconnect view; the Settings window; and the UI state model (`AppModel`, one `DeviceWorkspace` per device connection, one `WindowState` per main window) with navigation through `NavigationTarget`. What each sidebar section shows is specified in that section's document; this document only places it.

The scene ids, the window titles and subtitles, the window sizes and the restoration column are design-time values; the chat window's title follows the chat title (Brief §5.3). Default chosen at design time.

- Automatic window tabbing is disabled (`NSWindow.allowsAutomaticWindowTabbing = false`): windows never merge into native tabs, and View ▸ Show Tab Bar does not exist. Default chosen at design time.
- Closing the last window does not quit the app; the engine, its servers, Claude processes and runs keep going. Default chosen at design time.
- At launch, macOS state restoration reopens the previous session's main windows, each with its persisted [WindowState](#windowstate), and its chat windows. When nothing is restored, one main window opens on This Mac with the default project of the [project selector](projects.md#project-selector). A process started with `HEPHAESTUS_DATA_DIR` or `HEPHAESTUS_WINDOW_SCREEN` restores no window and saves no window state ([Environment overrides](architecture.md#environment-overrides)). macOS restores them only when Close windows when quitting an application is off, or after Quit and Keep Windows (⌥⌘Q). A restart for an update keeps the windows in every case: before posting `app.quitting` with `restart` true, `AppModel` writes the persisted `WindowState` of every main window and the `ChatWindowValue` of every chat window, front to back, to the `UserDefaults` key `windowsAtRestart`; at the next launch, when that key exists, the app opens exactly those windows, deletes the key and disables macOS restoration for that launch (`restorationBehavior(.disabled)`). The key holds a JSON array, front to back, of `{"main": <the persisted WindowState as JSON text>}` and `{"chat": {deviceID, chatID}}` objects; a value that cannot be decoded is deleted and counts as absent. When the restart does not happen (the Updater does not answer `installing`), the app deletes the key, so the next launch restores as usual. A process started with `HEPHAESTUS_DATA_DIR` or `HEPHAESTUS_WINDOW_SCREEN` neither writes nor reads the key. Default chosen at design time.
- `HEPHAESTUS_WINDOW_SCREEN` places every window as [Window placement](architecture.md#window-placement) specifies.
- A chat window shows one chat of one device. Opening a chat that already has a window brings that window to front. A chat window closes when its chat is deleted, when its project is removed and when its device is removed from the paired devices. Default chosen at design time.
- Each main window has its own device, active project, section and panel visibility; several windows may show different devices at once.

A main window opens with the sidebar at its default width and the inspector at `inspectorWidth` ([WindowState](#windowstate)), 380 in a new window. Default chosen at design time.

The welcome view and the reconnect view replace the sidebar, the content, the console drawer and the inspector ([Empty states](#empty-states)). The search panel ([Search panel](search.md#search-panel)) and the update-ready banner ([Update-ready banner](updater.md#update-ready-banner)) are drawn over the columns.

## Inspector

The inspector is the project chat panel in the right column ([Where chats appear](chats.md#where-chats-appear)).

- A new main window shows it. The toolbar's Project Chat button and View ▸ Show Project Chat / Hide Project Chat (⌥⌘0) toggle it; its visibility persists per window, and so does the width the user sets by dragging its divider ([Main window layout](#main-window-layout)).
- Header: a pop-up button listing the active project's chats of kind `project`, most recently updated first, each with its title and the state indicator of [Where chats appear](chats.md#where-chats-appear), where the SF Symbol `progress.indicator` stands for the spinner, which cannot animate in a menu; a `New Chat` button (`plus.bubble`); an `Open in New Window` button (`macwindow.badge.plus`), disabled while a draft is shown, that opens the selected chat in a [chat window](#windows).
- Body: the chat view of the selected chat ([Chat view](chats.md#chat-view)).
- The selected chat is kept per project and per window (`ProjectViewState.inspectorChatID`). Without a selection, the most recently updated project chat is selected. When the selected chat is deleted, the next most recently updated project chat is selected. With no project chat, the inspector shows a draft chat ([Draft chats](chats.md#draft-chats)).
- New Chat (the inspector button, the toolbar button, File ▸ New Chat ⌥⌘N) shows the inspector when it is hidden, shows a new draft chat in it (`inspectorShowsDraft`) and puts the keyboard focus in its composer. The draft is stored as a chat only at its first Send ([Draft chats](chats.md#draft-chats)).
- Ticket, bundle and feedback chats are not listed in the inspector; they appear in the Chats section and on their ticket or bundle.

The Open in New Window button, the selection fallback and the focus placement are design-time choices. Default chosen at design time.

## Console drawer

- The console drawer sits at the bottom of the centre column, under the section content; it does not extend under the sidebar or the inspector.
- View ▸ Show Console / Hide Console (⇧⌘Y) toggles it. A click on the status bar's Run item shows it with that run selected, or hides it when it already shows that run. Starting Run, Build or Test from a window shows the drawer in that window.
- Height: default 220 points, minimum 120, at most the centre column's height minus 200. Visibility and height persist per window.
- Its content and controls are specified in [Console](projects.md#console).

The placement, the sizes and the automatic showing are design-time choices. Default chosen at design time.

The Find items are the standard items of SwiftUI's `TextEditingCommands`: they have no target, and AppKit enables each one when the first view of the key window's responder chain that implements its action validates it. Editors and web tabs implement `performFindPanelAction:`; the Docs preview and chat transcripts implement `performTextFinderAction:` only, so the application delegate, at the end of the responder chain, sends Find…, Find Next and Find Previous on to them as `performTextFinderAction:` and validates them through them. Jump to Selection sends `centerSelectionInVisibleArea:`, which every text view and web view implements and enables, so a condition on the selection cannot be applied to it.
2. In the ticket list, Copy copies the selected ticket ids and Select All selects every visible ticket ([Keyboard shortcuts](tickets.md#keyboard-shortcuts)). In the image viewer, Copy copies the image. In a chat transcript, Copy copies plain text and Select All selects the whole transcript; in a chat composer, pasted files and images become attachments ([Keyboard shortcuts](chats.md#keyboard-shortcuts)).
3. Paste and Match Style, which SwiftUI does not provide, follows Select All. Window: Zoom, Fill, Center, Move & Resize, Full Screen Tile, Bring All to Front and the window list, with main windows by title and chat windows by chat title. macOS also handles ⌘\` (cycle through the app's windows) without a menu item.
4. A ticket editor is the New Ticket sheet, the ticket picker sheet, a ticket description editor, the comment composer or a comment editor ([Keyboard shortcuts](tickets.md#keyboard-shortcuts)).

### Shortcut conflict review

- Every menu shortcut appears once in the table.
- A `(none)` key never uses the combination of an enabled menu item. The one exception, ⌘. in a sheet, is resolved by the sheet modality rule of [Principles](#principles): Project ▸ Stop is disabled while a sheet is shown, so ⌘. cancels the sheet.
- Two `(none)` rows that share a key apply to different focused elements: Return (composer, chat title, ticket and bundle title, questions answer field, sheet, Choose Folder sheet, ticket picker filter, search panel, preview find bar, Go to Line popover, address bar, code editor, file tree), ← and → (image viewer, file tree), Escape (composer, chat title, ticket and bundle title, ticket editors, sheet, search panel, preview find bar, Go to Line popover, address bar, new tab placeholder, image viewer), ⌘Return (chat cards, ticket editors, sheet; in the New Ticket and ticket picker sheets both rows press the same default button), ⌫ (bundle tickets, skills list, docs tree, chats list and file tree) and ⌘⌫ (ticket and bundle lists, skills list, docs tree, chats list and file tree). ## Unsaved changes and quitting

An unsaved editor is a code editor tab, the Docs section's doc buffer, a skill form or a skill extra file whose content differs from what was last loaded or saved. Unsaved editors belong to their window, not to the engine.

| Moment                                                                                                                                             | Alert title / message                                                                                                                                                                                               | Buttons                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Closing a code editor tab or leaving a doc with unsaved changes ([Saving and changes on disk](documentation-viewer.md#saving-and-changes-on-disk)) | `Do you want to save the changes you made to “<file name>”?` / `Your changes will be lost if you don't save them.`                                                                                                  | `Save` (default), `Don't Save`, `Cancel`     |
| Leaving a skill with unsaved changes                                                                                                               | the prompt of [Saving](skills.md#saving)                                                                                                                                                                            | the prompt's buttons                         |
| Closing a main window with 1 unsaved editor                                                                                                        | that editor's prompt above                                                                                                                                                                                          | that prompt's buttons                        |
| Closing a main window with n > 1 unsaved editors                                                                                                   | `You have unsaved changes in <n> editors.` / `Your changes will be lost if you don't save them.`                                                                                                                    | `Save All` (default), `Don't Save`, `Cancel` |
| Removing a project ([Removing a project](projects.md#removing-a-project))                                                                          | as for closing a window, counting the unsaved editors of that project and its sub projects in every window of this app                                                                                              | as for closing a window                      |
| Quitting with unsaved editors                                                                                                                      | as for closing a window, counting the unsaved editors of every window                                                                                                                                               | as for closing a window                      |
| Quitting while This Mac's engine has chats in state `starting`, `running` or `waitingPermission`, or running runs                                  | `Quit HephaestusV2?` / `<chats> and <runs> on This Mac will be stopped.`, where `<chats>` is `1 chat` or `<n> chats` and `<runs>` is `1 run` or `<n> runs`; a part whose count is 0 is left out together with `and` | `Quit` (default), `Cancel`                   |

- Quitting checks unsaved editors first, then running work. Cancel at either step cancels the quit. A restart for an update runs the same checks with its own running-work alert ([Restart rules](updater.md#restart-rules)).
- `AppModel` counts This Mac's chats from the local workspace, which holds the metadata of every chat ([DeviceWorkspace](#deviceworkspace)), and its runs from the local workspace's runs.
- When a save fails (for example on a conflict), the close, the removal or the quit is cancelled and the editor shows the failure.
- A chat in state `waitingAnswers` is not counted: its questions are stored and can be answered after the next launch.
- Ticket description edits are saved when the window closes, and when the app quits or restarts: after the checks, the app calls `tickets.update` for each changed description editor and waits for the answers, at most 5 seconds; a failure cancels the quit and shows the error ([Ticket detail](tickets.md#ticket-detail)). Comment and composer drafts are discarded.
- After confirmation the app shuts down as [Shutdown](architecture.md#shutdown) specifies. Chats and runs of remote devices are not affected: they run on their own device.

The texts, the check order and the counted states are design-time choices. Default chosen at design time.

## UI state model

The UI state lives in `@MainActor @Observable` objects of the HephaestusUI module; their place in the architecture is in [UI state architecture](architecture.md#ui-state-architecture). Views read them and call their methods; a view keeps only presentation state of its own (scroll position, hover, focus, the composer text of a draft chat).

```
AppModel                       one per app
├── DeviceWorkspace            one per open device connection (This Mac's is always open)
│   └── EngineConnection       LocalEngineConnection or RemoteEngineConnection
├── WindowState                one per main window, refers to a DeviceWorkspace by deviceID
└── ChatWindowValue            one per chat window, refers to a DeviceWorkspace by deviceID
```

### AppModel

| Property                | Type                        | Meaning                                                                                                                                                 |
| ----------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `localDeviceID`         | `String`                    | This Mac's device id (`device.yml`).                                                                                                                    |
| `localWorkspace`        | `DeviceWorkspace`           | The workspace of the in-process engine; created at launch, never closed.                                                                                |
| `workspaces`            | `[String: DeviceWorkspace]` | Open workspaces by device id, This Mac's included.                                                                                                      |
| `devices`               | `[DeviceEntry]`             | This Mac first, then the paired devices in the order of [Paired devices](remote.md#paired-devices). `DeviceEntry {id, name, isLocal, online}`.          |
| `windows`               | `[UUID: WindowState]`       | The state of every open main window, by window id.                                                                                                      |
| `keyWindowOrder`        | `[UUID]`                    | Main window ids, most recently key first.                                                                                                               |
| `chatWindows`           | `Set<ChatWindowValue>`      | The open chat windows.                                                                                                                                  |
| `lastProjectIDByDevice` | `[String: String]`          | Last active project per device, persisted ([Persistence](#persistence)).                                                                                |
| `updaterStatus`         | `UpdaterStatus`             | The last status received from the Updater; `idle` without version, build or message before the first one ([Updater states](updater.md#updater-states)). |

Responsibilities:

1. At launch, create the local `Engine`, `localWorkspace` on a `LocalEngineConnection` and the local-only services, then start the Updater, in the order of [Startup](architecture.md#startup).
2. `workspace(for: deviceID)` returns the open workspace of a device, or opens one: a `RemoteEngineConnection` to the paired device ([One connection per device](remote.md#one-connection-per-device)) and a new `DeviceWorkspace`.
3. Close a remote workspace and its connection as soon as no main window and no chat window shows its device.
4. Keep `devices` current from the paired devices service and Bonjour discovery ([Online status](remote.md#online-status)).
5. Route `ui.open` events to a window ([Choosing the window](#choosing-the-window)).
6. Run the [quit checks](#unsaved-changes-and-quitting), then the [shutdown](architecture.md#shutdown).

Device-level data (device, projects, skills, settings, runs, Claude status) comes from the snapshot: This Mac's workspace subscribes to the events, then calls `snapshot.get` under the [replay rule](remote.md#seeding-calls-and-the-replay-rule); a remote workspace takes the `welcome` snapshot ([Welcome snapshot](remote.md#welcome-snapshot)).
2. The workspace then runs the seeding calls `claude.models` and `chats.list` for every project, so that the status bar and the quit check count the chats of every project. A project that appears later (`projects.changed`) gets its `chats.list` call too. These calls have no failure state: a failed call leaves the data as the events make it.
3. When a main window or a chat window shows a project that is not loaded, the workspace runs the seeding calls `projects.get`, `tickets.list`, `bundles.list` and `webTabs.list` under the replay rule; the project counts as loaded when all four have succeeded; when one fails, the centre column shows the failure state of [Empty states](#empty-states) until Try Again succeeds.
4. Section views load their own data (doc lists, file trees, file contents, transcripts with `chats.get`) through the workspace, as their documents specify, with the same rule: while a seeding call is in flight, the events that change its data are recorded; when the result arrives it replaces that data, then the recorded events are applied in arrival order ([Seeding calls and the replay rule](remote.md#seeding-calls-and-the-replay-rule)).
5. Loaded data stays until the project disappears or the workspace closes. Mutation results are never written into the workspace.
6. After a reconnection the workspace follows [After a reconnect](remote.md#after-a-reconnect): device-level data is replaced, every seeding call runs again and window state is kept. A run that the workspace knew as running and that is absent from the new snapshot is marked as ended while disconnected ([Console](projects.md#console)).

Loading every project's chat metadata and keeping loaded data are design-time choices. Default chosen at design time.

- A chat window's state is its `ChatWindowValue {deviceID: String, chatID: String}` (`Codable`, `Hashable`): the window observes the workspace of `deviceID`, opening it when needed, and shows `chatID`; it never changes while the window is open.
- `WindowSheet` has one case per sheet that a document attaches to a main window, with the values the sheet needs to open: `newProject`, `newProjectInFolder(path)`, `newSubProject(parentID)`, `openProjectFolder`, `projectSettings(projectID)`, `newTicket(projectID)`, `ticketPicker(projectID, bundleID?, checkedTicketIDs)`, `addDevice(deviceID?)`, `feedback(previewID)`, `newSkill(projectID)`, `newSkillFile(skillName)`, `newDoc(projectID, folder)`, `renameDoc(projectID, path)`, `newFile(projectID, folder, isFolder)`, `renameFile(projectID, path)` and `webPageDialog(tabID)`.
- `WindowState`, `ProjectViewState` and `ChatWindowValue` are `Codable`. They belong to their window: they are never sent to an engine and never synced. `debug_ui_state` encodes them as [WindowState](architecture.md#windowstate) specifies, without buffers: an editor tab encodes its path only, and `docBuffer` and the skill form are left out. The feedback context is built from them ([Feedback context](feedback.md#feedback-context)).
- In JSON, `projectStates` is an array of `{deviceID, projectID, state}` objects sorted by device and project, since JSON object keys are strings.

### Persistence

| What                                                                 | Where                                                             | Key                     |
| -------------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------- |
| The persisted properties of a main window's `WindowState`            | the window's `@SceneStorage`, JSON-encoded                        | `windowState`           |
| Chat windows                                                         | SwiftUI restoration of the `chat` scene's `ChatWindowValue`       | —                       |

Everything else comes from the engine. A process started with `HEPHAESTUS_DATA_DIR` or `HEPHAESTUS_WINDOW_SCREEN` neither reads nor writes this state ([Environment overrides](architecture.md#environment-overrides)). The storage keys are design-time names. Default chosen at design time.

## Navigation

A `NavigationTarget` ([NavigationTarget](engine-api.md#navigationtarget)) names something to show. Search results, links between docs and tickets, the status bar's chats popover, links and ids clicked in chat windows, `ui.open` events (sent when Claude calls `open_in_app`, [open_in_app](mcp.md#open_in_app)) and the debug tool `debug_navigate` all call `WindowState.navigate(to:)` on a main window. It behaves the same on This Mac and on remote devices.

### Resolving a target

| Kind                           | Project                                                                                                                                      | Section   | Selection                                                                                                                                                                                                                                      |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project{projectID}`           | `projectID`; the breadcrumb shows its top-level ancestor and, for a sub project, the project itself                                          | unchanged | none                                                                                                                                                                                                                                           |
| `ticket{ticketID}`             | the identifier part of the ticket id (`HEPH` for `HEPH-12`)                                                                                  | `tickets` | `selectedTicketIDs = [ticketID]`; list filters that hide the ticket are cleared, both of them while the ticket is not known yet (its project loading) ([Tickets](tickets.md))                                                                  |
| `bundle{bundleID}`             | the identifier part of the bundle id (`HEPH` for `HEPH-B2`)                                                                                  | `bundles` | `selectedBundleID`                                                                                                                                                                                                                             |
| `chat{chatID}`                 | `projectID` of the chat's `ChatMeta`; the active project (else the device's default project) when the workspace has no metadata for the chat | `chats`   | `selectedChatID`                                                                                                                                                                                                                               |
| `doc{projectID, path}`         | `projectID`                                                                                                                                  | `docs`    | `selectedDocPath = path`, in the window's current doc mode                                                                                                                                                                                     |
| `file{projectID, path, line?}` | `projectID`                                                                                                                                  | `code`    | opens the file in an editor tab or selects its open tab; the cursor goes to the start of `line`, which is scrolled to the vertical middle, or to the start of the file without `line`; a folder path is revealed and selected in the file tree |
| `skill{name}`                  | the active project, unchanged                                                                                                                | `skills`  | `selectedSkillName`                                                                                                                                                                                                                            |
| `webTab{projectID, tabID}`     | `projectID`                                                                                                                                  | `web`     | `selectedWebTabID`                                                                                                                                                                                                                             |
| `section{projectID, section}`  | `projectID`                                                                                                                                  | `section` | none                                                                                                                                                                                                                                           |

1. When the window's device is not connected, the target is stored in `pendingTarget` and applied once the workspace is connected.
2. When the window shows a sheet, the target is stored in `pendingTarget` and applied when the sheet closes.
3. The project is resolved as in the table. When it is not a project of the window's device, the window shows the alert `Project <projectID> was not found on <device name>.` and nothing else changes. A `skill` target in a window without an active project first activates the device's default project; when the device has no project, the target is ignored.
4. The window activates the project, loading it when needed, and selects the section.
5. When applying the selection would replace a doc buffer or a skill form with unsaved changes, that section's unsaved changes prompt is shown first; Cancel keeps the current selection, and the project and section changes of step 4 stay. The selection is applied. When the item does not exist once the project is loaded, the section's detail area shows `<Kind> <id> was not found.`, with `<Kind>` one of `Ticket`, `Bundle`, `Chat`, `Doc`, `File`, `Skill` or `Web tab` and `<id>` the target's id, path or name, until another item is selected; a missing web tab shows it until that tab appears too ([Selection](web-tabs.md#selection)).
6. A target always refers to the device whose workspace delivered it; navigation changes the window's device only for `debug_navigate`.

Keeping the section for `project` targets, `pendingTarget` and the not-found texts are design-time choices. Default chosen at design time.

### Choosing the window

| Source                                                                          | Window that navigates                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ui.open` event                                                                 | Handled only when its `deviceID` is absent or equals `localDeviceID` (Brief §4.2). The key window when it is a main window showing the workspace's device; otherwise the most recently key main window showing that device; otherwise a new main window opened on that device. |
| Search result                                                                   | The window whose search panel shows it ([Navigation](search.md#navigation)).                                                                                                                                                                                                   |
| Status bar chats popover                                                        | The window of the status bar.                                                                                                                                                                                                                                                  |
| Chat window: a link of its transcript, or the ticket or bundle id of its header | The most recently key main window showing the chat's device, ordered front and made key; otherwise a new main window opened on that device. The chat window stays open.                                                                                                        |
| `debug_navigate`                                                                | The frontmost main window, switched to This Mac first when it shows another device; a new main window on This Mac when no main window is open ([debug_navigate](mcp.md#debug_navigate)).                                                                                       |

A window chosen for a `ui.open` event is ordered front; it becomes key only when HephaestusV2 is already the active app, so a navigation requested by Claude never activates the app. Default chosen at design time.

## Requirements covered

- R5: A selector at the top of the window, like Xcode's, chooses { Main Device } > { project } > { sub project }.
- R6: Its first level chooses the Main Device: this Mac or another Mac, whose projects the window then shows.
- R7: Its next levels choose the project and, when the project has sub projects, the sub project.
- R33: Each project can have Claude chats.
- R56: A feedback feature is reached by tapping a ladybug icon at the bottom right of the status bar.
- R57: Feedback can be started from pretty much anywhere in the app.
- R64: The chat window takes that name.
