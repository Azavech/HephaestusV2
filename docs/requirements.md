# Requirements

This file reproduces the request HephaestusV2 is built from, byte for byte, splits it into numbered requirements and links each one to the doc sections that specify it. [Interpretations](#interpretations) records how the ambiguous and fragmentary parts of the request are read, and [Gaps](#gaps) lists the requirements the docs do not fully specify. A new requirement of the user is added here and to the `Requirements covered` section of each doc that fulfils it ([README.md › Conventions](README.md#conventions)).

The app has a feedback feature (accessible by tapping a ladybug icon on the bottom right of the status bar) that I can start pretty much anywhere in the app, a screenshot will be made and I can send a comment. then it will pop up a claude discussion that will create a ticket. 

when claude creates a ticket it should use a small haiku model to name the ticket.

 the doc accordingly and upon the doc being commited and pushed it will be regenerated then pushed and then github CI will rebuild it and the app will restart itself updated)

Implementing Tickets by claude starts by changing the doc, then updates the code to match the doc then commits ([fix, feat, etc…]: “”) and push

A: question A

All questions should be answered one by one by the user. Claude should always gives multiple way to answer including a recommended answer but the user can answer however he wants.

## Interpretations

- **R3**, "do not read or take inspiration from v1, go blind": an instruction about how the specification and the code are written. It describes no behaviour of the app; [development.md › Docs first](development.md#docs-first) states it as a contribution rule.
- **R4**, "coordinate work between all projects": every project registered on a Mac, with its sub projects, is in that Mac's app: the selector lists them, search covers them all, and Claude's MCP tools reach every project of the device. The Tickets section shows the tickets of one project, and a bundle holds the tickets of one project. Specified in [projects.md › Registry and project tree](projects.md#registry-and-project-tree), [search.md › Project filter](search.md#project-filter), [mcp.md › Actor rules](mcp.md#actor-rules), [tickets.md › Bundle rules](tickets.md#bundle-rules).
- **R5 to R7**, "top ui to select (like xcode does) { Main Device } > { project } > { sub project (if applicable) }": the principal toolbar item, a breadcrumb of up to three menu buttons like Xcode's scheme and destination control. The Main Device is the Mac whose engine the window shows: This Mac, or a paired Mac on the network; each window chooses its own. The sub project segment appears only when the project has sub projects. Specified in [ui.md › Breadcrumb selector](ui.md#breadcrumb-selector), [remote.md › Terms](remote.md#terms), [projects.md › Project selector](projects.md#project-selector).
- **R15**, "Generally inside the code folder/docs": the docs folder is the project's `docsPath`, `docs` by default, changed in Project Settings. Specified in [documentation-viewer.md › Docs folder](documentation-viewer.md#docs-folder), [projects.md › Project settings](projects.md#project-settings).
- **R19**, "set by the user upon creation": the user types the identifier in the New Project or New Sub Project sheet, which suggests one from the name, and it never changes. When Claude creates a project, the description of `create_project` tells it to ask the user for the name and the identifier unless the user gave them. Specified in [projects.md › Identifier rules](projects.md#identifier-rules), [projects.md › Creating a project](projects.md#creating-a-project), [mcp.md › create_project](mcp.md#create_project).
- **R27 to R30**, "a claude tab": a Claude chat of the ticket's Chats tab, shown under the tab's chat list or in its own window; "debugging etc..." covers any other work on the ticket. Specified in [tickets.md › Ticket chats and Implement](tickets.md#ticket-chats-and-implement), [chats.md › Prompt: ticket](chats.md#prompt-ticket).
- **R32**, "implement all ticket at once through a chat section": Implement All starts one bundle chat, which orchestrates the tickets: it starts at once a ticket chat for every ticket that waits for no other ticket of the bundle, each on its own branch with a commit and a completion comment, merges the branches into the main branch and pushes once at the end (R111). Specified in [tickets.md › Implement All](tickets.md#implement-all), [workflow.md › Bundles](workflow.md#bundles).
- **R35**, "make him work on the app": Claude works on the project's code and docs. Its process runs in the project root with the Claude CLI's own tools, under the chat's permission mode. Specified in [chats.md › Prompt: project](chats.md#prompt-project), [chats.md › Launch](chats.md#launch), [chats.md › Permission mode](chats.md#permission-mode).
- **R36 and R39**, "run projects", "run them": running a project runs its build, run or test command (`run_project`). Running a ticket implements it: `implement_ticket` starts a ticket chat that implements the ticket, and `implement_bundle` does the same for a bundle. Specified in [projects.md › Run commands](projects.md#run-commands), [mcp.md › implement_ticket](mcp.md#implement_ticket), [mcp.md › implement_bundle](mcp.md#implement_bundle).
- **R40**, "do anything I want": Claude reads and renames chats, and every change the user makes to a project's tickets, comments, bundles, web tabs, skills and project settings has an MCP tool, except chat settings, project chat defaults and host settings, which would let Claude raise its own permission mode; unlocking a web tab; removing the project of the calling chat; deleting a chat; registering an existing folder as a project; adding files to a ticket outside `create_ticket` and `add_comment`; and starting or messaging chats other than with `implement_ticket` and `implement_bundle`. Default chosen at design time. Files, docs and skill files change through Claude's own file tools. Specified in [mcp.md › Tool catalogue](mcp.md#tool-catalogue), [engine-api.md › Rules for Claude](engine-api.md#rules-for-claude).
- **R43 and R44**, "any remote", "as if the remote is the one working": a remote is another Mac running HephaestusV2 that was paired with the main device's pairing code. Its windows call the main device's engine through the same API as local windows, with the same rights, and receive every event as it is emitted. What belongs to the Mac in front of the user stays there: web pages load in its own web views, feedback screenshots are taken there, and its Settings window edits that Mac. Specified in [architecture.md › One API for every client](architecture.md#one-api-for-every-client), [remote.md › Pairing](remote.md#pairing), [remote.md › Remote windows](remote.md#remote-windows).
- **R45**, "search pretty much anything": eight scopes: projects, tickets with their comments and attachment names, bundles, docs, code, chats, skills and web tabs. Specified in [search.md › Scopes](search.md#scopes), [search.md › Sources](search.md#sources).
- **R47 and R49**, "can be used inside projects", "in their own folders": each skill is a folder of the app's skills library, `<data dir>/Skills` by default. A project enables library skills, and its chats get them through a generated plugin passed to the CLI with `--plugin-dir`. Specified in [skills.md › Library](skills.md#library), [skills.md › Per-project enablement](skills.md#per-project-enablement), [skills.md › Generated plugin](skills.md#generated-plugin).
- **R51**, "MCP commands": the tools of the MCP server that each engine runs; each tool calls one engine method. Specified in [mcp.md › Overview](mcp.md#overview), [mcp.md › Tool catalogue](mcp.md#tool-catalogue).
- **R54 and R55**, "this prompt will be making a documentation pushed in the docs folder (the app must be built against the doc)": this request is turned into the specification in the repository's `docs/` folder; the code is generated from it, and tests and CI check the two against each other. Specified in [README.md › Docs first](README.md#docs-first), [ci.md › Docs conformance tests](ci.md#docs-conformance-tests).
- **R58 and R60**, "a screenshot will be made", "pop up a claude discussion": the screenshot is a picture of the window the feedback starts from, rendered inside the app. The discussion is the feedback chat, with the comment, the screenshot and the context already sent; it pops up in a main window, which comes to the front with the chat selected in the Chats section of its project. Specified in [feedback.md › Screenshot capture](feedback.md#screenshot-capture), [feedback.md › Feedback sheet](feedback.md#feedback-sheet), [feedback.md › Creating the feedback chat](feedback.md#creating-the-feedback-chat), [ui.md › Choosing the window](ui.md#choosing-the-window).
