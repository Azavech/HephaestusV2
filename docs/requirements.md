# Requirements

This file reproduces the request HephaestusV2 is built from, byte for byte, splits it into numbered requirements and links each one to the doc sections that specify it. [Interpretations](#interpretations) records how the ambiguous and fragmentary parts of the request are read, and [Gaps](#gaps) lists the requirements the docs do not fully specify. A new requirement of the user is added here and to the `Requirements covered` section of each doc that fulfils it ([README.md › Conventions](README.md#conventions)).

## Original request

This is an app to coordinate work between all projects .

The app has a feedback feature (accessible by tapping a ladybug icon on the bottom right of the status bar) that I can start pretty much anywhere in the app, a screenshot will be made and I can send a comment. then it will pop up a claude discussion that will create a ticket. 

when claude creates a ticket it should use a small haiku model to name the ticket.

 the doc accordingly and upon the doc being commited and pushed it will be regenerated then pushed and then github CI will rebuild it and the app will restart itself updated)

Implementing Tickets by claude starts by changing the doc, then updates the code to match the doc then commits ([fix, feat, etc…]: “”) and push

When working on a ticket, claide should never invent anything it should ask for things unknown using labelled questions ex:
A: question A 
B: question B 
Etc…

All questions should be answered one by one by the user. Claude should always gives multiple way to answer including a recommended answer but the user can answer however he wants. 

When claude creates a task it should set it’s description as:

Problem

Current Behavior
(Explain the current behaviour)


Expected
(Explain the behaviour that should be expected)

Change
(Explain what should change)

Docs
(List all docs files and paragraphs relevant to the issue)

## Interpretations

- **R3**, "do not read or take inspiration from v1, go blind": an instruction about how the specification and the code are written. It describes no behaviour of the app; [development.md › Docs first](development.md#docs-first) states it as a contribution rule.
- **R4**, "coordinate work between all projects": every project registered on a Mac, with its sub projects, is in that Mac's app: the selector lists them, search covers them all, and Claude's MCP tools reach every project of the device. The Tickets section of a project lists its own tickets and those of all its loaded descendants, and a bundle holds the tickets of one project. Specified in [projects.md › Registry and project tree](projects.md#registry-and-project-tree), [search.md › Project filter](search.md#project-filter), [mcp.md › Actor rules](mcp.md#actor-rules), [tickets.md › Tickets section](tickets.md#tickets-section), [tickets.md › Bundle rules](tickets.md#bundle-rules).
- **R5 to R7**, "top ui to select (like xcode does) { Main Device } > { project } > { sub project (if applicable) }": the principal toolbar item, a breadcrumb of up to three menu buttons like Xcode's scheme and destination control. The Main Device is the Mac whose engine the window shows: This Mac, or a paired Mac on the network; each window chooses its own. The sub project segment appears only when the project has sub projects. Specified in [ui.md › Breadcrumb selector](ui.md#breadcrumb-selector), [remote.md › Terms](remote.md#terms), [projects.md › Project selector](projects.md#project-selector).

- **R19**, "set by the user upon creation": the user types the identifier in the New Project or New Sub Project sheet, which suggests one from the name, and it never changes. Specified in [projects.md › Identifier rules](projects.md#identifier-rules), [projects.md › Creating a project](projects.md#creating-a-project), [mcp.md › create_project](mcp.md#create_project).

- **R32**, "implement all ticket at once through a chat section": Implement All starts one bundle chat, which orchestrates the tickets: it starts at once a ticket chat for every ticket that waits for no other ticket of the bundle, each on its own branch with a commit and a completion comment, merges the branches into the main branch and pushes once at the end (R111). Specified in [tickets.md › Implement All](tickets.md#implement-all), [workflow.md › Bundles](workflow.md#bundles).
- **R35**, "make him work on the app": Claude works on the project's code and docs. Its process runs in the project root with the Claude CLI's own tools, under the chat's permission mode. Specified in [skills.md › Default: project](skills.md#default-project), [chats.md › Launch](chats.md#launch), [chats.md › Permission mode](chats.md#permission-mode).
- **R36 and R39**, "run projects", "run them": "run projects" meant running a project's build, run or test command, which the user withdrew, so R36 covers creating and updating projects; "run them" (R39) means running a ticket, which implements it: `implement_ticket` starts a ticket chat that implements the ticket, and `implement_bundle` does the same for a bundle. Specified in [mcp.md › implement_ticket](mcp.md#implement_ticket), [mcp.md › implement_bundle](mcp.md#implement_bundle).
- **R40**, "do anything I want": Claude reads and renames chats, and every change the user makes to a project's tickets, comments, bundles, web tabs, skills and project settings has an MCP tool, except chat settings, project chat defaults and host settings, which would let Claude raise its own permission mode; a project's GitHub page and `Use parent settings`, which only the user changes; unlocking a web tab; removing the project of the calling chat; deleting a chat; registering an existing folder as a project; adding files to a ticket outside `create_ticket` and `add_comment`; and starting or messaging chats other than with `implement_ticket` and `implement_bundle`. Default chosen at design time. The user added one more exception: the environments of a Go service project, which only Project Settings changes. Files, docs and skill files change through Claude's own file tools. Specified in [mcp.md › Tool catalogue](mcp.md#tool-catalogue), [engine-api.md › Rules for Claude](engine-api.md#rules-for-claude).
- **R43 and R44**, "any remote", "as if the remote is the one working": a remote is another Mac running HephaestusV2 that was paired with the main device's pairing code. Its windows call the main device's engine through the same API as local windows, with the same rights, and receive every event as it is emitted. What belongs to the Mac in front of the user stays there: web pages load in its own web views, feedback screenshots are taken there, and its Settings window edits that Mac. Specified in [architecture.md › One API for every client](architecture.md#one-api-for-every-client), [remote.md › Pairing](remote.md#pairing), [remote.md › Remote windows](remote.md#remote-windows).
- **R45**, "search pretty much anything": eight scopes: projects, tickets with their comments and attachment names, bundles, docs, code, chats, skills and web tabs. Specified in [search.md › Scopes](search.md#scopes), [search.md › Sources](search.md#sources).

Specified in [feedback.md › Screenshot capture](feedback.md#screenshot-capture), [feedback.md › Feedback sheet](feedback.md#feedback-sheet), [feedback.md › Creating the feedback chat](feedback.md#creating-the-feedback-chat), [ui.md › Choosing the window](ui.md#choosing-the-window).

Specified in [updater.md › About window](updater.md#about-window), [updater.md › IPC](updater.md#ipc), [updater.md › Versions and display](updater.md#versions-and-display).

After feedback or a ticket, Claude updates the docs accordingly, regenerates the code from them, commits both together and pushes to `main`; GitHub CI builds a release; the Updater installs it and the app restarts on the new version. Specified in [workflow.md › Self-update loop](workflow.md#self-update-loop), [workflow.md › Implementation workflow](workflow.md#implementation-workflow), [updater.md › Restart for an update](updater.md#restart-for-an-update).
