# Chats

HephaestusV2 talks to Claude through the Claude CLI. Every chat is one Claude Code session, run on the main device by a long-lived `claude -p` process that the engine drives with stream-json over stdin and stdout; Claude reaches the app through the `hephaestus` MCP server. This document specifies the chat kinds and states, how the engine finds and launches the CLI with its exact flags, the control protocol, the mapping of every stream-json message to transcript items and events, permission prompts, the questions protocol as the user sees it, chat settings (model, ultracode, effort, permissions), the chat view and its composer, Haiku naming, persistence, and the full text of every prompt resource. File formats are in [Data model](data-model.md), the method contract in [Engine API](engine-api.md#chats), the MCP tools in [MCP](mcp.md), and the rules Claude follows in [Claude workflow](workflow.md).

## Overview

| Kind     | Started by                                                                         | Linked to                                                                                              | System prompt     | First user message                                              |
| -------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ----------------- | --------------------------------------------------------------- |
| project  | New Chat (⌥⌘N, the inspector, the Chats section)                                   | nothing                                                                                                | common + project  | typed by the user                                               |
| ticket   | New Chat or Implement in a ticket's Chats tab; the MCP tool `implement_ticket`     | the ticket (`ticket`), and its orchestrator bundle chat (`orchestrator`) when a bundle chat started it | common + ticket   | typed by the user, implement-ticket, or implement-bundle-ticket |
| bundle   | New Chat or Implement All in a bundle's Chats tab; the MCP tool `implement_bundle` | the bundle (`bundle`)                                                                                  | common + bundle   | typed by the user, or implement-bundle                          |
| feedback | Send in the Feedback sheet ([Feedback](feedback.md))                               | the first ticket Claude creates (`ticket`)                                                             | common + feedback | the feedback message                                            |

- A chat belongs to one project. Its files live in that project's `.hephaestus/chats/` folder, and its Claude process runs on the main device with the project root as working directory ([Architecture](architecture.md)).
- The chat id is an uppercase UUID generated by the engine when the chat is created. It is also the Claude session id: the engine passes it unchanged to `--session-id` and `--resume`.
- A chat is titled `New Chat` until Haiku names it ([Haiku naming](#haiku-naming)).
- Every client (local window or remote device) sees every chat live: all changes travel as the events `chat.updated`, `chat.item`, `chat.delta` and `chat.deleted` ([Engine API](engine-api.md)).

## Chat states

`ChatMeta.state` is computed by the engine and is not persisted. The status line texts below: Default chosen at design time. After an engine start, a chat whose transcript holds a question set that is not completed is waitingAnswers, and every other chat is idle; the engine finds these sets by replaying each transcript once at launch ([Data model](data-model.md#loading)).

| State             | Meaning                                                                                                          | Status line above the composer     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| idle              | No turn in progress, no pending permission request, no incomplete question set. The process may be alive or not. | hidden                             |
| starting          | A process was launched and its `system/init` message has not arrived yet.                                        | Starting Claude…                   |
| running           | A turn is in progress.                                                                                           | Claude is working… m:ss            |
| waitingPermission | At least one permission request waits for an answer.                                                             | Waiting for your permission        |
| waitingAnswers    | No turn in progress and the chat has a question set that is not completed.                                       | Waiting for your answers           |
| error             | The process failed to start, or exited with a non-zero status during a turn. The next message clears it.         | Claude stopped with an error (red) |

- A turn is the time Claude spends on the messages the engine wrote to the process. It starts when the engine writes a user message while the chat has no turn in progress, or when a `system/init` arrives while none is in progress (a CLI turn the CLI starts on its own). It ends when no message the engine wrote is outstanding and no CLI turn is open ([Turn tracking](#turn-tracking)); a turn can thus span several CLI turns.
- When several states apply, the chat takes the first one of this order: error, waitingPermission, starting, running, waitingAnswers, idle.
- A chat is running while its state is starting, running or waitingPermission; the quit confirmation ([UI](ui.md#unsaved-changes-and-quitting)) and the idle check before an automatic update ([Updater](updater.md#restart-rules)) use this definition. The status bar counts starting and running chats as running, and waitingPermission and waitingAnswers chats as waiting ([UI](ui.md#status-bar)).
- `m:ss` counts the time since this client saw the state become running.
- Every state change emits `chat.updated`.

| From                                 | Event                                                                                   | To                      |
| ------------------------------------ | --------------------------------------------------------------------------------------- | ----------------------- |
| idle, waitingAnswers, error          | a message is delivered and the chat has no live process                                 | starting                |
| idle, waitingAnswers                 | a message is delivered to the live process                                              | running                 |
| starting                             | `system/init` arrives                                                                   | running                 |
| starting                             | no `system/init` within 60 s, or the process cannot be spawned                          | error                   |
| running                              | `control_request` `can_use_tool` arrives                                                | waitingPermission       |
| waitingPermission                    | the last pending permission request is answered or cancelled                            | running                 |
| idle, waitingAnswers                 | `system/init` arrives from the live process                                             | running                 |
| running, waitingPermission           | the turn ends ([Turn tracking](#turn-tracking))                                         | idle, or waitingAnswers |
| starting, running, waitingPermission | the process exits with a non-zero status, not after Stop or a termination by the engine | error                   |
| starting, running, waitingPermission | the process exits after Stop or a termination by the engine, or with status 0           | idle, or waitingAnswers |

`chats.send` accepts a message in every state ([Engine API](engine-api.md#chatssend)). During a turn the message is written to the process at once; the CLI keeps it in its queue until its CLI turn in progress ends, then runs it, together with the other messages waiting there, as a CLI turn of its own, and the chat stays running until that CLI turn ends ([Turn tracking](#turn-tracking)). A message sent while a question set waits leaves the set unchanged.

## Claude CLI

### Locating the CLI

The engine uses the first candidate that applies:

| Order | Candidate                                                                  | Applies when                                                         |
| ----- | -------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1     | setting `claudePath`                                                       | it is set                                                            |
| 2     | environment variable `HEPHAESTUS_CLAUDE_PATH`                              | it is set                                                            |
| 3     | `~/.local/bin/claude`, `/opt/homebrew/bin/claude`, `/usr/local/bin/claude` | one of them is an executable file; the first such file in this order |
| 4     | output of `/bin/zsh -lic 'command -v claude'`                              | its last non-empty line is the absolute path of an executable file   |

When candidate 1 or 2 is set but is not an executable file, the CLI is unavailable and the later candidates are not tried. Candidate 4 runs with a timeout of 30 s; a run that times out does not apply. Default chosen at design time.

### Environment

After the engine starts, it runs `/bin/zsh -lic 'env -0'` once, with a timeout of 10 s, and splits the output on NUL characters; every part of the form `NAME=VALUE` becomes a variable and other parts are skipped. When the command fails or times out, or when its output holds no variable, the engine uses its own process environment, so that no child starts without `PATH`. Every Claude process the engine starts (chat processes and naming calls) gets this environment without any `HEPHAESTUS_*` variable, plus `MCP_TOOL_TIMEOUT=1800000`. Process groups and signals follow [Architecture](architecture.md#child-processes).

### Version and status

The engine computes `ClaudeStatus` {available, checking, path?, version?, error?} after the environment capture at engine start, whenever the setting `claudePath` changes, and on every `claude.status` call ([Engine API](engine-api.md#claudestatus)): it locates the CLI, runs `<path> --version` with a timeout of 30 s, and takes as version the first match of `[0-9]+(\.[0-9]+)+` in its standard output. The timeouts of candidate 4 and of `--version` only end a shell or a CLI that hangs: on a busy or slow machine, where starting the login shell or the CLI takes several seconds, the CLI is still found and its version read, `checking` staying true meanwhile. Default chosen at design time.

| Outcome                                                    | available | path | version | error                                                                              |
| ---------------------------------------------------------- | --------- | ---- | ------- | ---------------------------------------------------------------------------------- |
| detection not finished                                     | false     | null | null    | null                                                                               |
| no candidate found                                         | false     | null | null    | `Claude CLI not found. Install Claude Code or set its path in Settings > General.` |
| candidate 1 or 2 is not an executable file                 | false     | set  | null    | `<path> is not an executable file.`                                                |
| `--version` exits non-zero, times out or prints no version | false     | set  | null    | `<path> --version failed: <reason>.`                                               |
| version found                                              | true      | set  | set     | null                                                                               |

`<reason>` is `timeout` after the timeout; the system's error text when the CLI cannot be spawned; else the first non-empty line of stderr, trimmed and without its trailing periods; else `exit code <n>`, n being 128 + the signal number for a process killed by a signal, as in `run.finished`. Default chosen at design time.

`checking` is true in the first row and false in the others: from engine start, and after a change of `claudePath`, until the CLI has been located and `--version` has answered. Default chosen at design time. When the status differs from the previous one, the engine emits `claude.updated` {status, models}. Running chat processes keep running after a change of `claudePath`; later launches use the new path.

When the CLI is unavailable, every method that has to deliver a message to Claude fails with `unavailable` and creates and changes nothing ([Engine API](engine-api.md#chats)), and Haiku naming keeps the provisional title. While `checking` is true, such a method waits for the computation to end, at most 20 seconds, then applies this rule. The message is `ClaudeStatus.error`, or `The Claude CLI is not available yet; it is still being checked.` while the status is still checking. No Claude process (chat process, naming call or models probe) starts before the environment capture has finished. Default chosen at design time.

### Models

`claude.models` returns the model list of the last `initialize` response received from the models probe or from a chat process ([Control protocol](#control-protocol)); `claude.updated` is emitted when the list changes. Models probe: at engine start and after each change of `claudePath`, once the CLI is found available, the engine starts `<CLI path> -p --input-format stream-json --output-format stream-json --verbose --no-session-persistence --strict-mcp-config --mcp-config '{"mcpServers":{}}'` in `<data dir>/Runtime/claude-cwd/` with the [Environment](#environment), writes the `initialize` control request, takes `response.models` from its answer and closes stdin; without an answer after 30 s it ends the probe as [Signals](#signals) specifies, and the list stays as it was. Default chosen at design time. Each entry of `response.models` becomes one `ClaudeModel`, in the same order:

| ClaudeModel field     | `initialize` field                        |
| --------------------- | ----------------------------------------- |
| value                 | `value`                                   |
| displayName           | `displayName`                             |
| description           | `description`                             |
| supportedEffortLevels | `supportedEffortLevels`, `[]` when absent |

An entry without a string `value` is skipped; a missing `displayName` is the `value` and a missing `description` is empty. Default chosen at design time. The engine also keeps each entry's `resolvedModel` in memory, to name the model of `system/init` ([Session start item](#session-start-item)).

Until the first `initialize` response since the engine started, and while the CLI is unavailable, the list is this fallback. Default chosen at design time.

| value   | displayName | description                                             | supportedEffortLevels         |
| ------- | ----------- | ------------------------------------------------------- | ----------------------------- |
| default | Default     | Recommended model                                       | low, medium, high, xhigh, max |
| opus    | Opus        | Best for everyday, complex tasks                        | low, medium, high, xhigh, max |
| fable   | Fable       | Most capable for your hardest and longest-running tasks | low, medium, high, xhigh, max |
| sonnet  | Sonnet      | Efficient for routine tasks                             | low, medium, high, xhigh, max |
| haiku   | Haiku       | Fastest for quick answers                               | low, medium, high, xhigh, max |

## Chat process

### Launch

A process starts when a message has to be delivered to a chat that has no live process. A chat has at most one process; the number of chats with a live process is not limited. The engine:

1. Takes the chat's stored `settings` ([Chat settings](#chat-settings)).
2. Writes the MCP configuration file ([MCP configuration file](#mcp-configuration-file)) and prepares the skills plugin ([Skills](skills.md#generation)).
3. Renders the system prompt ([System prompts](#system-prompts)).
4. Spawns the CLI with the arguments below, the working directory set to the project root and the environment above, with pipes on stdin, stdout and stderr.
5. Writes the `initialize` control request, then the user message, without waiting for any answer. The state becomes starting.
6. When `system/init` arrives, the state becomes running.
7. When no `system/init` arrives within 60 s, terminates the process (SIGTERM, then SIGKILL 5 s later), adds the system item `Claude did not start within 60 seconds.` with level error, and sets the state to error. Default chosen at design time.
8. When the spawn itself fails, adds the system item `Claude failed to start: <error description>` with level error and sets the state to error.

### Command line

Every row is one or two argv elements, in this order; no shell is involved.

| #   | Arguments                                                | Condition                                                                              |
| --- | -------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 1   | `<CLI path>`                                             | always                                                                                 |
| 2   | `-p`                                                     | always                                                                                 |
| 3   | `--input-format` `stream-json`                           | always                                                                                 |
| 4   | `--output-format` `stream-json`                          | always                                                                                 |
| 5   | `--verbose`                                              | always                                                                                 |
| 6   | `--include-partial-messages`                             | always                                                                                 |
| 7   | `--session-id` `<chat id>`                               | `sessionStarted` is false                                                              |
| 7   | `--resume` `<chat id>`                                   | `sessionStarted` is true                                                               |
| 8   | `--model` `<settings.model>`                             | always                                                                                 |
| 9   | `--effort` `<settings.effort>`                           | always                                                                                 |
| 10  | `--permission-mode` `<settings.permissionMode>`          | always; one of manual, acceptEdits, plan, auto, dontAsk, bypassPermissions             |
| 11  | `--allow-dangerously-skip-permissions`                   | always                                                                                 |
| 12  | `--permission-prompt-tool` `stdio`                       | always                                                                                 |
| 13  | `--mcp-config` `<data dir>/Runtime/mcp/<chat id>.json`   | always                                                                                 |
| 14  | `--allowedTools` `<pre-approved tools>`                  | always                                                                                 |
| 15  | `--disallowedTools` `AskUserQuestion`                    | always                                                                                 |
| 16  | `--append-system-prompt` `<rendered system prompt>`      | always                                                                                 |
| 17  | `--plugin-dir` `<data dir>/Runtime/plugins/<project id>` | the project enables at least one skill of the library ([Skills](skills.md#generation)) |
| 18  | `--settings` `{"ultracode":true}`                        | `settings.ultracode` is true                                                           |

- Rows 14 and 15 let `ask_questions`, `close_chat`, the read-only `hephaestus` tools and the tools that create and edit tickets, comments and bundles (`create_ticket`, `update_ticket`, `set_ticket_status`, `add_comment`, `update_comment`, `create_bundle` and `update_bundle`) run in every permission mode, and keep Claude from using the CLI's own question tool. The tools that delete (`delete_ticket`, `delete_comment`, `remove_attachment` and `delete_bundle`) are not pre-approved, so in Ask Every Time the user approves each call. Default chosen at design time, except for `close_chat` and the ticket, comment and bundle tools, which the user chose.
- `<pre-approved tools>` is this single argument: `mcp__hephaestus__ask_questions,mcp__hephaestus__close_chat,mcp__hephaestus__list_projects,mcp__hephaestus__get_project,mcp__hephaestus__list_tickets,mcp__hephaestus__get_ticket,mcp__hephaestus__create_ticket,mcp__hephaestus__update_ticket,mcp__hephaestus__set_ticket_status,mcp__hephaestus__add_comment,mcp__hephaestus__update_comment,mcp__hephaestus__list_bundles,mcp__hephaestus__get_bundle,mcp__hephaestus__create_bundle,mcp__hephaestus__update_bundle,mcp__hephaestus__search,mcp__hephaestus__list_docs,mcp__hephaestus__list_web_tabs,mcp__hephaestus__list_skills,mcp__hephaestus__get_skill,mcp__hephaestus__list_chats,mcp__hephaestus__get_chat`. Every other tool, the other `hephaestus` tools included, follows the chat's permission mode.
- `--permission-mode` takes `manual` for Ask Every Time; the control request `set_permission_mode` takes `default` for the same mode ([Permission mode](#permission-mode)).

Example, for a ticket chat that resumes its session in a project with enabled skills and ultracode on, with shell quoting and the prompt abbreviated:

```
claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages \
  --resume 3F2504E0-4F89-11D3-9A0C-0305E82C3301 \
  --model opus --effort high --permission-mode manual --allow-dangerously-skip-permissions \
  --permission-prompt-tool stdio \
  --mcp-config "$HOME/Library/Application Support/HephaestusV2/Runtime/mcp/3F2504E0-4F89-11D3-9A0C-0305E82C3301.json" \
  --allowedTools mcp__hephaestus__ask_questions,mcp__hephaestus__close_chat,mcp__hephaestus__list_projects,mcp__hephaestus__get_project,mcp__hephaestus__list_tickets,mcp__hephaestus__get_ticket,mcp__hephaestus__create_ticket,mcp__hephaestus__update_ticket,mcp__hephaestus__set_ticket_status,mcp__hephaestus__add_comment,mcp__hephaestus__update_comment,mcp__hephaestus__list_bundles,mcp__hephaestus__get_bundle,mcp__hephaestus__create_bundle,mcp__hephaestus__update_bundle,mcp__hephaestus__search,mcp__hephaestus__list_docs,mcp__hephaestus__list_web_tabs,mcp__hephaestus__list_skills,mcp__hephaestus__get_skill,mcp__hephaestus__list_chats,mcp__hephaestus__get_chat \
  --disallowedTools AskUserQuestion \
  --append-system-prompt "You are Claude, working inside HephaestusV2, …" \
  --plugin-dir "$HOME/Library/Application Support/HephaestusV2/Runtime/plugins/HEPH" \
  --settings '{"ultracode":true}'
```

### MCP configuration file

Before every launch the engine writes `<data dir>/Runtime/mcp/<chat id>.json` with file mode 0600:

```json
{"mcpServers":{"hephaestus":{"type":"http","url":"http://127.0.0.1:47820/mcp","headers":{"Authorization":"Bearer 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"}}}}
```

- The port is the one the MCP server listens on: `HEPHAESTUS_MCP_PORT` when set, else `mcpPort`.
- The token is a new chat token generated at each launch; the MCP server maps it to the Actor `claude` with the chat's id. When the process exits, the token is revoked and the file is deleted. Token format and lifetime: [MCP](mcp.md#authentication).

### User messages

Each message written to stdin is one line of compact UTF-8 JSON ending with `\n`:

```json
{"type":"user","message":{"role":"user","content":[{"type":"text","text":"Why does the build fail?\n\nAttached files:\n- /Users/example/Developer/HephaestusV2/.hephaestus/chats/3F2504E0-4F89-11D3-9A0C-0305E82C3301/9B2D6C1E-0F4A-4E8B-A1C2-3D4E5F607182-build.log"},{"type":"image","source":{"type":"base64","media_type":"image/png","data":"iVBORw0KGgo…"}}]},"uuid":"7C3E1F0A-2B4D-4E6F-8A9B-0C1D2E3F4A5B"}
```

- The engine first stores every attachment in the chat's attachment folder `chats/<chat id>/` ([Data model](data-model.md#attachments)). The stored `name` and `contentType` follow [AttachmentUpload](engine-api.md#attachmentupload).
- An attachment whose content type is `image/png`, `image/jpeg`, `image/gif` or `image/webp` and whose size is at most 5,000,000 bytes becomes an `image` block with `media_type` = its content type and `data` = its base64 content. Default chosen at design time.
- Every other attachment is listed in the text. The text sent is the message text; when files are listed, a blank line (only when the message text is not empty), the line `Attached files:` and one line `- <absolute path of the stored file>` per file follow it.
- The `text` block is left out when the text sent is empty. The content is the `text` block followed by the `image` blocks in attachment order.
- `uuid` is the `id` of the message's `user` item; the CLI reports what it does with the message under this id ([Turn tracking](#turn-tracking)). Default chosen at design time.
- The `user` item stores the message text without the `Attached files:` lines ([Data model](data-model.md#user-item)).
- A message sent from the inspector starts with the `Open in the app:` lines of its [linked items](#linked-items); the engine handles them as the rest of the text.
- Its `sender` is the name of the device of a `user` actor ([Request handling](remote.md#request-handling)), `Claude` for a `claude` actor, and the main device's name for the `system` actor. Default chosen at design time.

### Session and resume

- When `sessionStarted` is false the process gets `--session-id`; the engine sets `sessionStarted` to true (file write and `chat.updated`) when the first `system/init` of that process arrives.
- When `sessionStarted` is true the process gets `--resume`. When such a process exits before its `system/init` and its stderr contains `No conversation found with session ID`, the engine sets `sessionStarted` to false, adds the system item `Claude's session for this chat was not found. A new session started; Claude does not remember the earlier messages of this chat.` with level warning, and launches once more with `--session-id`, delivering the same message. Default chosen at design time.

### Stopping a turn

`chats.interrupt` does nothing in the states idle, waitingAnswers and error. In the other states the engine:

1. Denies every pending permission request of the chat with the message `The user stopped Claude.` ([Answer](#answer)); `decidedBy` is the name of the device that pressed Stop. Default chosen at design time.
2. Adds the system item `Stopped by <device name>.` with level info. Default chosen at design time.
3. Writes the control request `interrupt`. The CLI ends its CLI turn in progress with a `result` ([Turn result](#turn-result)). The messages waiting in its queue are not dropped: the CLI runs them next and the chat stays running ([Turn tracking](#turn-tracking)); Stop again stops them.
4. When no `result` has arrived 5 s later, sends SIGINT to the process; when the process is still alive 5 s after that, SIGTERM; SIGKILL 5 s after the SIGTERM when it is still alive ([Signals](#signals)).

An exit caused by these signals adds no error item.

When the chat has no process yet because its launch has not started it, the engine adds the `Stopped by` item, drops the messages waiting for the process, and the chat becomes idle, or waitingAnswers. Default chosen at design time.

### Idle termination and quitting

- When a turn ends, the engine starts a 20-minute timer; the next delivered message, or a `system/init` that starts a turn, cancels it. When it fires, the engine closes the process's stdin, sends SIGTERM when the process is still alive 5 s later, and SIGKILL 5 s after that. Default chosen at design time for the closing sequence.
- When the app quits ([UI](ui.md#unsaved-changes-and-quitting)), for every chat with a turn in progress the engine adds the system item `Stopped because HephaestusV2 quit.` with level warning and cancels its pending permission requests; then the processes end as [Architecture](architecture.md#shutdown) specifies (SIGTERM, then SIGKILL after 3 s). Default chosen at design time.
- `chats.delete` and `projects.remove` terminate the processes of the chats concerned: SIGTERM, then SIGKILL 5 s later.
- Closing a chat ends its process when the current turn ends ([Closing a chat](#closing-a-chat)).
- The next message to a chat whose process ended starts a new process with `--resume`.

### Closing a chat

Claude closes the chat it runs in with the MCP tool `close_chat` ([MCP](mcp.md#close_chat)), when the user asks for it or when the work of the chat is finished ([Prompt: common](#prompt-common), [Claude workflow](workflow.md#project-and-feedback-chats)). The tool is available in every chat kind and runs without a permission prompt in every permission mode ([Command line](#command-line)).

- `close_chat` calls `chats.close` for the calling chat ([Engine API](engine-api.md#chatsclose)). Nothing changes at once: Claude can still finish its reply.
- When the turn in progress ends ([Turn tracking](#turn-tracking)), the engine sets the chat's `closed` to true in the metadata write of the turn's end, which emits `chat.updated`, then ends the chat's process: it closes the process's stdin, sends SIGTERM when the process is still alive 5 s later, and SIGKILL 5 s after that, as for idle termination ([Signals](#signals)). Default chosen at design time for the closing sequence.
- When that turn is stopped with Stop, or ends in error (the chat's state becomes error, or the turn's last `result` has `isError`), or ends because the process exited, the close is cancelled: the chat stays open and its process is handled as without the call.
- `chats.close` for a chat without a turn in progress closes it at once. Default chosen at design time.
- `closed` is stored in the chat's metadata file ([Data model](data-model.md#chat-metadata-file)), so a closed chat stays closed after an app restart. Closing changes neither the chat's state ([Chat states](#chat-states)) nor its transcript: the chat stays in every list with its transcript.
- In a closed chat, the composer is replaced by the text `This conversation is over` on every client ([Composer](#composer)).
- Reopen, in the More menu of the chat view while the chat is closed ([Chat view](#chat-view)), calls `chats.reopen` ([Engine API](engine-api.md#chatsreopen)), which sets `closed` to false and emits `chat.updated`; the composer shows again, and the next message starts a process with `--resume` ([Session and resume](#session-and-resume)).
- A message delivered to a closed chat reopens it: `chats.send`, the answers message of a question set ([Answering](#answering)) and the report of an orchestrated ticket chat ([Orchestrated ticket chats](#orchestrated-ticket-chats)) set `closed` to false in the metadata write that follows the new `user` item, and the message is delivered as in an open chat.

### Signals

Every signal the engine sends to a Claude process, chat process, naming call or models probe, goes to its process group (`killpg`), so the commands it started (Bash tool commands, local MCP servers) receive it too. A sequence stops as soon as the process has exited. Default chosen at design time.

| Trigger                                                                              | Sequence                                                                                                           |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Stop ([Stopping a turn](#stopping-a-turn))                                           | `interrupt` request; SIGINT 5 s later when no `result` has arrived; SIGTERM 5 s after that; SIGKILL 5 s after that |
| No `system/init` within 60 s, `chats.delete`, `projects.remove`, an `mcpPort` change | SIGTERM; SIGKILL 5 s later                                                                                         |
| Idle termination, closing a chat ([Closing a chat](#closing-a-chat))                 | stdin closed; SIGTERM 5 s later; SIGKILL 5 s after that                                                            |
| Timeout of a naming call or of the models probe                                      | SIGTERM; SIGKILL 2 s later                                                                                         |
| App quit                                                                             | SIGTERM; SIGKILL 3 s later ([Shutdown](architecture.md#shutdown))                                                  |

### Exit handling and logs

- stderr of each chat process is appended to `<data dir>/Logs/claude-<chat id>.log`. Each launch first appends the line `--- <ISO-8601 date> launch: <argv> ---`, where the value of `--append-system-prompt` is replaced by `<N characters>`. `<argv>` is the arguments joined with spaces; an argument that is empty or holds a character other than letters, digits and `-_./:=,@+%` is written in single quotes, with each `'` written `'\''`. When the file is larger than 10 MB at launch, it is emptied first. Default chosen at design time.
- Every ignored stdout message ([Output mapping](#output-mapping)) appends the line `ignored <type>` or `ignored <type>/<subtype>` to the same file.
- With `HEPHAESTUS_DEBUG_TOOLS=1`, every stdout line is also appended unchanged to `<data dir>/Logs/claude-<chat id>.stdout.jsonl` ([Development](development.md)), the source of new fixtures.
- When the process exits during a turn with a non-zero exit code and the exit was not caused by Stop or a termination by the engine, the engine adds the system item `Claude exited with code <n>: <last non-empty stderr line>` (`Claude exited with code <n>.` when stderr was empty) with level error, and the state becomes error. When it was killed by a signal, the text is `Claude was terminated by signal <n>.` These texts are Default chosen at design time.
- On every exit the engine cancels the pending permission requests, finalizes the open blocks ([Streaming](#streaming)), revokes the chat token and deletes the MCP configuration file.

## Control protocol

Control messages travel on the same lines as the other messages. Request ids written by the engine are `hephaestus-<n>`, with `<n>` counting from 1 for each process. Default chosen at design time.

Requests from the engine to the CLI (`<id>` is the request id):

| Purpose         | Line written to stdin                                                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| start-up        | `{"type":"control_request","request_id":"<id>","request":{"subtype":"initialize"}}`                                                         |
| Stop            | `{"type":"control_request","request_id":"<id>","request":{"subtype":"interrupt"}}`                                                          |
| model           | `{"type":"control_request","request_id":"<id>","request":{"subtype":"set_model","model":"<settings.model>"}}`                               |
| permission mode | `{"type":"control_request","request_id":"<id>","request":{"subtype":"set_permission_mode","mode":"<CLI mode>"}}`                            |
| effort          | `{"type":"control_request","request_id":"<id>","request":{"subtype":"apply_flag_settings","settings":{"effortLevel":"<settings.effort>"}}}` |
| ultracode       | `{"type":"control_request","request_id":"<id>","request":{"subtype":"apply_flag_settings","settings":{"ultracode":<true or false>}}}`       |

Answers from the CLI:

| Outcome | Line read from stdout                                                                                    |
| ------- | -------------------------------------------------------------------------------------------------------- |
| success | `{"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{…}}}`        |
| error   | `{"type":"control_response","response":{"subtype":"error","request_id":"<id>","error":"<description>"}}` |

- The success `response` of `initialize` carries `models` ([Models](#models)). Other success payloads are not used.
- An error answer to `set_model`, `set_permission_mode` or `apply_flag_settings` adds the system item `Claude did not accept the new <model, permission mode, effort or ultracode> setting now: <description>. It applies the next time Claude starts.` with level warning. Other error answers are logged.
- A request without an answer after 30 s is logged and forgotten; for the settings requests the same warning item is added with the description `no answer`. Default chosen at design time.

Requests from the CLI to the engine:

| Request                                                 | Engine reaction                                                                                                                                   |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `control_request` with `request.subtype` `can_use_tool` | permission prompt ([Permission prompts](#permission-prompts))                                                                                     |
| `control_request` with any other subtype                | answers at once `{"type":"control_response","response":{"subtype":"error","request_id":"<id>","error":"Unsupported control request: <subtype>"}}` |
| `{"type":"control_cancel_request","request_id":"<id>"}` | cancels the pending permission request with that id ([Cancellation](#cancellation)); no answer is written                                         |

### Item ids

Item ids are formed as in this table. Default chosen at design time.

| Item                         | `id`                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------- |
| user, system, result         | a new uppercase UUID                                                         |
| questions                    | the question set's `questionSetID` (a new uppercase UUID)                    |
| assistant, thinking, toolUse | `<message id>#<block index>`, for example `msg_011CgbN9DUEEzm4yYRLnxmCV#0`   |
| toolResult                   | `<tool_use_id>#result`, for example `toolu_01JGkKXVVCvtBiysD3rhiEXj#result`  |
| permissionRequest            | `perm-<request_id>`, for example `perm-1967e0c0-4eab-4e9a-8c9e-67ec5e2cb4a0` |

Every item gets `created` = the time the engine creates it, in UTC with seconds. Default chosen at design time.

### Streaming

The engine keeps, per chat and per message id, the blocks opened by `content_block_start` events, in index order.

- Message id of a `stream_event` line: its `api_message_id` field; when absent, the `event.message.id` of the latest `message_start` event with the same `parent_tool_use_id`.
- `content_block_start` opens the block `event.index` of that message with the type `event.content_block.type`; its item id is `<message id>#<index>` and its accumulated text starts empty.
- A delta appends its text to the block's accumulated text and to its pending buffer. A delta with empty text changes nothing and never produces a `chat.delta`.
- Flush (Default chosen at design time): at most every 50 ms per chat, the engine emits one `chat.delta` {chatID, itemID, kind, append}, where `append` is the pending buffer of the block whose buffer is the oldest, and empties that buffer. Every chat thus stays at 20 `chat.delta` events per second or fewer.
- When the final item of a block is emitted, the block's pending buffer is dropped: the item carries the complete text.
- `chat.delta` events are not persisted and are not replayed to clients that connect later.
- Finalization: when a `result` arrives or the process exits, every open `text` or `thinking` block that has no final item and whose accumulated text is not empty becomes an `assistant` or `thinking` item with that text; every open `tool_use` block without a final item is dropped. Then the open blocks are cleared. Default chosen at design time.

### Assistant blocks

With `--include-partial-messages` the CLI sends one `assistant` line per finished content block, before that block's `content_block_stop`; the lines of one message share `message.id`. For each block of `message.content`, in order, the engine takes the first open block of the same message id with the same type and no final item yet, and uses its index. When none matches (a block that was not streamed), the index is the number of blocks already known for that message id, and the block is recorded as known.

| Content block `type`                         | Item        | Fields                                                                                                                                                         |
| -------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text`                                       | `assistant` | `text` = block `text`; `messageID` = `message.id`; `parentToolUseID` = line `parent_tool_use_id`. No item when `text` is empty. Default chosen at design time. |
| `thinking`                                   | `thinking`  | `text` = block `thinking`; `parentToolUseID` = line `parent_tool_use_id`. No item when `thinking` is empty.                                                    |
| `tool_use`                                   | `toolUse`   | `toolUseID` = block `id`; `name` and `server` from block `name` (rule below); `input` = block `input`; `parentToolUseID` = line `parent_tool_use_id`.          |
| any other type (`redacted_thinking`, others) | none        | the block still counts for the index rule                                                                                                                      |

Name rule ([Data model](data-model.md#tool-use-item)): a tool name `mcp__<server>__<tool>` gives `server` = the text between `mcp__` and the next `__`, and `name` = the rest; any other name gives `name` = the tool name and `server` = null. Example: `mcp__hephaestus__create_ticket` gives `server` `hephaestus` and `name` `create_ticket`.

With Claude Code 2.1.309 and its default thinking display, `thinking` blocks stream empty text (`thinking_display` `updates`), so they produce no item.

### Tool results

Each `tool_result` block of a `user` line becomes one `toolResult` item:

| Field       | Source                                                                                                                                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `toolUseID` | block `tool_use_id`                                                                                                                                                                                                     |
| `text`      | block `content` when it is a string; when it is an array, the `text` of its `text` blocks joined with `\n`, then one line of compact JSON per block that is neither `text` nor `image`                                  |
| `isError`   | block `is_error`; false when absent                                                                                                                                                                                     |
| `images`    | one Attachment per `image` block of `content`, stored in the chat's attachment folder with the name `image-<n>.<png, jpg, gif or webp>`, `<n>` counting from 1 in each result ([Data model](data-model.md#attachments)) |

An `image` block whose `source.type` is not `base64` holds no data and is left out; one without `source.media_type` counts as `image/png`. An image of another media type takes the media type's subtype as extension (`image/bmp` gives `bmp`), `bin` when it has none. Default chosen at design time.

A `toolResult` whose `toolUseID` matches no `toolUse` item is kept and rendered alone ([Item rendering](#item-rendering)).

### Session start item

For the first `system/init` of each process the engine adds a `system` item with level info and the text:

`Session started · <model name> · effort <settings.effort> · <permission label>`, followed by ` · Ultracode` when `settings.ultracode` is true.

- `<model name>`: the `displayName` of the first cached model whose value is not `default` and whose `resolvedModel` equals `init.model`; else the `displayName` of the model whose `value` equals `init.model`; else `init.model` itself. Example: `claude-opus-5-5` gives `Opus 5.5`.
- `<permission label>`: from `init.permissionMode`, with the labels of the column "System line" in [Permission mode](#permission-mode); a mode the table does not list is shown as the CLI reports it. Example: `default` gives `Ask every time`.
- When `system/init` has no `model` or no `permissionMode`, the chat's `settings.model` or the CLI value of `settings.permissionMode` stands for it. Default chosen at design time.

MCP check: when `init.mcp_servers` has no entry named `hephaestus`, or that entry's `status` is `failed`, `needs-auth` or `disabled`, the engine adds a `system` item with level warning and the text `MCP server hephaestus is <status, or missing when there is no entry>: the HephaestusV2 tools are not available in this session.` Default chosen at design time.

### Turn result

A `result` line becomes a `result` item:

| Field        | Source                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `durationMs` | `duration_ms`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `costUSD`    | `total_cost_usd`, the running total of the session, not the cost of this turn; null when absent                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `isError`    | `is_error`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `summary`    | null when `is_error` is false; else `Stopped by the user.` for the first `result` after Stop ([Stopping a turn](#stopping-a-turn)), whose `errors` hold only a diagnostic of the CLI such as `[ede_diagnostic] result_type=user last_content_type=n/a stop_reason=null` (Default chosen at design time); else `result` when `subtype` is `success`, else the `errors` strings joined with `\n`, else the `subtype` (`error_during_execution`, `error_max_turns`, `error_max_budget_usd`, `error_max_structured_output_retries`) |

### Turn tracking

Claude Code 2.1.309 runs the messages as CLI turns: a `system/init` line, the lines of Claude's work, then a `result` line. A message written during a CLI turn waits in the CLI's queue; when the CLI turn ends, the CLI runs every waiting message together as the next CLI turn, which starts with a new `system/init`. The CLI reports each message by the `uuid` of its line ([User messages](#user-messages)) in `command_lifecycle` lines:

```json
{"type":"command_lifecycle","command_uuid":"7C3E1F0A-2B4D-4E6F-8A9B-0C1D2E3F4A5B","state":"started","uuid":"1a63b051-eb56-4e4d-a9b2-7b8fff546781","session_id":"3F2504E0-4F89-11D3-9A0C-0305E82C3301"}
```

| `state`     | Sent when                                                                |
| ----------- | ------------------------------------------------------------------------ |
| `queued`    | the CLI has read the message                                             |
| `started`   | the CLI turn that runs the message begins, just before its `system/init` |
| `completed` | after the `result` of that CLI turn                                      |
| `cancelled` | after the `result` of that CLI turn, when Stop interrupted it            |

For each process the engine keeps the outstanding messages, those it wrote and that are not finished, each with the last `state` reported, and whether a CLI turn is open:

1. Writing a user message to the process adds it as outstanding, with no state.
2. `system/init` opens a CLI turn. When the chat has no turn in progress, a turn starts: the idle timer is cancelled and the state becomes running.
3. `command_lifecycle` records the `state` of the outstanding message `command_uuid`; a state other than `queued` and `started` finishes it. A line that names no outstanding message is ignored.
4. `result` closes the CLI turn and finishes every outstanding message whose state is `started`. When none has that state, it finishes the oldest outstanding message that has no state, so that a turn still ends when the CLI sends no `command_lifecycle` lines.
5. When step 3 or 4 leaves no outstanding message and no open CLI turn during a turn, the turn ends: the metadata file is rewritten, the idle timer starts and `chat.updated` reports the new state.
6. When the process exits, its outstanding messages are dropped ([Exit handling and logs](#exit-handling-and-logs)).

These rules are Default chosen at design time. Example with Claude Code 2.1.309, a new process and the messages A and B written 0.3 s apart:

| Line read, or message written                       | Outstanding         | CLI turn | State    |
| --------------------------------------------------- | ------------------- | -------- | -------- |
| A written                                           | A                   | closed   | starting |
| `command_lifecycle` A `queued`, then A `started`    | A started           | closed   | starting |
| `system/init`                                       | A started           | open     | running  |
| B written; `command_lifecycle` B `queued`           | A started, B queued | open     | running  |
| `result` of A                                       | B queued            | closed   | running  |
| `command_lifecycle` A `completed`, then B `started` | B started           | closed   | running  |
| `system/init`                                       | B started           | open     | running  |
| `result` of B                                       | none                | closed   | idle     |
| `command_lifecycle` B `completed`                   | none                | closed   | idle     |

### Plan usage

A `rate_limit_event` line reports the usage limits of the Claude account the CLI is signed in to. The engine reads only the weekly window, `seven_day`, of its `rate_limit_info`; the five-hour window and the other windows are not read. Every such line, from any chat of the device, replaces the engine's plan usage ([Engine API › Plan usage](engine-api.md#plan-usage)) with a [PlanUsage](data-model.md#plan-usage-file):

| PlanUsage field         | Taken from `rate_limit_info`                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `utilization`           | `unifiedWindows.seven_day.utilization`: the fraction of the week's limit used, usually 0 to 1; the CLI sends values above 1 past the limit. |
| `resetsAt`              | `unifiedWindows.seven_day.resetsAt`, in Unix seconds.                                                                                       |
| `status`                | `status`: `allowed`, `allowed_warning` or `rejected`. It describes the window that currently limits the account.                            |
| `overageStatus`         | `overageStatus`, for example `rejected`; null when absent.                                                                                  |
| `overageDisabledReason` | `overageDisabledReason`, for example `out_of_credits`; null when absent.                                                                    |
| `isUsingOverage`        | `isUsingOverage`; null when absent.                                                                                                         |
| `received`              | The time the engine read the line ([Plan usage](engine-api.md#plan-usage)).                                                                 |

The strings are stored as the CLI sends them, so a value that a later CLI version adds is kept and shown. An optional field of the wrong type, or a string that is empty or holds a line break, counts as absent; such a `status` makes the line ignored. The line produces no transcript item and is not logged. Default chosen at design time.

### Sub-agents

Lines with a non-null `parent_tool_use_id` come from a sub-agent started by the tool call (`Agent`, or `Task` in older CLI versions) with that id. Their `assistant`, `thinking` and `toolUse` items keep it in `parentToolUseID` and are rendered inside that tool call's card ([Tool cards](#tool-cards)); a `toolResult` is rendered in the card of its own `toolUse`, so it nests with it.

### Size limits

In a stored `toolUse.input` (at any depth) and in `toolResult.text`, a string longer than 100,000 characters is cut to 100,000 characters followed by `… [truncated <n> characters]`, where `<n>` is the number of characters removed. Default chosen at design time.

## Permission prompts

### Request

A `can_use_tool` control request carries `request_id` and `request` {`tool_name`, `display_name`, `input`, `description`, `permission_suggestions`, `decision_reason`, `decision_reason_type`, `tool_use_id`, other fields}. The engine:

1. Keeps the request in memory as pending: request id, input and `permission_suggestions`.
2. Adds a `permissionRequest` item: `requestID` = `request_id`, `toolName` = `tool_name`, `input` = `input`, `reason` = `decision_reason` with ANSI escape sequences removed (null when absent), `decision` and `decidedBy` null.
3. Sets the state to waitingPermission.

A `permissionRequest` item is pending while its `decision` is null.

### Answer

`chats.answerPermission` {chatID, requestID, decision, message?} ([Engine API](engine-api.md#chatsanswerpermission)) writes one line and replaces the item with `decision` and `decidedBy` = the name of the answering device:

| Decision      | Line written to stdin                                                                                                                                                                           |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `allow`       | `{"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{"behavior":"allow","updatedInput":<request input>}}}`                                               |
| `allowAlways` | `{"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{"behavior":"allow","updatedInput":<request input>,"updatedPermissions":<permission_suggestions>}}}` |
| `deny`        | `{"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{"behavior":"deny","message":"<message>"}}}`                                                         |

- `allowAlways` without `permission_suggestions` (absent or empty) writes the `allow` line. The suggestions are passed unchanged; their `destination` decides how long the CLI keeps them.
- `<message>` is the trimmed `message` parameter, or `Permission denied by the user.` when it is empty or absent. Default chosen at design time. The CLI returns it to Claude as the tool's error result.
- When the last pending request of the chat is answered, the state returns to running.
- Several clients can show the same request: the first answer wins and the others get `conflict`. A client that gets this conflict shows no alert: the card follows the `chat.item` event.

### Cancellation

A pending request is cancelled when the CLI sends `control_cancel_request` for it, when the process exits, or when the app quits: the item gets `decision` `deny` and `decidedBy` `null`, and no line is written. Answering a request that already has a decision fails with `conflict` (`This permission request was already answered.`). When the engine loads a transcript (`chats.get` or a launch) while the chat has no live process, every pending `permissionRequest` item is cancelled the same way. Default chosen at design time.

### Pinned permission card

While the chat has pending requests, a native SwiftUI card is pinned above the composer of every view of the chat:

- Header: `Claude wants to use <tool>`, where `<tool>` is the tool name, or the short name followed by a badge `MCP · <server>` for an MCP tool.
- Reason: the `reason`, in secondary text, when present.
- Every text of the card is selectable (`textSelection(.enabled)`): the header, the reason and the input preview.
- Input preview, at most 20 lines with a `Show All` button that shows the rest:

| Tool           | Preview                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| `Bash`         | `command` in monospace, then `description`                                                              |
| `Write`        | `file_path` and `content`, in monospace                                                                 |
| `Edit`         | `file_path`, then `old_string` on a red background and `new_string` on a green background, in monospace |
| `ExitPlanMode` | `plan` rendered as Markdown                                                                             |
| `WebFetch`     | `url` in monospace, then `prompt`                                                                       |
| any other tool | `input` as JSON with 2-space indentation, in monospace                                                  |

Paths and URLs are in SF Mono, as in [Principles](ui.md#principles). When a field that a row needs is missing (`command`; `file_path` and `content`; `file_path`, `old_string` and `new_string`; `plan`; `url`), the preview is `input` as JSON, as for any other tool. Default chosen at design time.

- A single-line field `Message for Claude (optional)`, sent as `message` with Deny.
- Buttons: Allow Once (⌘Return) → `allow`; Always Allow (⌥⌘Return) → `allowAlways`; Deny (⇧⌘Return) → `deny`. The three keys act while the keyboard focus is in the chat view outside its composer, and only once the request shown has been on screen for 1 second; from the composer, and earlier, they do nothing. Default chosen at design time.
- With several pending requests, the card shows the oldest one and `1 of <n>`.

### Mode changes made by the CLI

The chat's `settings.permissionMode` follows the CLI. When the engine answers `allowAlways` with suggestions that contain an entry `{"type":"setMode","mode":"<mode>"}`, or when a `system/status` line carries `permissionMode`, and that mode differs from the stored one, the engine stores it (the CLI value `default` stored as `manual`) and emits `chat.updated`. Default chosen at design time.

## Questions

Claude never invents unknowns: it asks with the MCP tool `ask_questions`, which calls `chats.postQuestions` for the chat that owns the token and returns at once. The rules Claude follows are in [Claude workflow](workflow.md#questions-protocol) and in the prompt [common](#prompt-common).

### Posting questions

`chats.postQuestions` accepts only the chat's own Claude ([Engine API](engine-api.md#chatspostquestions)). It checks these rules in this order and fails with `invalid` and the message of [Claude workflow](workflow.md#validation) on the first one broken:

| Rule                                                                                                     |
| -------------------------------------------------------------------------------------------------------- |
| 1 to 26 questions.                                                                                       |
| Question `n`, counting from 1, has the `n`-th letter of A–Z as `label`: A, B, C… in order.               |
| `question` is not empty after trimming.                                                                  |
| 2 to 10 options per question.                                                                            |
| Option labels are not empty after trimming and are unique within the question, ignoring case.            |
| Each option label is one line of at most 200 characters ([Data model](data-model.md#questions-item)).    |
| `recommended` equals the `label` of one of the question's options, so exactly one option is recommended. |

A chat has at most one question set that is not completed; posting another fails with `conflict` (`Questions are already waiting for answers in this chat.`). The MCP tool checks its own schema first ([MCP](mcp.md#question-rules)).

Once the set passes these rules, the engine moves each question's recommended option to the first place of its `options`; the other options keep their relative order. Claude's prompts have no rule about the place of the recommended option: the engine does the reordering. The engine then adds a `questions` item {questionSetID (new uppercase UUID), questions in this order, answers `{}`, completed false} and returns the `QuestionSet` with the same order, so the pinned questions card, the transcript's Questions card and every other device list the recommended option first. When the turn that posted it ends, the state becomes waitingAnswers. Example of `questions`:

```json
[
  {"label":"A","question":"Should Command-W on a locked tab do nothing, or select the next tab?","options":[{"label":"Do nothing and beep","description":"The tab never closes, as its lock icon promises."},{"label":"Select the next tab","description":"Command-W still moves away from the locked tab."}],"recommended":"Do nothing and beep"},
  {"label":"B","question":"Should the beep come with a tooltip?","options":[{"label":"Yes, \"This tab is locked\""},{"label":"No"}],"recommended":"Yes, \"This tab is locked\""}
]
```

### Answering

`chats.answerQuestion` {chatID, questionSetID, label, answer} ([Engine API](engine-api.md#chatsanswerquestion)) stores one answer:

- `answer` is trimmed and has 1 to 10,000 characters (`invalid` otherwise).
- `label` is the label of any question of the set (`invalid` otherwise): the questions are answered in any order, and answering a question that already has an answer replaces that answer.
- A completed set gives `conflict`. A client whose answer fails because the set was completed on another device (`conflict` while `chat.item` already carries the completed set) shows no alert.
- The item is replaced with `answers[label] = answer`. When every question of the set then has an answer, the item also gets `completed` true, and the engine delivers the Answers message as a user message whose `sender` is the name of the answering device. During a turn it is delivered like any message ([Chat states](#chat-states)).
- Skipping a question stores the answer `Skipped` ([Pinned questions card](#pinned-questions-card)). It counts as an answer: a set whose questions are all answered or skipped is completed.

Answers message, with the answers in label order, lines separated by `\n`; an answer keeps its own line breaks, and a skipped question reads `<label>: Skipped`:

```
Answers:
A: Do nothing and beep
B: Skipped
```

Claude leaves a skipped point out: it does not act on it or guess, and it mentions it in its reply ([Prompt: common](#prompt-common)).

A set stays incomplete across process exits and app restarts; answering its last unanswered question later starts a process with `--resume`. Messages typed in the composer while a set is incomplete are delivered normally and do not change the set. Until every question of the set has an answer, the set stays pinned and Claude cannot post another set in this chat. Default chosen at design time.

### Pinned questions card

While the chat has a question set that is not completed, a native SwiftUI card is pinned above the composer of every view of the chat, below the permission card when both exist. It shows one question of the set at a time. Each chat view chooses its displayed question on its own: when the card appears for a set, it displays the first question of the set, in label order, that has no answer.

- Header `Question <label> (<position> of <count>)`, where `<position>` is the displayed question's place in the set counting from 1, for example `Question A (1 of 1)` or `Question B (2 of 3)`.
- At the top right, previous and next arrow buttons, then a minimize button, a chevron pointing down. The arrows display the previous and the next question of the set, in label order, answered or not; they wrap at neither end: the previous arrow is disabled on the first question and the next arrow on the last one.
- The question text rendered as Markdown ([Block model](documentation-viewer.md#block-model)) with the `isSymbolAvailable` of [Links, images and files](#links-images-and-files): an SF Symbol marker of an available symbol shows the symbol's image (`Image(systemName:)`) followed by a space and its name, inline in the text; any other marker shows its text unchanged.
- One row per option: a radio button, then the label in bold and the description in secondary text. The label and the description are plain text in which each SF Symbol marker of an available symbol shows the symbol's image followed by a space and its name ([SF Symbol markers](documentation-viewer.md#sf-symbol-markers)). A click anywhere in the row (the radio button, the label, the `Recommended` tag, the description or the empty space) chooses the option. The label and the description are not selectable as text. The recommended option carries a `Recommended` tag.
- The header and the question text are selectable (`textSelection(.enabled)`); the texts of the option rows are not.
- A last radio row `Answer another way` with a multi-line text field (1 to 6 visible lines). A click on the radio button, the label `Answer another way` or the empty part of its line chooses this row; the field stays editable, and typing in it selects this row; Return inserts a line break.
- Selection when a question is displayed: a question without an answer appears with its recommended option selected and an empty field. An answered question appears with its answer selected: the option whose label equals the answer, or else `Answer another way` with the answer as its text; a skipped question thus shows `Answer another way` with the text `Skipped`.
- Submit (⌘Return while the focus is in the chat view outside its composer, no permission card is shown and the card is not minimized) calls `chats.answerQuestion` for the displayed question with the selected option's label, or with the field's text. It is disabled while `Answer another way` is selected with an empty field. Submitting on an answered question replaces its answer.
- Skip, next to Submit, calls `chats.answerQuestion` for the displayed question with the answer `Skipped`.
- After a successful Submit or Skip, the card displays the next question after the displayed one, in label order, that has no answer, wrapping to the first question of the set; when every question has an answer the set is completed and the card disappears.
- The transcript's Questions card of the same chat view marks the displayed question with `➡️` before its label, and the mark moves when the card displays another question ([Item rendering](#item-rendering)).
- Answers given in another view or on another device appear live through `chat.item`. When one is for the displayed question, the card keeps displaying that question and selects the new answer.
- Minimize: the minimize button turns the card into a one-line collapsed bar above the composer, which shows the card's header text and a chevron pointing up. Clicking the bar opens the card again. The minimized state is kept per chat and applies to the question set that was minimized: a new question set of the chat opens the card. It is stored on this device only, never in the chat files and never synced, and survives an app restart ([UI › Persistence](ui.md#persistence)). Every view of the chat on this device shares it.

## Transcript view

### Web view and bridge

The transcript of a chat view is one `WKWebView` loading the bundled `chat.html`, `chat.css` and `chat.js` (`Sources/HephaestusUI/Resources/`), so the text of every bubble is selectable as one document. Swift renders each item to an HTML fragment (Markdown through the HephaestusText HTML renderer, with the rules of [Documentation viewer](documentation-viewer.md)), and `chat.js` places the fragments. The fragment of a `questions` item that is not completed also depends on the question that the pinned questions card of the same chat view displays: when that question changes, Swift renders the fragment again and sends it with `upsert`, so the `➡️` mark of [Item rendering](#item-rendering) moves with the card. The page runs no other script, except the user script of the inspector's transparent background below, and never navigates. Its context menu keeps Copy, Copy Link, Copy Image and Look Up, as the doc preview's ([Preview web view](documentation-viewer.md#preview-web-view)). The bridge and the context menu are Default chosen at design time.

In the inspector the transcript has a transparent background, so that the inspector's frosted material shows through it ([Inspector](ui.md#inspector)): the web view draws no background (`drawsBackground` false, `underPageBackgroundColor` clear), and a user script injected at document start adds the class `transparent` to the page's root element, for which `chat.css` makes the `html` and `body` backgrounds transparent. The bubbles, cards and buttons keep their backgrounds. In the other chat views the page keeps the opaque page background of `chat.css`. The user script is Default chosen at design time.

Calls from Swift (`evaluateJavaScript`) on the global object `HephaestusChat`:

| Call                                      | Effect                                                                                                                                                            |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reset({items, hasEarlier, placeholder})` | Replaces the transcript with `items` (fragments in order); shows the `Show Earlier Messages` button when `hasEarlier`; shows `placeholder` when `items` is empty. |
| `prepend({items, hasEarlier})`            | Inserts older fragments before the first one.                                                                                                                     |
| `upsert(fragment)`                        | Adds the fragment, or replaces the fragment with the same `id`, and removes the streaming bubble with that id.                                                    |
| `stream({itemID, kind, html})`            | Creates or updates the streaming bubble `itemID` of kind `text`, `thinking` or `toolInput`.                                                                       |
| `clearStreams()`                          | Removes every streaming bubble.                                                                                                                                   |

A fragment is `{id, type, html, parentToolUseID, toolUseID}`: `type` is the item type, `parentToolUseID` the item's value or null, `toolUseID` the value of `toolUse` and `toolResult` items or null.

Messages to Swift (`window.webkit.messageHandlers.hephaestus.postMessage`):

| Message                                              | Effect                                                          |
| ---------------------------------------------------- | --------------------------------------------------------------- |
| `{"action":"ready"}`                                 | the page is loaded; Swift calls `reset`                         |
| `{"action":"openLink","url":"…","commandKey":false}` | [Links, images and files](#links-images-and-files)              |
| `{"action":"copy","text":"…"}`                       | puts the text on the general pasteboard as plain text           |
| `{"action":"openAttachment","path":"…"}`             | opens the attachment (`path` relative to `.hephaestus/`)        |
| `{"action":"loadEarlier"}`                           | Swift calls `prepend` with the 300 items before the first shown |

### Tool cards

A tool card is collapsed by default. Its header row shows an icon, the tool name (the short name for MCP tools), the badge `MCP · <server>` for MCP tools, a one-line summary truncated with an ellipsis, and at the trailing edge a spinner (no result yet while the chat is running), the red tag `Error` (result with `isError`), or nothing. Clicking the header expands the card:

- `Input`: `input` as JSON with 2-space indentation; for `Bash`, the `command` as a shell code block; for `Edit`, `old_string` and `new_string` as two code blocks; for `Write`, `content` as a code block whose language word is the extension of `file_path`, lowercased: the languages of [Code blocks](documentation-viewer.md#code-blocks) are highlighted, other extensions are plain.
- `Result`: the result text in monospace, first 200 lines with a `Show All` button; result images as thumbnails.
- `Steps`: the items whose `parentToolUseID` is this card's `toolUseID`, in order, rendered with the same rules. A collapsed card that has steps shows `<n> steps` in its header, `1 step` for one.

| Tool                                    | Icon      | Summary                                                                       |
| --------------------------------------- | --------- | ----------------------------------------------------------------------------- |
| `Bash`                                  | terminal  | first line of `command`                                                       |
| `Read`, `Write`, `Edit`, `NotebookEdit` | document  | `file_path` (or `notebook_path`), relative to the project root when inside it |
| `Glob`, `Grep`                          | magnifier | `pattern`, followed by ` in <path>` when `path` is set                        |

| `Agent`, `Task`                         | people    | `description`                                                                 |
| `TodoWrite`                             | checklist | `<n> todos`, the number of elements of `todos`                                |
| MCP tools                               | plug      | generic rule                                                                  |
| any other tool                          | wrench    | generic rule                                                                  |

Summaries are cut at 120 characters with `…`. The icons are inline SVG drawings in `chat.js`. Icons and summaries: Default chosen at design time.

### Streaming bubbles

- The first `chat.delta` of an item id without a fragment creates a streaming bubble: kind `text` an assistant bubble, kind `thinking` an expanded `Thinking` block, kind `toolInput` a card `Preparing tool call…` that shows the last 300 characters of the partial JSON in monospace.
- Each later `chat.delta` appends to that item's streaming buffer (`TranscriptState`, [UI](ui.md#deviceworkspace)); text and thinking bubbles are rendered again as Markdown on every update.
- A `chat.item` with the same id replaces the streaming bubble in place.
- When `chat.updated` reports the state idle, waitingAnswers or error, every remaining streaming bubble is removed.

### Links, images and files

- Clicking an `http` or `https` link opens it in a new web tab of the chat's project (`webTabs.open`) and navigates to the new tab (`webTab` target) in the chat view's main window, or, from a chat window, in the main window chosen by [Choosing the window](ui.md#choosing-the-window); ⌘-click opens it in the default browser of the Mac showing the window. Default chosen at design time.
- A relative link, or a `file` URL inside the project root, opens the file: in the Docs section when its name ends in `.md` (any letter case) and it is under `docsPath`, else in the Code section. A `.markdown` file opens in the Code section. In the Code section the line of a GitHub line fragment (`L<n>`, `L<n>-L<m>`, `L<n>C<c>`) is shown, as in the doc preview ([Link activation](documentation-viewer.md#link-activation)). Other links, a `#fragment` link included, do nothing. The same window choice applies. Default chosen at design time.
- A link click that fails, such as a failed `webTabs.open`, shows the alert `Open Link failed`; a file of the transcript that cannot be read shows the alert `Open failed` ([Principles](ui.md#principles)). Default chosen at design time.
- Images use URLs `hephaestus-attachment://attachment/<percent-encoded path relative to .hephaestus/>`, served by a `WKURLSchemeHandler` that calls `attachments.read` for the chat's project through the window's engine connection; results are cached per window.
- Clicking an image opens the [image viewer](tickets.md#image-viewer). Clicking another file opens it with Quick Look on a temporary copy, as for ticket attachments ([Tickets](tickets.md#showing-attachments)).
- An SF Symbol marker is a Markdown image whose source has the scheme `sf`, for example `![](sf:line.3.horizontal.decrease.circle)` ([SF Symbol markers](documentation-viewer.md#sf-symbol-markers)). The transcript renders Markdown with `isSymbolAvailable` true for a name when `NSImage(systemSymbolName:accessibilityDescription:)` gives an image for it on the Mac that shows the window. A marker of such a name is drawn as the symbol's icon followed by its name; any other marker shows its text unchanged, for example `![](sf:no.such.symbol)`.
- The icon is the `md-symbol-icon` element of the marker: 1.25em wide and 1em high, 0.25em before the name, filled with the color of the text around it through a mask that holds the symbol's image, scaled to fit and centered. `chat.js` sets that mask to `hephaestus-symbol://symbol/<name>`, the name encoded with `encodeURIComponent`, and the page's Content Security Policy allows `hephaestus-symbol:` images. Default chosen at design time.
- `SymbolSchemeHandler`, registered for `hephaestus-symbol` on the transcript web view only, answers a GET whose host is `symbol` with a PNG of the symbol named by the percent-decoded path without its leading `/`, drawn from `NSImage(systemSymbolName:accessibilityDescription:)` at 48 points and scale 2. The response has status 200, `Content-Type: image/png`, `Content-Length` and `Access-Control-Allow-Origin: *`, since WebKit loads mask images in CORS mode. It makes no engine call, so a window showing a remote device draws the symbols of its own Mac. A name without symbol fails with `URLError(.fileDoesNotExist)` and a malformed URL with `URLError(.noPermissionsToReadFile)`. Default chosen at design time.

### Orchestrated ticket chats

The bundle chat started by Implement All or `implement_bundle` is the orchestrator of its bundle: it starts one ticket chat per ticket and waits for each one's report ([Implement All](tickets.md#implement-all), [Claude workflow](workflow.md#bundles)).

- `chats.implementTicket` called by a `claude` actor whose chat is of kind `bundle`, for a ticket that this chat's bundle lists, creates an orchestrated ticket chat: its `orchestrator` is the calling chat ([Data model](data-model.md#chat-metadata-file)), and its first message is the rendered implement-bundle-ticket prompt. Every other call creates a ticket chat without `orchestrator`, whose first message is the rendered implement-ticket prompt.
- The orchestrated ticket chat is in its ticket's `chats`. It is listed in the ticket's Chats tab, and in the bundle's Chats tab under its orchestrator ([Bundles section](tickets.md#bundles-section)). It asks its questions and permission prompts in its own chat, where the user answers them.
- When the state of a chat with an `orchestrator` goes from `starting`, `running` or `waitingPermission` to `idle` or `error`, the engine sends the orchestrator chat one message, as the `system` actor, so its `sender` is the main device's name ([Engine API](engine-api.md#chatssend)):

| The turn                                                                                        | Message                                                                      |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| was stopped with Stop                                                                           | `Chat of <TICKET-ID> was stopped.`                                           |
| left the chat in state `error`, or its last `result` has `isError` without being a stopped turn | `Chat of <TICKET-ID> ended in error: <error message>`                        |
| ended otherwise                                                                                 | `Chat of <TICKET-ID> finished its turn:`, a blank line, then the final reply |

- `<TICKET-ID>` is the ticket chat's `ticket`. The final reply is the text of the turn's last `assistant` item without `parentToolUseID`, empty when the turn has none. The error message is the text of the turn's last `system` item of level `error` when there is one, otherwise the `summary` of the turn's last `result`.
- A turn that ends in `waitingAnswers`, on `ask_questions`, sends nothing: the orchestrator keeps waiting, and the turn that follows the answers reports.
- Nothing is sent while the engine stops, or when the orchestrator chat no longer exists or is being deleted; `engine.log` records the skipped message.
- The orchestrator receives the message in any state ([Chat states](#chat-states)): during one of its turns, the CLI runs it after that turn. A closed orchestrator chat is reopened by the message ([Closing a chat](#closing-a-chat)).

These rules are Default chosen at design time, except the message texts, which the user chose.

## Haiku naming

A Haiku call names tickets created without a title, bundles created without a title, and every chat after its first user message.

### Command

```
<CLI path> -p --model haiku --output-format json --no-session-persistence --tools "" --strict-mcp-config --mcp-config '{"mcpServers":{}}' --system-prompt <naming prompt> <input>
```

- The command is shown with shell quoting; the engine passes each argument as one argv element, without a shell.
- `<naming prompt>` is the resource naming-ticket, naming-bundle or naming-chat, unchanged. `<input>` is built as below and never starts with `-`.
- Working directory: `<data dir>/Runtime/claude-cwd/`, an empty folder created when missing ([Architecture](architecture.md#child-processes)); environment: [Environment](#environment). Default chosen at design time.
- Timeout 30 s: SIGTERM, then SIGKILL 2 s later ([Signals](#signals)); the provisional title stays.
- At most 2 naming calls run at once; the others wait in first-in first-out order. Default chosen at design time.
- Failures and timeouts are written to `engine.log`.

### Inputs

| Subject | `<input>`                                                                              | Maximum title length | Provisional title                       |
| ------- | -------------------------------------------------------------------------------------- | -------------------- | --------------------------------------- |
| ticket  | `Ticket description:` + `\n` + the description                                         | 70                   | [Tickets](tickets.md#titles-and-naming) |
| bundle  | `Tickets:` + `\n` + one line `<ticket id>: <ticket title>` per ticket, in bundle order | 60                   | [Tickets](tickets.md#bundle-rules)      |
| chat    | `First message:` + `\n` + the text of the chat's first `user` item that has text       | 60                   | `New Chat`                              |

- The first line of each `<input>` (the label) and the part after it, cut at 4,000 characters: Default chosen at design time.
- When the first user message of a chat has no text, the chat is named from the first later user message that has text.

### Output cleanup

1. Parse stdout as one JSON object. A parse failure, a non-zero exit code or `is_error` true keeps the provisional title.
2. Take `result`, trim it, and keep its first line.
3. Remove a leading `Title:`, `Ticket title:`, `Bundle title:` or `Chat title:` (any letter case) and trim. Default chosen at design time.
4. Remove surrounding quote characters (`"`, `'`, `“`, `”`, `‘`, `’`, `«`, `»`, `` ` ``) from both ends, repeatedly, and trim.
5. Remove trailing periods and trim. Steps 4 and 5 run again, in this order, until neither changes the text: `` `Fix it`. `` and `"Fix it."` both give `Fix it`. Default chosen at design time.
6. When the text is longer than the maximum, cut it at the last space at or before the maximum (at the maximum when there is no space) and trim. Default chosen at design time.
7. An empty text keeps the provisional title.

### Applying the title

- The Haiku title replaces the title only when the current title still equals the provisional title, so a title set meanwhile by the user or by Claude wins.
- The update emits `ticket.updated`, `bundle.updated` or `chat.updated` with origin `system`. Chat windows follow the chat title.
- Naming is not retried, after a failure or after an app restart.

## Persistence

| Path (relative to `.hephaestus/`)               | Content                                                                                                                                   |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `chats/<chat id>.yml`                           | chat metadata ([Data model](data-model.md#chat-metadata-file))                                                                            |
| `chats/<chat id>.jsonl`                         | transcript: `{"op":"add","item":ChatItem}` and `{"op":"update","item":ChatItem}` lines ([Data model](data-model.md#chat-transcript-file)) |
| `chats/<chat id>/<attachment uuid>-<file name>` | the chat's attachment folder: user attachments, the feedback screenshot and tool-result images ([Data model](data-model.md#attachments))  |

- The line `chats/` of `.hephaestus/.gitignore` keeps all three out of git.
- The metadata file is rewritten atomically when the title, settings, links, `sessionStarted` or `closed` change, when a user message is added and when a turn ends; each rewrite sets `updated` and emits `chat.updated`.
- Each new item appends an `add` line; replacing an item (a permission decision or cancellation, an answer) appends an `update` line. The transcript is never rewritten; loading replays it as [Data model](data-model.md#replay) specifies.
- `chats.delete` terminates the process, keeps the chat's cost in the project's `deletedChats` ([Deleted chats](costs.md#deleted-chats)), removes the chat id from its ticket's or bundle's `chats`, and moves the metadata file, the transcript and the attachment folder to the Trash ([Engine API](engine-api.md#chatsdelete)). Claude's own session files are left untouched. From the moment `chats.delete` starts, the engine ignores every line the chat's terminating process still writes, adds no item, writes no file and emits no event for that chat.

# HephaestusV2 tools

HephaestusV2 gives you the MCP server "hephaestus". Its tools appear to you as mcp__hephaestus__<name>:

- Projects: list_projects, get_project, create_project, update_project, remove_project, run_project (runs the project's build, run or test command), stop_run (stops a run).
- Tickets: list_tickets, get_ticket, create_ticket, update_ticket, delete_ticket, set_ticket_status, add_comment, update_comment, delete_comment, remove_attachment, implement_ticket (starts a new chat that implements a ticket).
- Bundles, groups of tickets implemented together: list_bundles, get_bundle, create_bundle, update_bundle, set_bundle_status, delete_bundle, implement_bundle (starts a new chat that implements a bundle).
- Questions to the user: ask_questions.
- Search and documentation: search (projects, tickets, bundles, docs, code, chats, skills and web tabs), list_docs.
- Chats: list_chats, get_chat (a chat and its transcript, for example another chat of the same ticket), rename_chat, close_chat (closes the chat you run in).
- The project's integrated browser: list_web_tabs, open_web_tab, update_web_tab, move_web_tab, close_web_tab.
- The HephaestusV2 skills library: list_skills, get_skill, create_skill, update_skill, delete_skill, set_skill_enabled (enables or disables a skill in a project).
- Navigation: open_in_app (shows the user a project, ticket, bundle, chat, doc, file, skill, web tab or section of a project).

Read and change HephaestusV2 data (projects, tickets, comments, bundles, chats, web tabs and skills) only with these tools. Never create, edit or delete files inside a .hephaestus folder yourself: HephaestusV2 owns them, validates every change and shows it to the user live. To show the user an item, call open_in_app. Files the user attaches to a message are saved on this device: images are included in the message, and the paths of the other files are listed at the end of the message.

# Never invent

- Never invent a requirement, a behaviour, a name or value visible to users, a text shown to users, a file format or a product decision. Everything of this kind that you build comes from the user's messages, the ticket with its comments and attachments, the docs, or the existing code.
- Technical choices inside the code that change no documented behaviour are yours to make.
- Before you ask, look for the answer yourself in the ticket, its comments and attachments, the docs, the code and the git history. Ask only what is still unknown.
- Statements that contradict each other, such as a comment that contradicts the description, are an unknown.
- Ask what is still unknown before you act on it, then end your turn and wait. Never continue on a guess to be confirmed later.
- In comments and replies, report only what you did and checked.

# Asking questions

- Ask only with ask_questions, never with questions written in your reply.
- Put every point that is unknown at that moment into one call, with at most 26 questions.
- Label the questions A, B, C and so on, in order, starting at A in every call.
- Make each question ask for one decision, and give it 2 to 10 options. An option's label is the answer itself; its optional description is one line that states the consequence of that answer.
- Set recommended to the label of exactly one option of each question: the option you recommend.
- Add no "Other" option: the user can always answer another way.
- After ask_questions returns, end your turn: call no other tool, and do not repeat the questions in your reply, because the chat shows them.
- Never call ask_questions while earlier questions of this chat still wait for their answers.

The user answers the questions one by one in HephaestusV2. All the answers arrive in your next user message, in this form:

Answers:
A: <answer to question A>
B: <answer to question B>

An answer is the label of one of your options or the user's own words. The answer Skipped means that the user skipped the question: leave that point out, without acting on it or guessing, and mention it in your reply. Answers are decisions: apply them and do not ask them again. When an answer raises a new unknown, ask a new set of questions, labelled from A again.

# Writing tickets

- Create a ticket with create_ticket: projectID, description and, when needed, attachments. Never give a title: HephaestusV2 names the ticket. A new ticket starts with the status todo.
- When something the ticket needs is unknown, ask first and create the ticket after the answers.
- Create one ticket per problem: a request that covers several problems gets one create_ticket call per problem.
- attachments are paths of files on this device, such as screenshots or logs; HephaestusV2 copies them into the ticket.
- After you create tickets, tell the user their ids.
- When you rewrite the description of an existing ticket with update_ticket, the new description follows the template too.

Write every description with exactly this template. Keep the six headings unchanged, in this order, each alone on its line, and replace every hint line in parentheses with your text; never keep a hint line. HephaestusV2 rejects a description that does not follow the template.

<template>
Problem
(Explain the problem)

Current Behavior
(Explain the current behaviour)

Expected
(Explain the behaviour that should be expected)

Change
(Explain what should change)

Testing
(List the tests that decide whether the ticket is done)

Docs
(List all docs files and paragraphs relevant to the issue)
</template>

Under each heading, write:

- Problem: what is wrong or missing, from the user's point of view, in one to three sentences.
- Current Behavior: what happens today, with numbered steps to reproduce a defect. For a feature that does not exist yet, write: None: the feature does not exist yet.
- Expected: the behaviour after the change, precise enough to be tested.
- Change: what changes in the docs and in the code, naming the docs files and the code areas, limited to what has been decided.
- Testing: one bullet per test that decides whether the ticket is done, prefixed with who performs it: - Claude: <test> for a test you run, or - User: <test> for a test the user performs.
- Docs: one bullet per relevant docs file and section, as a Markdown link relative to the project root, for example: - [tickets.md › Status rules](docs/tickets.md#status-rules). Write (new) after a section that does not exist yet.

# Ticket status

A ticket's status is todo (not started), in_progress (being worked on), review (finished, waiting for the user's review) or done (finished and accepted).

- Every ticket is created with the status todo.
- Set in_progress with set_ticket_status when you start working on a ticket: as the first step of implementing it, and in a ticket chat before your first change to the docs or the code for that ticket. Reading the ticket and asking questions do not change the status.
- When you have finished a ticket, after its completion comment, set it with set_ticket_status to done when every Claude test of its Testing section has passed and the user has said in the chat that every User test has passed; otherwise set it to review, and your completion comment and your final reply ask the user to review it and set it to Done. A ticket without a Testing section goes to review.
- When the user later says in the chat that every User test of a ticket in review has passed, and every Claude test has passed, set it to done.
- To change a ticket that is in review, for example for a correction the user asked for, set it to in_progress before your first change and back to review after the completion comment of the correction.
- Never change the status of a ticket that is done, and never implement it: tell the user to set its status to To Do or In Progress first.
- Set todo only when the user asks for it, or when the user decides to skip a ticket of a bundle.
- When HephaestusV2 answers forbidden, tell the user its message and do not work around it.

# Implementing a ticket

Follow these steps in this order.

1. Set the ticket to in_progress with set_ticket_status.
2. Read the ticket with get_ticket: its description, comments and attachments; view image attachments by reading their paths. Read every docs section listed under Docs, the docs index (the README.md of the docs folder, when there is one) and the code involved. When anything is unknown, ask with ask_questions, end your turn, and continue when the answers arrive.
3. Change the docs first. Change every affected docs section so that it describes the behaviour after the change completely, following the conventions of that docs folder. When the docs already describe the expected behaviour (a defect where the code differs from the docs), leave them unchanged and say so in the completion comment. When the project has no docs folder, ask whether to create one, recommending <docs folder>/<topic>.md.
4. Then change the code until it does what the docs say. Where the project has tests, add or update tests for the changed behaviour.
5. Build and test. When the project has build or test commands, run them with run_project, kind build then kind test, and wait for each. Otherwise run the repository's own commands with your shell tool: the Makefile targets build and test when they exist, otherwise swift build and swift test for a Swift package, or go build ./... and go test ./... for a Go module. When a command fails, fix the cause and run it again. Never commit while the build or the tests fail; when a failure also happens without your change, ask whether to commit anyway. When no build or test command exists, skip this step and say so in the completion comment. Do not start the project's run command unless the user asks for it.
6. Commit, then push, as "Commits" and "Pushing" describe.
7. Post the completion comment that "Completion comment" describes, with add_comment.
8. Set the ticket to done or review with set_ticket_status, as "Ticket status" describes.
9. End with a short final reply: what changed, the commit, the checks, the result of each test, and, for a ticket in review, that it waits for the user to set it to Done.

# Commits

The first line of the commit message is:

<type>: <summary> (<TICKET-ID>)

An optional body and an optional footer follow it, each after a blank line.

- <type> is one of: feat (new behaviour, or a change to intended behaviour), fix (a defect corrected), docs (a change to the docs only), refactor (code restructured without a change in behaviour), perf (faster or lighter code without a change in behaviour), test (a change to the tests only), build (build system, packaging and dependencies), ci (CI workflows and their scripts), chore (any other maintenance). When the docs and the code change together, the type describes the code change (feat or fix), not docs.
- Put no scope: nothing comes between the type and the colon except ! for a breaking change.
- Write the summary in English, in the imperative mood, starting with a lowercase letter unless it starts with a name or code, without a final period. The whole first line has at most 72 characters. Example: fix: answer 503 from /health when the database is down (DEMO-7)
- The body explains why. It is wrapped at 72 columns.
- Write a breaking change as <type>!: <summary> (<TICKET-ID>) with the footer BREAKING CHANGE: <what breaks>, only when the ticket or the user says that the change breaks compatibility; ask when unsure.
- Make one commit per ticket. A later correction asked for in the same chat gets its own commit, with the same ticket id. Work without a ticket, done in a project chat at the user's request, uses the same format without (<TICKET-ID>).
- Stage by path only the files you changed for the ticket. Never run git add -A or git add ., never stage the .hephaestus folder (the user commits ticket data), and never commit changes you did not make. When a file you must change already has uncommitted changes you did not make, ask.
- Never amend or rebase a pushed commit, never skip hooks with --no-verify, never force-push, and never change the git configuration.

# Pushing

- Push the current branch to its upstream with git push. Create no branch and no pull request.
- When the branch has no upstream and a remote named origin exists, run git push -u origin <branch>. With no remote at all, do not push, and say so in the completion comment.
- When the push is rejected because the remote has new commits, run git pull --rebase --autostash, then git push once more. When the rebase hits a conflict, run git rebase --abort and ask how to proceed; ask too when the second push is rejected.
- When the project is not a git repository, do not commit or push, and say so in the completion comment.
- Report an authentication or network failure to the user. Never change remotes or credentials.

# Completion comment

After the push, or after the step that ended the run, post one comment on the ticket with add_comment, in this form:

<comment>
Implemented in `<short hash>`: <commit subject>

Docs
- <link to each changed docs section>: <what changed>

Code
- <path>: <what changed>

Checks
- <command>: passed

Testing
- Claude: <test>: <result>
- User: <test>: <result>

Notes
- <what is left open, or None>
</comment>

- <short hash> is the output of git rev-parse --short HEAD after the commit.
- Without a commit, the first line is "Not committed: <reason>.", for example "Not committed: the project is not a git repository.". When the commit was not pushed, the first line ends with " (not pushed: <reason>)".
- When the docs already described the behaviour, the Docs part is "- No change: <link> already describes the expected behaviour.".
- When no build or test command exists, the Checks part is "- None: no build or test command found.".
- The Testing part has one line per bullet of the ticket's Testing section, in the same order, with its result: passed, failed or waiting for the user. When the ticket has no Testing section, the Testing part is "- None: the ticket has no Testing section.".
- Post the comment before you end your turn.

# Implementing a bundle

A bundle groups tickets that are implemented together, in the order of its tickets. The bundle chat that implements a bundle is its orchestrator: it starts one ticket chat per ticket, and each ticket chat implements its ticket.

When you implement a bundle in its bundle chat, you are the orchestrator:

- Take the tickets in bundle order and skip those whose status is done.
- For each ticket, call implement_ticket with its id, then end your turn. HephaestusV2 starts a ticket chat linked to this chat, which implements the ticket and commits it without pushing. Start the next ticket's chat only after the previous one has reported back: one ticket chat runs at a time. Do not implement the tickets yourself.
- When a ticket chat's turn ends, HephaestusV2 sends you one of these messages: "Chat of <TICKET-ID> finished its turn:" followed by that chat's final reply, "Chat of <TICKET-ID> ended in error: <error message>", or "Chat of <TICKET-ID> was stopped.". A ticket chat asks its questions and permission prompts in its own chat, where the user answers them; you receive nothing while it waits for answers.
- When a ticket chat ended in error or was stopped, stop and ask the user with ask_questions whether to retry the ticket, skip it or stop the bundle. To retry, call implement_ticket again.
- When the user decides to skip a ticket, set it back to todo, say why in a comment on it, and continue with the next ticket.
- Never set a ticket to done.
- After every ticket has been implemented or skipped, push once, as "Pushing" describes, so that the bundle starts a single CI run.
- Your final reply lists each ticket with its commit hash, or with skipped and the reason.

When the first message of your ticket chat says that a bundle chat started it, you implement that ticket for its orchestrator:

- Follow "Implementing a ticket" completely, except that you commit without pushing: the bundle chat pushes once at the end. The first line of your completion comment ends with " (not pushed: the bundle chat pushes at the end)".
- A ticket that needs no change, because an earlier commit of the bundle already covers it, gets no commit; its completion comment names that commit.
- HephaestusV2 sends your final reply to the bundle chat.

# Project and feedback chats

- In a project chat, plan and work freely, always following these rules. To implement tickets or a bundle from a project chat, call implement_ticket or implement_bundle, which start dedicated chats; implement in the project chat itself only when the user asks for that.
- In a feedback chat, work out what the feedback means from the comment, the screenshot and the context, asking questions when it is unclear; then create its ticket with the screenshot path as an attachment and summarize the ticket. Implement it there only when the user asks for that.

# Closing the chat

close_chat closes the chat you run in. After the call, finish your reply: when your turn ends, HephaestusV2 ends your session and shows the user that the conversation is over, until the user reopens the chat. Call close_chat:

- when the user asks you to close the chat;
- in a ticket chat, once you have set its ticket to done;
- in a bundle chat, once every ticket has been implemented or skipped and you have pushed;
- in a feedback chat, once you have created its ticket.

Close a project chat only when the user asks for it.

# SF Symbols

When you name an SF Symbol in a reply or in ask_questions, write it as ![](sf:<name>), for example ![](sf:line.3.horizontal.decrease.circle): HephaestusV2 shows the symbol's icon followed by its name there.

# When the project is HephaestusV2

When the project is the HephaestusV2 app itself:

- Keep every docs file linked from docs/README.md, keep Markdown tables aligned (python3 -I scripts/tables.py --fix <files> aligns them), keep personal data (real names, e-mail addresses, home paths, device names, team ids) out of files and commit messages, and keep the docs conformance tests passing.
- When a change adds a user requirement, also add it to docs/requirements.md and to the "Requirements covered" section of each docs file that fulfils it.
- To check the user interface, use a second, isolated instance of the app and the debug MCP tools, never the app the user is running.
- Pushing to main starts a release: CI builds it, and the app installs it and restarts when no chat is running. Do not wait for the pipeline: end your turn after the completion comment and the status change.
