# Projects

A project is a folder that contains `.hephaestus/project.yml`. It has a display name and an identifier of 2 to 8 letters chosen at creation, and the identifier is the project's id everywhere: in the engine API, in MCP tools, in ticket and bundle ids and in navigation targets. A sub project is a normal project whose folder lies inside its parent's folder. This document specifies the identifier rules, the registry and the project tree, how projects and sub projects are created, opened and removed (with local and remote folder picking), the HephaestusV2 project that every device has, the project selector's rules and the Project Settings section. File formats are in [Data model](data-model.md) and method signatures in [Engine API](engine-api.md#projects).

## Project model

| Field of `project.yml`                 | Meaning                                                                                                                                                                | Changed by                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `id`                                   | The [identifier](#identifier-rules); the project's `projectID` in the API, in MCP tools and in `NavigationTarget`.                                                     | `projects.create`, once                                                        |
| `name`                                 | Display name: single line, 1 to 100 characters; two projects may have the same name.                                                                                   | [Project Settings](#project-settings), `projects.update`, MCP `update_project` |
| `created`                              | Creation time.                                                                                                                                                         | `projects.create`                                                              |
| `type`                                 | The [project type](#project-types): `none`, `goService` or `swiftApplication`; `none` when the key is absent.                                                          | `projects.create`, Project Settings, `projects.update`, `update_project`       |
| `color`                                | The project's color: `#RRGGBB` in uppercase; no color when the key is absent. The ticket list draws the project's badge in it ([Ticket list](tickets.md#ticket-list)). | Project Settings, `projects.update`, `update_project`                          |
| `icon`                                 | The project's icon: the name of an SF Symbol; no icon when the key is absent ([Project settings](#project-settings)).                                                  | Project Settings, `projects.update`, `update_project`                          |
| `nextTicketNumber`, `nextBundleNumber` | Next ticket and bundle numbers ([Id allocation](data-model.md#id-allocation)).                                                                                         | the engine                                                                     |
| `docsPath`                             | Docs folder, relative to the project root; `docs` by default; the folder may be missing ([Documentation viewer](documentation-viewer.md)).                             | Project Settings, `projects.update`, `update_project`                          |
| `githubPage`                           | The page typed in the GitHub page field, `https://github.com/<owner>/<name>`; absent when the field is empty ([GitHub page](#github-page)).                            | Project Settings, `projects.update`                                            |
| `useParentSettings`                    | Whether a sub project uses its parent's settings; `true` when the key is absent ([Sub projects](#sub-projects)).                                                       | Project Settings, `projects.update`                                            |
| `subprojects`                          | Relative paths of the direct [sub projects](#sub-projects).                                                                                                            | the engine, on create, open and remove                                         |
| `webTabs`                              | The project's web tabs ([Web tabs](web-tabs.md)).                                                                                                                      | the web tab methods; the engine for the [GitHub tabs](web-tabs.md#github-tabs) |
| `skills`                               | Library skills enabled in the project ([Skills](skills.md)).                                                                                                           | `skills.setEnabled`                                                            |
| `chatDefaults`                         | Settings of new chats of the project; absent means the device's `defaultChatSettings` ([Chat settings](chats.md#chat-settings)).                                       | Project Settings, `projects.update`; never Claude                              |
| `environments`                         | The [environments](#environments) of a Go service: the name, URL, optional port and Kubernetes resources of each place where it runs, in the order they were added.    | Project Settings, `projects.update`; never Claude                              |
| `environmentOverrides`                 | A sub project's changes to the [environments it inherits](#inherited-environments) from its parent, keyed by environment name.                                         | Project Settings, `projects.update`; never Claude                              |

### Project types

| Stored value       | Shown as            |
| ------------------ | ------------------- |
| `none`             | `None`              |
| `goService`        | `Go service`        |
| `swiftApplication` | `Swift application` |

The type lets the app show content and offer tools that depend on it: the `goService` type adds the Go Service category to the sidebar, with the API Explorer of the contract `openapi/contract.yaml` ([Sidebar](ui.md#sidebar), [API Explorer](openapi.md#api-explorer)) and the Environments section to Project Settings, whose environments the Contract view sends its requests to ([Environments](#environments), [Environment](openapi.md#environment)), and the `swiftApplication` type enables the MCP tools `ask_sound`, with which Claude asks the user to choose a sound for an app of an Apple platform ([Sound requests](chats.md#sound-requests)), `ask_shortcut`, with which Claude asks the user to choose a keyboard shortcut ([Shortcut requests](chats.md#shortcut-requests)), and `ask_animation`, with which Claude asks the user to choose a SwiftUI animation ([Animation requests](chats.md#animation-requests)); in a chat of a project of another type, `ask_sound`, `ask_shortcut` and `ask_animation` fail with `forbidden` ([ask_sound](mcp.md#ask_sound), [ask_shortcut](mcp.md#ask_shortcut), [ask_animation](mcp.md#ask_animation)). The `goService` type also changes the workflow of Claude: the tickets of a Go service project have only Claude tests, and after the push the chat that implemented them waits for CI to be green, through a CI chat when the project has a GitHub page ([Waiting for CI](workflow.md#waiting-for-ci)), tests them on a test service run from the repository's Docker image and sets them to done ([Go service projects](workflow.md#go-service-projects)). `none` is the default: a project created without a type, and a `project.yml` without the key `type`, have the type `none`. The New Project and New Sub Project sheets set `goService` for a project folder that has `go.mod` until the user picks a type ([Creating a project](#creating-a-project)). Every menu of project types lists the three values in this order. The system prompt of every chat gives the project's type by the name it is shown as ([Placeholders](chats.md#placeholders)). The stored values are design-time choices. Default chosen at design time.

The project root is the folder that contains `.hephaestus/`. Tickets, bundles, attachments and chats are stored under `.hephaestus/` ([Project folder layout](data-model.md#project-folder-layout)); the exact format of `project.yml` is in [Project file](data-model.md#project-file).

## Identifier rules

| Rule         | Detail                                                                                                                                     | Origin                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------ |
| Characters   | 2 to 8 letters `A` to `Z`. Digits, spaces, accented letters and punctuation are refused.                                                   | Brief §1                       |
| Case         | Typed in any case, stored and shown in uppercase: `heph` becomes `HEPH`.                                                                   | Brief §1                       |
| Uniqueness   | Unique among all projects loaded on the device, top-level projects and sub projects at any depth.                                          | Brief §1                       |
| Reserved     | `HEPH` is reserved for the [HephaestusV2 project](#hephaestusv2-project): no other project gets it.                                        | The user                       |
| Immutability | Set at creation. No screen, engine method or MCP tool changes it.                                                                          | Brief §1                       |
| Use          | It is the project's id. Ticket ids are `<IDENT>-<n>` and bundle ids `<IDENT>-B<n>` ([Identifiers](engine-api.md#identifiers)).             | Brief §1                       |
| Scope        | Uniqueness is per device: two devices may each have a project `HEPH`, because a window and a chat only address the projects of one device. | Default chosen at design time. |

A typed identifier is valid when it matches `^[A-Za-z]{2,8}$` and, uppercased, is not the id of a loaded project of the window's device. The sheets check this while the user types and show the message under the field:

| Condition                            | Message                                        |
| ------------------------------------ | ---------------------------------------------- |
| The field is empty                   | `Enter an identifier.`                         |
| The value does not match the pattern | `Use 2 to 8 letters (A–Z).`                    |
| The value is `HEPH`, in any case     | `HEPH is reserved for HephaestusV2.`           |
| A loaded project uses it             | `<IDENT> is already used by “<project name>”.` |

The engine checks again; its errors (`identifier: use 2 to 8 letters A–Z.`, `HEPH is reserved for HephaestusV2.`, `Identifier HEPH is already used by Hephaestus V2.`) are shown the same way ([projects.create](engine-api.md#projectscreate)). The sheets refuse `HEPH` in every folder, while the engine accepts it for a folder whose origin names the HephaestusV2 repository ([HephaestusV2 project](#hephaestusv2-project)). Default chosen at design time. The `HEPH is reserved for HephaestusV2.` message comes from the user; the other sheet messages are design-time texts. Default chosen at design time.

While the user has not edited the identifier field, the New Project and New Sub Project sheets fill it from the name: the name's letters with their diacritics removed (`é` becomes `E`), uppercased, keeping only `A` to `Z`, first four of them. `Hephaestus V2` gives `HEPH`, `Go API` gives `GOAP`. A name with fewer than 2 such letters leaves the field empty. A suggestion that is already used stays in the field with its message. Default chosen at design time.

## Registry and project tree

- `registry.yml` lists the root paths of the top-level projects in registration order ([Registry file](data-model.md#registry-file)). Sub projects are not listed there: each is reached through its parent's `subprojects` ([Sub project entries](data-model.md#sub-project-entries)).
- At start the engine loads every registered project and, recursively, the sub projects they list. A project whose `project.yml` is missing or invalid, or whose identifier is already used by a project loaded before it, is skipped and logged, its entry is kept, and it loads as soon as its file becomes valid ([Projects](engine-api.md#projects), [Loading](data-model.md#loading)). A project with the identifier `HEPH` whose origin does not name the HephaestusV2 repository is skipped the same way ([HephaestusV2 project](#hephaestusv2-project)).
- Then the engine checks that the device's HephaestusV2 project is loaded, and clones it when it is not ([HephaestusV2 project](#hephaestusv2-project)).
- `projects.list` returns every loaded project in depth-first order: the top-level projects in `registry.yml` order, each followed by its descendants in `subprojects` order. Every project menu and project picker of the UI shows projects in this order, sub projects indented by depth. Default chosen at design time. A hidden HephaestusV2 project and its sub projects are left out ([Hiding the HephaestusV2 project](#hiding-the-hephaestusv2-project)).
- Absolute paths are standardized by the engine before use ([Paths](engine-api.md#paths)).
- Creating or opening a project inside the folder of a loaded project makes it a sub project of that project ([Creating a project](#creating-a-project), [Opening an existing project](#opening-an-existing-project)).

## Creating a project

| Entry point                                                                                | Sheet                                                                                         |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| File ▸ New Project… (⇧⌘N), Project segment ▸ New Project…, the welcome view's New Project… | New Project                                                                                   |
| Project ▸ New Sub Project…, Sub project segment ▸ New Sub Project…                         | New Sub Project ([Sub projects](#sub-projects))                                               |
| `Create Project Here…` after opening a folder without a project                            | New Project in Existing Folder mode, with that folder                                         |
| Claude, MCP tool `create_project`                                                          | none: `projects.create` with `createDirectory` true ([create_project](mcp.md#create_project)) |

The entry points are enabled while the window's device is connected ([Menus and keyboard shortcuts](ui.md#menus-and-keyboard-shortcuts)).

| Field          | Control                                                                                                                                | Initial value                                                                                                                 | Rule                                                                                                                                                                        |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name           | text field                                                                                                                             | empty; with `Create Project Here…`, the folder's name                                                                         | single line, 1 to 100 characters after trimming; message `Enter a name of 1 to 100 characters.`                                                                             |
| Identifier     | text field, shown in uppercase, SF Mono                                                                                                | the suggestion from the name                                                                                                  | [Identifier rules](#identifier-rules)                                                                                                                                       |
| Project type   | menu of the [project types](#project-types)                                                                                            | `None`, or `Go service` for a project folder with `go.mod`                                                                    | follows the project folder until the user picks a type                                                                                                                      |
| Parent project | pop-up button: `None`, a separator, then every project of the window's device in `projects.list` order, sub projects indented by depth | `None`, or the innermost loaded project that contains the project folder                                                      | follows the project folder until the user picks a value; `None` makes a top-level project; with a project selected, the folder rules of [Sub projects](#sub-projects) apply |
| Folder         | segmented control `New Folder` / `Existing Folder`                                                                                     | `New Folder`; `Existing Folder` with `Create Project Here…`                                                                   | —                                                                                                                                                                           |
| Parent folder  | New Folder mode: read-only path in SF Mono and a `Choose…` button                                                                      | the folder that contains the root of the active project's top-level project; with no active project, the device's home folder | an existing folder                                                                                                                                                          |
| Folder name    | New Folder mode: text field                                                                                                            | the name with `/` and `:` replaced by `-`, trimmed, without leading `.`; it follows the name until the user edits it          | 1 to 255 UTF-8 bytes, no `/`, not starting with `.`; message `Enter a folder name without “/” that does not start with “.”.`                                                |
| Folder         | Existing Folder mode: read-only path in SF Mono and a `Choose…` button                                                                 | none, or the folder of `Create Project Here…`                                                                                 | an existing folder; message `Choose a folder.` while empty                                                                                                                  |
| Project folder | read-only text                                                                                                                         | the resulting root path: parent folder + `/` + folder name, or the existing folder                                            | —                                                                                                                                                                           |

- `Choose…` opens a folder picker. On This Mac it is an `NSOpenPanel` presented as a sheet of the window: folders only, one selection, folder creation allowed, prompt `Choose`. On a remote device it is the [Choose Folder sheet](#picking-a-folder-on-a-remote-device).
- The device's home folder is the user's home folder on This Mac, and on a remote device the `path` that `fs.browse` returns when called without a path ([fs.browse](engine-api.md#fsbrowse)).
- Until the user picks a type in the `Project type` menu, the type follows the project folder shown in the sheet: `Go service` when that folder has a file named `go.mod` at its root, `None` otherwise: no `go.mod`, a folder that does not exist yet, or no folder chosen. This holds in both folder modes, the folder of `Create Project Here…` included, and in both sheets. Each time the project folder changes, the sheet calls `fs.browse` with it on the window's device and reads `hasGoMod` ([fs.browse](engine-api.md#fsbrowse)); a call that fails counts as no `go.mod`. Once the user picks a type, choosing another folder, editing the folder name or switching the folder mode leaves the type as it is. Only `go.mod` is detected: no file sets `Swift application`.
- Until the user picks a value in the `Parent project` pop-up, `None` included, the New Project sheet's parent follows the project folder shown in the sheet: the innermost loaded project whose root strictly contains that folder, at any depth, or `None` when no loaded project contains it. This holds in both folder modes. In Existing Folder mode the folder is the chosen folder, the folder of `Create Project Here…` included. In New Folder mode it is parent folder + folder name, so a parent folder that is a project's root or lies inside a project selects that project. The parent is computed from the `rootPath` of the loaded projects of the window's device, each time the project folder or the loaded projects change. A parent selected this way leaves the parent folder as it is. Once the user picks a value, choosing another folder, editing the folder name or switching the folder mode leaves `Parent project` as it is. The New Sub Project sheet's parent does not follow the folder ([Sub projects](#sub-projects)).
- Picking in `Parent project` a project other than the one it shows sets the parent folder to that project's root ([Sub projects](#sub-projects)). Picking `None` leaves the parent folder and the folder as they are.
- When the project folder is inside the root of a loaded project and `Parent project` is `None`, the New Project sheet shows the note `This folder is inside “<project name>”: the new project becomes its sub project.`, computed from the `rootPath` of the loaded projects. Until the user picks a value, `Parent project` names that project, so the note shows only after the user has picked `None`. While a parent is selected the sheet shows no note: the `Parent project` field names the parent. The New Sub Project sheet never shows the note.
- Buttons: `Cancel` and `Create` (default button). Create is enabled when every field is valid.

The New Folder and Existing Folder modes, the initial values, the folder name rules and the inside-a-project note are design-time choices. Default chosen at design time.

Create calls `projects.create` with:

| Param             | Value                                                       |
| ----------------- | ----------------------------------------------------------- |
| `rootPath`        | the project folder shown in the sheet                       |
| `name`            | the trimmed name                                            |
| `identifier`      | the identifier as typed; the engine uppercases it           |
| `type`            | the chosen project type                                     |
| `parentID`        | the selected parent; absent when `Parent project` is `None` |
| `createDirectory` | `true` in New Folder mode, `false` in Existing Folder mode  |

The engine validates, creates the folder when needed (an existing folder is used as it is), writes `.hephaestus/project.yml` and `.hephaestus/.gitignore`, and registers the project: in the `subprojects` of the selected parent; without one, in the `subprojects` of the innermost loaded project that contains the folder, or in `registry.yml` when there is none ([projects.create](engine-api.md#projectscreate)). It does not create the docs folder, does not run `git init` and leaves untouched the registered projects that lie inside the new folder.

- On success the sheet closes and the window activates the new project (`WindowState.projectID`, [WindowState](ui.md#windowstate)). The section does not change.
- On failure the engine's message shows in red under the fields and the sheet stays open. When the folder already contains a project (`conflict`, `<rootPath> already contains a project; open it instead.`), an `Open It` button follows the message: it calls `projects.open` with the same path, closes the sheet on success and activates the opened project. Default chosen at design time.
- While the window's device is disconnected, Create fails with the connection's error, shown the same way.

## Picking a folder on a remote device

A window that shows a remote device cannot use `NSOpenPanel`, which browses This Mac. Its folder pickers use the Choose Folder sheet, which lists the main device's folders with `fs.browse` ([fs.browse](engine-api.md#fsbrowse), [Remote windows](remote.md#remote-windows)).

| Element       | Behaviour                                                                                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Title         | `Choose a Folder on <device name>`; `Open a Project on <device name>` when it is opened by Open Project…                                                                                    |
| Path bar      | The components of the current folder's path as buttons, from `/`; clicking one browses that folder.                                                                                         |
| Up            | Button with `chevron.up`: browses `parent`; disabled at `/`.                                                                                                                                |
| Home          | Button with `house`: calls `fs.browse` without a path.                                                                                                                                      |
| Go to field   | Text field with the placeholder `/Users/example/Developer`; Return browses the typed absolute path.                                                                                         |
| Folder list   | The `entries` of the result in their order, each row with the `folder` icon and the name; a row with `hasProject` shows the tag `Project`. Double-click or Return on a row browses into it. |
| Cancel        | Closes the sheet without a choice (Escape).                                                                                                                                                 |
| Choose / Open | Default button, titled `Open` when opened by Open Project…, otherwise `Choose`. It returns the selected row's path, or the current folder when no row is selected.                          |

- The first folder shown is the folder of the field that opened the sheet when it has a value, otherwise the result of `fs.browse` without a path.
- While a call is in flight, a spinner shows in the path bar and the previous list stays visible.
- A failed call (`invalid`, `notFound` or a connection error) shows its message in red under the list; the current folder does not change.
- The list shows what `fs.browse` returns: sub-folders whose name does not start with `.`, in Finder order.

The layout, the texts and the first folder are design-time choices. Default chosen at design time.

## Opening an existing project

1. File ▸ Open Project… (⌘O), Project segment ▸ Open Project… or the welcome view's Open Project… asks for a folder. On This Mac it is an `NSOpenPanel` presented as a sheet of the window: folders only, one selection, no folder creation, prompt `Open`, message `Choose a folder that contains .hephaestus/project.yml.`, starting in the default parent folder of [Creating a project](#creating-a-project). On a remote device it is the [Choose Folder sheet](#picking-a-folder-on-a-remote-device) titled `Open a Project on <device name>`.
2. The window calls `projects.open` with the chosen folder ([projects.open](engine-api.md#projectsopen)).
3. On success the window activates the returned project, as for a created project. This includes a folder that is already a loaded project's root, which the engine returns unchanged, except the root of a hidden HephaestusV2 project or of one of its sub projects, which fails with `HephaestusV2 is hidden. Show it in Settings ▸ General.` ([Hiding the HephaestusV2 project](#hiding-the-hephaestusv2-project)).

A folder whose `project.yml` has the identifier `HEPH` and whose origin does not name the HephaestusV2 repository fails with `HEPH is reserved for HephaestusV2.` ([HephaestusV2 project](#hephaestusv2-project)).

What the engine does on open:

- A folder inside the root of a loaded project becomes a sub project of the innermost one: its path, relative to that project's root, is appended to that project's `subprojects`.
- Otherwise its root is appended to `registry.yml`.
- The sub projects the opened project lists are loaded with it; a top-level `registry.yml` entry that is now loaded as one of its descendants is removed from `registry.yml`.

| Error                                                   | Presentation                                                                                                                                                                                                                                                  |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `notFound`                                              | Alert `No project in “<folder name>”` with the message `The folder has no .hephaestus/project.yml.` and the buttons `Create Project Here…` and `Cancel` (default). Create Project Here… opens the New Project sheet in Existing Folder mode with that folder. |
| `invalid`, `conflict`, `internal` or a connection error | Alert `Open Project failed` with the engine's message ([Principles](ui.md#principles)).                                                                                                                                                                       |

Both pickers return existing folders, so `notFound` means that the chosen folder has no `.hephaestus/project.yml`.

The panel texts and the `No project` alert are design-time choices. Default chosen at design time.

## Sub projects

A sub project is a normal project whose folder is strictly inside its parent's folder and whose path, relative to the parent's root, is listed in the parent's `subprojects`. Sub projects may nest.

- The New Project sheet chooses a parent in its `Parent project` field, which lists every project of the window's device and, until the user picks a value, selects the innermost loaded project that contains the project folder ([Creating a project](#creating-a-project)).
- New Sub Project… opens the New Sub Project sheet: the fields of the [New Project sheet](#creating-a-project), titled `New Sub Project`, whose `Parent project` field is its first row and lists, without `None`, the active project's top-level project and all its descendants in `projects.list` order, indented by depth, initially the window's active project; it does not follow the project folder. Its parent folder starts at that project's root.
- In both sheets, while a parent is selected: in New Folder mode the parent folder must be the parent project's root or a folder inside it, and picking another parent in the pop-up sets the parent folder to that parent's root; in Existing Folder mode the folder must be strictly inside the parent project's root. Otherwise the sheet shows `Choose a folder inside “<parent name>”.` and Create stays disabled.
- Create calls `projects.create` with `parentID` = the selected parent; the engine appends the folder's relative path to that parent's `subprojects`.
- Opening a project folder that lies inside a loaded project also makes it a sub project ([Opening an existing project](#opening-an-existing-project)).
- A sub project has its own identifier, tickets, bundles, chats, web tabs, enabled skills, docs folder and GitHub page field. The sections of a parent show only the parent's own items, except the Tickets section, which also lists the tickets of all the parent's loaded descendants ([Tickets section](tickets.md#tickets-section)); the parent's Code section shows a sub project's folder as an ordinary folder ([Code editor](code-editor.md)). Search's `This project` uses the window's active project ([Project filter](search.md#project-filter)).
- A sub project's [Project Settings](#project-settings) have the checkbox `Use parent settings`, right after Parent. It is on for a new sub project and for a sub project whose `project.yml` has no `useParentSettings` key, and its state is stored as `useParentSettings`. It covers two settings. While it is on, the GitHub page field shows the parent's GitHub page, disabled, and the sub project's GitHub page is its parent's, which may itself come from the parent's parent ([GitHub page](#github-page)); and a `goService` sub project has its parent's environments, as the parent resolves them, before its own, and changes only their URL, port, deployment and Argo CD application ([Inherited environments](#inherited-environments)). While it is off, the sub project's own GitHub page field and its origin apply, and only its own environments: the changes it made to inherited environments are kept, unused. Top-level projects have no checkbox, and their `useParentSettings` has no effect until they become sub projects.
- A sub project always inherits the memories of its ancestors whose memory folder differs from its own, for example ancestors in another git repository: its chats receive them besides its own, and its Memories section lists them read-only ([Inherited memories](memories.md#inherited-memories)). `Use parent settings` does not affect memories.
- An entry of `subprojects` whose folder or `project.yml` is missing or invalid stays in the file and is skipped while loading ([Sub project entries](data-model.md#sub-project-entries)).
- The sidebar's Sub Projects category lists every loaded descendant of the window's active project, indented by depth, each with its icon in its color; a click on one shows its Dashboard without switching the active project, and the window keeps its section ([Sidebar](ui.md#sidebar), [Dashboard › Section](dashboard.md#section)).
- A sub project is removed like any project ([Removing a project](#removing-a-project)): its entry leaves its parent's `subprojects`.

The New Sub Project sheet's parent picker and the folder constraints are design-time choices. Default chosen at design time.

## Removing a project

Project ▸ Remove Project… removes the window's active project, top-level or sub project, from HephaestusV2. Every user, on This Mac or on a remote device, may remove projects; Claude can, with `remove_project`, except the project its chat belongs to and that project's ancestors ([Rules for Claude](engine-api.md#rules-for-claude)).

The HephaestusV2 project and its ancestors cannot be removed ([HephaestusV2 project](#hephaestusv2-project)):

- Project ▸ Remove Project… is not shown while the window's active project is the HephaestusV2 project or one of its ancestors. The window recognizes it as its device's project `HEPH`, which the engine loads only for the HephaestusV2 project. Default chosen at design time.
- `projects.remove` and Claude's `remove_project`, called on it or on one of its ancestors, fail with `forbidden` and the message `“<project name>” cannot be removed: it is the HephaestusV2 project. Hide it in Settings ▸ General instead.`, where `<project name>` is the name of the HephaestusV2 project ([projects.remove](engine-api.md#projectsremove)).

1. The window runs the unsaved editors check for the project and its descendants ([Unsaved changes and quitting](ui.md#unsaved-changes-and-quitting)).
2. It shows the alert `Remove “<project name>” from HephaestusV2?` with the message below and the buttons `Remove` (destructive) and `Cancel` (default).
3. Remove calls `projects.remove` ([projects.remove](engine-api.md#projectsremove)). The engine unregisters the project and all its descendants, terminates the Claude processes of their chats and emits `project.removed` for each of them. No file is changed or deleted: `.hephaestus/`, its tickets, bundles and chats stay in the folders.

The message is `The folder and its files stay on disk: <root path>.`, followed by `Its sub project “<name>” is removed with it.` when the project has one descendant or `Its <n> sub projects are removed with it.` when it has n > 1, followed by `Running chats of these projects are stopped.` when the window's workspace knows a working chat among them: a chat in state `starting`, `running` or `waitingPermission`, or with background work running ([Chat states](chats.md#chat-states)).

When `project.removed` arrives, every client reacts:

| Window                                            | Reaction                                                                                                                                                                           |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A main window whose active project was removed    | Activates the nearest ancestor of that project that is still loaded; with none, the device's default project ([Project selector](#project-selector)); with none, the welcome view. |
| A chat window showing a chat of a removed project | Closes.                                                                                                                                                                            |
| Unsaved editors of a removed project              | Discarded.                                                                                                                                                                         |

Opening the folder again with Open Project… registers the project again with its tickets, bundles and chats.

## HephaestusV2 project

Each device has one HephaestusV2 project: the project of the app's own repository, which receives all feedback ([Feedback](feedback.md#feedback-project)). The repository URL `https://github.com/Azavech/HephaestusV2` is hardcoded in the app; the Info.plist key `HephaestusReleaseRepository` is read only by the Updater and Settings ▸ Updates ([Info.plist keys](ci.md#infoplist-keys)).

### Recognition

The HephaestusV2 project of a device is its loaded project with the identifier `HEPH` whose `origin` remote names `Azavech/HephaestusV2`.

- A remote URL names `Azavech/HephaestusV2` when its path, without the leading `/`, a trailing `/` and a trailing `.git`, equals `Azavech/HephaestusV2`, compared case-insensitively, whatever its host. The forms read are `https://`, `http://`, `ssh://` and `git://` URLs, with or without user info and port, and the scp-like form `[<user>@]<host>:<path>`, whose host may be an SSH host alias, for example `git@github-alias:Azavech/HephaestusV2.git`.
- The engine reads the origin without running `git`: the last `url` of the `[remote "origin"]` section of the configuration of the repository that holds the project root, found in the `.git` folder of the root or of its nearest parent folder that has one; a `.git` file (`gitdir: <path>`) and the `commondir` of a linked worktree are followed. Default chosen at design time.
- A project with the identifier `HEPH` whose origin does not name `Azavech/HephaestusV2`, or that has no origin, is not loaded: at start, and each time the engine loads projects, it is skipped like a project whose identifier is already used; its registry entry is kept and the skip is logged ([Loading](data-model.md#loading)).
- A clone of the repository whose identifier is not `HEPH` is a regular project.

### Reserved identifier

`HEPH` is reserved for the HephaestusV2 project ([Identifier rules](#identifier-rules)).

- `projects.create`, and so the New Project and New Sub Project sheets and Claude's `create_project`, refuse the identifier `HEPH` with `invalid` and the message `HEPH is reserved for HephaestusV2.`, unless the project folder exists and its origin names `Azavech/HephaestusV2` ([projects.create](engine-api.md#projectscreate)). The sheets show that message under the Identifier field as soon as `HEPH` is typed.
- Open Project… on a folder whose `project.yml` has the identifier `HEPH` and whose origin does not name `Azavech/HephaestusV2` fails with the alert `Open Project failed` and the message `HEPH is reserved for HephaestusV2.` ([projects.open](engine-api.md#projectsopen)).

### Launch check and clone

At every launch, once the tools are looked up ([Startup](architecture.md#startup), step 7), each device's engine checks that its HephaestusV2 project is loaded, whether it is shown or hidden. When it is not, the engine clones `https://github.com/Azavech/HephaestusV2` into `<data dir>/HephaestusV2` and registers that folder as a top-level project:

1. When `<data dir>/HephaestusV2` already exists and its origin names `Azavech/HephaestusV2`, the engine uses it as it is and skips the clone. When it exists with another origin or none, the attempt fails and is logged, and the folder is left untouched. Default chosen at design time.
2. Otherwise the engine deletes `<data dir>/.HephaestusV2.clone` when it exists, runs `git clone --quiet https://github.com/Azavech/HephaestusV2 <data dir>/.HephaestusV2.clone` in the data directory, with `GIT_TERMINAL_PROMPT=0` so that git never asks for credentials, and renames that folder to `<data dir>/HephaestusV2` once the clone succeeded. A failed clone deletes the temporary folder. The clone has a timeout of 10 minutes ([Child processes](architecture.md#child-processes)). Default chosen at design time.
3. When the folder has no `.hephaestus/project.yml`, the engine creates it with the name `HephaestusV2`, the identifier `HEPH`, the type `swiftApplication` and the docs folder `docs`, and writes `.hephaestus/.gitignore` with the line `chats/`, as `projects.create` does.
4. The folder's root is appended to `registry.yml`, even when it lies inside a loaded project, and the project loads; the engine emits `project.updated` and `projects.changed`.

- One attempt runs at a time. When a HephaestusV2 project is loaded before the attempt ends, for example a clone the user opened, the attempt registers nothing; a finished clone stays on disk. Default chosen at design time.
- When the attempt fails (no network, `git` not found, a timeout, a folder that cannot be written), the engine logs the reason and tries again at the next launch and each time feedback starts for that device: the feedback sheet calls `projects.ensureHephaestus` on the receiving device ([projects.ensureHephaestus](engine-api.md#projectsensurehephaestus), [Feedback sheet](feedback.md#feedback-sheet)).
- While the attempt runs or after it failed, the device has no HephaestusV2 project and feedback cannot be sent to it ([Feedback sheet](feedback.md#feedback-sheet)).
- The test engines of `swift test` have no HephaestusV2 project unless a test configures one ([Engine configuration](architecture.md#engine-configuration)).

### Hiding the HephaestusV2 project

Settings ▸ General has the toggle `Show the HephaestusV2 project`, on by default, with the caption `Hiding it also turns off Send Feedback.` under it ([General](ui.md#general)). Like every control of the Settings window, it changes This Mac's host settings: the key `showHephaestusProject` ([Settings file](data-model.md#settings-file)). Each device has its own value.

While the toggle is off, the HephaestusV2 project and its sub projects stay registered and loaded in the engine, but are hidden everywhere from the clients and from Claude:

- They are left out of `projects.list`, of the projects of `snapshot.get` and of `projects.changed`, and out of the sub projects of a `ProjectDetail` and the `subprojectIDs` of a `ProjectSummary`. As a result, the breadcrumb menus, the default project of a window, search results ([Project filter](search.md#project-filter)), the Dashboard, Claude's `list_projects`, the chats popover, the Running chats and Waiting chats counts of the status bar, the Dock badge and chat notifications leave them and their chats out.
- Every call of a user or of Claude that names one of them by id fails with `notFound`, as for a project that is not registered: Claude's `get_project`, `list_tickets` and `create_ticket`, `open_in_app`, navigation targets and engine calls. The engine checks the params `projectID`, `parentID`, `ticketID`, `ticketIDs`, `bundleID` and `chatID`, and those of a `target`; a ticket, bundle or chat of a hidden project counts as not found (`Ticket HEPH-3 not found.`) ([Dispatcher errors](engine-api.md#dispatcher-errors)).
- The events about them are not emitted, except `project.removed`; `tickets.list` with `includeSubprojects` leaves out their tickets and `search.query` their results.

| Change                 | Effect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Turning the toggle off | The engine terminates the Claude processes of their chats and stops the comment answers of their tickets, as when a project is removed, then emits `project.removed` for each of them, depth first, and `projects.changed`. The clients react as to a removal ([Removing a project](#removing-a-project)): a main window whose active project is one of them activates the device's default project ([Project selector](#project-selector)), or shows the welcome view when there is none; the chat windows of their chats close. |
| Turning the toggle on  | `projects.changed` lists them again. No window switches to them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

- Open Project… on the folder of the hidden HephaestusV2 project, or of one of its sub projects, fails with the alert `Open Project failed` and the message `HephaestusV2 is hidden. Show it in Settings ▸ General.` ([projects.open](engine-api.md#projectsopen)).
- While the receiving device hides its HephaestusV2 project, the feedback entry points are hidden ([Starting feedback](feedback.md#starting-feedback)).
- The launch check and the clone also run while the project is hidden ([Launch check and clone](#launch-check-and-clone)).

The repository URL, the identifier, the recognition, the clone folder, the created `project.yml`, the retry, the removal refusal and the hiding rules come from the user, as do the toggle, its caption and the messages.

### GitHub page

A project's GitHub page is the page of its repository on GitHub, `https://github.com/<owner>/<name>`. It is resolved in this order, and `get_project` and the [ProjectDetail](engine-api.md#projectdetail) give the result as `githubPage`, absent when the project has none:

1. A sub project whose `Use parent settings` is on has its parent's GitHub page, which may itself come from the parent's parent ([Sub projects](#sub-projects)).
2. Otherwise, the value of the project's GitHub page field, the key `githubPage`, when it is set.
3. Otherwise, the page of the project's `origin` remote, when the origin is on GitHub.
4. Otherwise the project has no GitHub page.

- A page typed in the field is valid when, trimmed and without one trailing `/`, it is `https://github.com/<owner>/<name>`, where `<owner>` holds ASCII letters, digits, `-` and `_`, and `<name>` holds ASCII letters, digits, `.`, `-` and `_` and is neither `.` nor `..`. Default chosen at design time (the characters).
- The origin is the project's `gitRemoteURL` ([ProjectDetail](engine-api.md#projectdetail)). Its host, owner and name are read from these forms, each with or without a final `.git`:

| Form                              | Example                                |
| --------------------------------- | -------------------------------------- |
| `git@<host>:<owner>/<name>`       | `git@github-work:owner/name.git`       |
| `ssh://git@<host>/<owner>/<name>` | `ssh://git@github-work/owner/name.git` |
| `https://<host>/<owner>/<name>`   | `https://github.com/owner/name`        |

- In every form, the user may be another one than `git` or be left out, and an `ssh://` or `https://` URL may also carry a password after the user and a port after the host; any other remote has no page. Default chosen at design time.
- The origin is on GitHub when its host is `github.com`, or an SSH host alias (for example `github-work`) for which `ssh -G <alias>` prints the line `hostname github.com`. The origin's page is then `https://github.com/<owner>/<name>`. Only the host of the two SSH forms may be an alias, hosts are compared without regard to letter case, and a page that breaks the rule of the field counts as none. Default chosen at design time.
- The engine runs `ssh -G <alias>` in the background, with the `ssh` of the tools lookup and a timeout of 5 seconds ([Child processes](architecture.md#child-processes)), each time it has read an origin that uses the alias ([ProjectDetail](engine-api.md#projectdetail)); an alias has at most one run at a time, and a run asked for meanwhile starts after it. Until the first run for an alias has ended, and when `ssh` was not found, the origins that use it have no page. Default chosen at design time.
- The field's placeholder is the origin's page, which the ProjectDetail gives as `originGithubPage`; it is empty when the origin has no page. While `Use parent settings` is on, the disabled field has no placeholder, so that it is empty when the parent has no page. Default chosen at design time.
- A change of the field, of the `Use parent settings` checkbox, of the origin remote, of what `ssh -G` prints or of the parent's page emits `project.updated` for every project whose GitHub page changes, so that the windows of every device follow. So does `projects.open` for a top-level project it makes a sub project ([projects.open](engine-api.md#projectsopen)). The engine reads an origin again when a `.git/config` inside a watched project root changes, besides the reads of [ProjectDetail](engine-api.md#projectdetail). Default chosen at design time (the `projects.open` event and the `.git/config` reads).
- A project that has a GitHub page has two [GitHub tabs](web-tabs.md#github-tabs) in its Web section, its GitHub page and its CI page `<GitHub page>/actions`, locked and first in its tab strip. The engine adds them when the project gets a GitHub page, typed, from its origin or from its parent, changes their URLs when the page changes and removes them when the project loses its page; a sub project with its own or an inherited page has its own two tabs ([Keeping the GitHub tabs](web-tabs.md#keeping-the-github-tabs)).

The resolution order, the remote forms, the alias rule, the placeholder and the live updates come from the user.

### Environments

The environments of a Go service are the places where it runs, for example the service started on this Mac and a staging server. Each has a name and its API Access, an optional URL with an optional port, which the Contract view sends its requests to ([Environment](openapi.md#environment)), and a setting that lets those requests accept an invalid server certificate, for example a self-signed one, one issued by a private CA or one that does not name the IP address the URL uses ([Sending a request](openapi.md#sending-a-request)). An environment that runs on Kubernetes also names its kubeconfig file, namespace and deployment, and may name the Argo CD application that deploys it; kubectl always uses the current context of the kubeconfig file. The system prompt of every chat of the project except its CI chats lists them ([Rendered blocks](chats.md#rendered-blocks)), and Claude inspects and operates the deployment and the application with the [Kubernetes and Argo CD tools](mcp.md#kubernetes-and-argo-cd-tools), which take the environment's name. They are stored in the project's `environments` ([Project environment](data-model.md#project-environment)). A sub project that uses its parent's settings also has its parent's environments, whose URL, port, certificate setting, deployment and Argo CD application it may change ([Inherited environments](#inherited-environments)). One of the environments is the project's [current working environment](#current-working-environment), chosen under the project identifier in the sidebar footer, which the Contract view, the Environments section and Claude use.

- When the section appears, the pop-up shows the project's [current working environment](#current-working-environment), and the rows under it show the values of the selected environment; choosing another environment in the pop-up shows its values and does not change the current working environment. When the selected environment is renamed or removed elsewhere, on another device or in `project.yml`, the pop-up shows the first environment.
- When the project has no environment, the pop-up is empty and disabled, `−` is disabled and the rows under the pop-up are hidden.
- `+` adds an environment named `New Environment` at the end of the project's own environments, with every other field empty. When an environment of the project, inherited ones included, already has that name, it is named `New Environment 2`, then `New Environment 3`, and so on: the first of these names that no environment has. Once the change applies, the new environment is selected and the Name field gets the keyboard focus.
- `−` removes the selected environment at once. It is disabled while an inherited environment is selected. After a removal, the pop-up shows the first environment.
- `+` and `−` apply at once, each with `projects.update`; a failure shows the engine's message in red under the Environment row.
- Each field applies on its own, as the other fields of Project Settings do: a text field or a combo box on Return or when it loses the focus, an item of a combo box when it is picked, the Kubeconfig file also when the open panel returns a file, and the `Allow invalid certificates` checkbox at once when it is toggled. A field applies only when its value differs from the stored one. A value that breaks its rule shows its message in red under its row and is not applied; an engine failure also shows in red under the row. The URL and the port share the message line of the API Access row, the URL's message first; an engine failure of the checkbox shows under the checkbox.
- A field that holds a value not applied yet when another environment is selected applies it to the environment it showed, as when it loses the focus.
- Each change calls `projects.update` with `projectID` and `environments`, the whole list of the project's own environments with the change applied: the name and the URL trimmed, the port as a number, or no port when its field is empty, `allowInvalidCertificates` as the checkbox shows it, the namespace, the deployment and the kubeconfig file trimmed, an empty field giving no value; the environment keeps its other stored keys, its Argo CD application and its unknown keys included ([projects.update](engine-api.md#projectsupdate)).
- Names are compared after trimming, letter case included: `Local` and `local` are two names. The selected environment's own name is not a duplicate.
- The base URL of an environment is its URL with the port replaced by its port when it has one, without a trailing `/`: `http://127.0.0.1` with the port 8080 gives `http://127.0.0.1:8080`, `https://api.example.com:8443/v1/` with the port 9000 gives `https://api.example.com:9000/v1`, and `https://staging.example.com/` without port gives `https://staging.example.com`. An environment without a URL has no base URL, whatever its port.
- `Browse…` opens an open panel, as a sheet of the window, that chooses one file, hidden files shown, starting in the folder `~/.kube` of the home folder, or in the home folder when `~/.kube` does not exist. The chosen file applies at once as its absolute path. `Browse…` shows only in windows of This Mac; in a window of a remote device the path is typed. An empty Kubeconfig file field removes the file.
- The connection dot shows only while the selected environment has a kubeconfig file. The main device's engine checks the connection when the environment shows and each time its file changes ([kubernetes.check](engine-api.md#kubernetescheck)): kubectl, with that file and its current context, tries to reach the cluster. The dot works as the Claude CLI status of [Settings › General](ui.md#general): a small spinner while checking, then a green dot when kubectl reaches the cluster, or a red dot when it fails. On failure, the engine's message, with kubectl's error, shows in red under the row.
- The Namespace combo box lists the namespaces of the cluster that kubectl finds with the file ([kubernetes.namespaces](engine-api.md#kubernetesnamespaces)). The Deployment combo box lists the deployments of the environment's namespace, or of the namespace of the file's current context when the environment has no namespace ([kubernetes.deployments](engine-api.md#kubernetesdeployments)). Both lists keep kubectl's order and are read once the dot turns green, and again when the file or the environment's namespace changes. The user can pick a listed name or type any name.
- Without a kubeconfig file, while the connection is checked or fails, and when the cluster refuses to list them, the lists are empty and the fields still accept typed names; a list that cannot be read shows no message.
- kubectl runs on the main device, so the dot and the lists also work in windows of remote devices.
- The checkbox is off for a new environment and for an environment stored before the setting existed. While it is on, the Contract view's requests to the environment accept any invalid server certificate; while it is off, the certificate is checked as for any other request ([Sending a request](openapi.md#sending-a-request)).
- `project.updated` refreshes every field except the one that has the keyboard focus, on every device: the windows of every device follow every change, the section and the Contract view's Environment pop-up included.
- The section has no field for the Argo CD application. A stored `argoCDApplication`, and a sub project's change of it, is kept by every change of the section; `argocd_status`, `argocd_sync`, `get_project` and the system prompt keep using it. It has no field for a kubectl context either: kubectl always uses the current context of the kubeconfig file, and a `context` key that an earlier version stored stays in `project.yml` as an unknown key, unused ([Project environment](data-model.md#project-environment)).
- A renamed environment stays the current working environment when it was, and a removed one gives way to the first environment ([Current working environment](#current-working-environment)). The values stored for the contracts keep no environment ([Stored values](openapi.md#stored-values)).
- Changing the project's type keeps its environments in `project.yml`. A project whose type is not `goService` has no Environments section, and its Contract views have no environment ([Environment](openapi.md#environment)).

The section at the bottom with its separator and heading, the pop-up with `+` and `−` on its right, the rows and their order, the editable Kubeconfig file field with its `Browse…` button opening in `~/.kube` and storing the absolute path, the connection dot working as the Claude CLI status, the Namespace and Deployment combo boxes filled from the cluster, the API Access line with its `:` label and the extra space before it, the `Allow invalid certificates` checkbox on its own line under it, off by default, applied at once and accepting any invalid certificate on every server a request reaches, `+` adding `New Environment` and its numbered names, the typed path in the windows of remote devices, the failure message under the row, the current context of the kubeconfig file without a field, the Argo CD application hidden but kept, and an environment without API Access listed in the Contract view with Send disabled and its message come from the user, as do the names, the URL and the port with the base URL and their messages. The pop-up showing names only, the selection after a rename or removal elsewhere, the failure of `+` and `−` under the Environment row, the shared message line of API Access, the checkbox's failure under it, the value applied when another environment is selected, the hidden files of the open panel, the lists read once the dot is green, in kubectl's order and without failure message, the letter case of names and the environments kept when the type changes are design-time choices. Default chosen at design time.

### Inherited environments

A `goService` sub project whose `Use parent settings` is on inherits the environments of its parent ([Sub projects](#sub-projects)): it does not declare them again and changes only the URL, the port, the certificate setting, the deployment and the Argo CD application that differ. The environments of a project are resolved in this order, and everything that uses environments uses the result: the Environments section, the Contract view's Environment pop-up ([Environment](openapi.md#environment)), `get_project` ([get_project](mcp.md#get_project)), the system prompt ([Rendered blocks](chats.md#rendered-blocks)) and the Kubernetes and Argo CD tools ([Rules of the Kubernetes tools](mcp.md#rules-of-the-kubernetes-tools)).

1. A project whose type is not `goService` has no environments.
2. A sub project whose `Use parent settings` is on first has its parent's environments, as the parent resolves them with these rules, so also those the parent inherits, in the parent's order. Each takes the sub project's change for its name: the URL, the port, the certificate setting, the deployment and the Argo CD application that the change sets replace the parent's; the name, the namespace and the kubeconfig file stay the parent's.
3. Then come the project's own environments, its `environments`, in the order they were added. An environment of its own whose name an inherited environment has, because the parent added that name or the checkbox was turned on afterwards, is left out and kept in `project.yml`; turning the checkbox off brings it back.

- A top-level project, and a sub project whose `Use parent settings` is off, has only its own environments. A parent whose type is not `goService` has none, so its sub projects inherit none.
- The changes are stored in the sub project's `project.yml`, under `environmentOverrides`, keyed by the environment's name ([Environment override](data-model.md#environment-override)). A change for a name that the parent's environments no longer have is ignored and kept in the file; it applies again when an inherited environment has that name. While the checkbox is off, the changes are kept and unused.
- The [ProjectDetail](engine-api.md#projectdetail) gives the result as `environments`, and the inherited environments, as the parent resolves them and without the sub project's changes, as `inheritedEnvironments`.
- A change of a parent's environments, of its type or of its own `Use parent settings`, made in Project Settings or in its `project.yml`, emits `project.updated` for every sub project whose `environments` or `inheritedEnvironments` change, at any depth, so the Environments section and the Contract views of the sub projects follow live on every device ([projects.update](engine-api.md#projectsupdate), [External changes](#external-changes)). So does `projects.open` for a top-level project it makes a sub project ([projects.open](engine-api.md#projectsopen)).

In the Environments section of a sub project that inherits environments, the fields of the selected inherited environment change it for the sub project only:

- While an inherited environment is selected, `Inherited from <parent name>` shows in secondary color after `−` on the Environment row, `<parent name>` being the name of the sub project's parent, and `−` is disabled.
- Name, Kubeconfig file and Namespace show the parent's values, disabled, empty when the parent has none, and `Browse…` is disabled.
- Deployment, URL and Port show the sub project's change, or are empty. An empty field uses the parent's value, which it shows as its placeholder, empty when the parent has none. A field that is not empty has the rule and the message of its row.
- The `Allow invalid certificates` checkbox is enabled and shows the value that applies: the sub project's change when it sets one, else the parent's value.
- Each of the three fields and the checkbox applies on its own, as in [Environments](#environments), with `projects.update`, `projectID` and `environmentOverrides`: all the sub project's changes, with the change of this environment, keyed by its name, made of the stored change with the field's value, trimmed, an empty field giving no value; the stored Argo CD application and unknown keys of the change are kept. The checkbox sets `allowInvalidCertificates` in the change only while its value differs from the parent's; set back to the parent's value, it removes the key from the change. When the change no longer sets any value, it is removed. Clearing a changed field brings back the parent's value.
- The connection dot and the lists use the parent's kubeconfig file, and the Deployment list the parent's namespace.
- The Name field of an environment of the project's own also refuses the name of an inherited environment: `An environment named “<name>” already exists.`, and `+` skips those names too.

The inheritance and its order, the five values a sub project changes, the three fields that change four of them with the parent's values as placeholders, the enabled checkbox showing the value that applies and kept in the change only while it differs from the parent's, the other fields disabled with the parent's values, the disabled `−`, the `Inherited from <parent name>` mark after `−`, the dot and the lists from the parent's kubeconfig file, the changes kept in `project.yml` by name, ignored and kept for an environment the parent no longer has, the name clash and its message, the checkbox turned off and the live updates come from the user. The parent of another type that gives no environments, the environment of its own left out on a name clash, the change removed when it sets no value, the keys of the ProjectDetail and the `projects.open` event are design-time choices. Default chosen at design time.

### Current working environment

Each project whose type is `goService` has a current working environment: the environment the user works with. The Contract view sends its requests to it ([Environment](openapi.md#environment)), the [Environments](#environments) section of Project Settings opens on it, the Instances widgets of the Dashboard list the pods of its deployment ([Instances widget](dashboard.md#instances-widget)), and Claude uses it when the user names no environment ([Rendered blocks](chats.md#rendered-blocks), [get_project](mcp.md#get_project)).

- It is one of the project's environments as they apply, inherited ones included ([Inherited environments](#inherited-environments)). Each project, each sub project included, has its own. A project whose type is not `goService`, and a Go service without environments, has none.
- Until the user chooses one, the first environment is current.
- The user chooses it in the pop-up under the project identifier in the sidebar footer ([Sidebar](ui.md#sidebar)) or in the Environment pop-up of a Contract view ([Environment](openapi.md#environment)); both call [projects.setCurrentEnvironment](engine-api.md#projectssetcurrentenvironment). The pop-up of the Environments section only selects the environment it edits.
- The main device keeps it per project in its own data directory, in `current-environments.yml` ([Current environments file](data-model.md#current-environments-file)), not in `project.yml`: choosing one changes no committed file. Every window, on This Mac and on remote devices, shows the same one: a change emits `project.updated`, whose ProjectDetail names it as `currentEnvironment` ([ProjectDetail](engine-api.md#projectdetail)), and the sidebar footer, the Contract views, the Environments section and the Instances widgets follow at once.
- The first environment becomes current when the current one no longer applies: it was removed, the parent removed it, `Use parent settings` was turned off, or the project's type is no longer `goService`. The engine then forgets the choice, so that an environment that gets the name later does not become current again.
- A rename in the Environments section keeps the renamed environment current under its new name, in the project and in the sub projects that inherit it and have it as their current working environment. `projects.update` takes an environment of `environments` whose name changed at the same position of the list, the list keeping its length, as renamed ([projects.update](engine-api.md#projectsupdate)). A rename made in `project.yml` outside the app counts as a removal.
- Claude reads it, in its system prompt and with `get_project`, and has no tool to change it.

The current working environment of each Go service project and sub project, the pop-up under the identifier in the sidebar footer, the Contract view's pop-up that changes it, the Environments section opening on it and its pop-up that does not change it, its storage on the main device outside `project.yml`, shared by every device and shown at once in every window, the first environment until the user chooses one and after a removal, a parent's removal or `Use parent settings` turned off, the rename that keeps it, and Claude reading it without changing it come from the user. The file and its format, the engine forgetting the choice, the type change, the rename recognized by position and the rename outside the app counted as a removal are design-time choices. Default chosen at design time.

## External changes

`project.yml` may change outside the app (`git pull`, a text editor, Claude editing the file). The engine reloads it and emits `project.updated`, then `project.updated` for every other project whose [GitHub page](#github-page), environments, inherited environments ([Inherited environments](#inherited-environments)) or [current working environment](#current-working-environment) changed, followed by `projects.changed` when the change alters a project's summary (its name, type, color, icon, sub projects or costs), or `project.removed` when the file disappears. A file that becomes invalid, a changed `id` included, leaves the loaded project unchanged; the engine logs a warning and rewrites the file from memory at its next write of the project ([Processing a change](data-model.md#processing-a-change), [Changes made outside the engine](engine-api.md#changes-made-outside-the-engine), [External changes](data-model.md#external-changes)). The windows follow the events: a rename updates the selector, a changed color updates the [project badges](tickets.md#ticket-list) of the ticket lists, a changed `subprojects` list loads or unloads sub projects, a changed `deletedChats` list updates the [costs](costs.md#live-updates), and a removed project is handled as in [Removing a project](#removing-a-project). The engine then checks the [GitHub tabs](web-tabs.md#github-tabs), which follow a changed GitHub page and come back when the change removed or moved them ([Keeping the GitHub tabs](web-tabs.md#keeping-the-github-tabs)).
